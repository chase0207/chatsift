## 1. 结论

原报告确认的 `admin/dist/plugin-downloads` 静态产物耦合成立,且是 P0 发版阻塞。

但风险不只在静态目录。按当前仓库证据,test/prod 还需要补查以下耦合面:

- 发布链路:脚本和部署速查仍偏 prod 单通道。
- Nginx 入口:仓库只有示例和文档,真实宝塔 vhost 需线上核实。
- 机密配置:test/prod 的 DB/JWT 隔离需实测,不能只信 `.env` 约定。
- 插件客户端:serverUrl、env badge、heartbeat/events 实际落点需纳入验收。
- 数据库/服务:compose 设计上已隔离,但线上容器 env 和挂载仍需只读核实。

v0.6.6 不应只修 compose 挂载,应按“环境隔离矩阵”完成最小闭环。

---

## 2. 已确认高风险

### 2.1 发布链路耦合

当前 `scripts/package-plugin.sh` 固定将插件产物写入:

```text
server/public/plugin-downloads/
```

当前 `scripts/release-prod.sh` 会将该目录复制到:

```text
admin/dist/plugin-downloads/
```

`docs/ops/server-access.md` 的部署速查也仍是 prod 口径:

```text
rsync admin/dist/ -> /opt/chatsift/admin/dist/
```

风险:

- 即使 test compose 改为 `/opt/chatsift-test/admin/dist`,操作员仍可能按旧脚本/旧文档把 test 插件产物写入 prod 静态目录。
- `package-plugin.sh` / `release-prod.sh` / `server-access.md` 不是“可能关注”,而是 v0.6.6 必须处理的发布链路。
- 必须提供 test 专用输出目录或明确的 test 发布命令,并保留 prod 发版兼容。

建议:

- `package-plugin.sh` 增加可选输出目录参数,默认行为不变。
- `server-access.md` 明确 prod/test 两套 rsync 目标。
- `release-prod.sh` 保持 prod-only,避免被 test 发版复用。

### 2.2 插件客户端环境状态耦合

插件默认生产地址:

```text
https://admin.kongyuekeji.com
```

popup 通过 `serverUrl` 在 prod/test/local 间切换。历史上 v0.6.4 已修过“test 重开误回 prod”的问题,v0.6.5 又通过 `envHash` 隔离 seen/position。

风险:

- 这说明客户端本地状态曾真实发生过环境串联。
- 静态目录隔离后,如果插件 `serverUrl` 或 token/cache 错误,仍可能把 test 采集数据发到 prod。

建议:

- v0.6.6 验收必须包含插件侧实际落点:
  - popup 显示 test 环境。
  - `cfg.serverUrl` 为 `https://test-admin.kongyuekeji.com`。
  - heartbeat/events 请求落到 test API。
  - prod API 无新增 test 验收数据。

## 3. 需线上核实的中风险

### 3.1 Nginx 入口耦合

文档约定:

```text
prod: admin.kongyuekeji.com      -> 127.0.0.1:3100 -> /opt/chatsift/admin/dist
test: test-admin.kongyuekeji.com -> 127.0.0.1:3101 -> /opt/chatsift-test/admin/dist
```

但仓库中没有真实宝塔 vhost 文件,只能线上只读核实。

必须核实:

- `admin.kongyuekeji.com` 的 `root` 是否为 `/opt/chatsift/admin/dist`。
- `admin.kongyuekeji.com` 的 `/api` 是否反代 `127.0.0.1:3100`。
- `test-admin.kongyuekeji.com` 的 `root` 是否为 `/opt/chatsift-test/admin/dist`。
- `test-admin.kongyuekeji.com` 的 `/api` 是否反代 `127.0.0.1:3101`。

### 3.2 机密配置耦合

仓库约定:

```text
prod DB: chatsift
test DB: chatsift_test
prod JWT_SECRET != test JWT_SECRET
```

v0.6.5 复盘已记录过 `deploy/.env.test` 丢失并从 live 容器反推重建,说明 test 配置管理存在脆弱点。

必须核实:

- `chatsift-server` 容器内 `DB_HOST/DB_NAME/JWT_SECRET` 指向 prod。
- `chatsift-server-test` 容器内 `DB_HOST/DB_NAME/JWT_SECRET` 指向 test。
- test token 不能访问 prod API。
- prod token 不能访问 test API。

### 3.3 数据库与数据卷耦合

仓库 compose 设计上已隔离:

```text
prod: chatsift-mysql      / deploy/data/mysql      / chatsift
test: chatsift-mysql-test / deploy/data-test/mysql / chatsift_test
```

风险主要不在仓库设计,而在线上实际 env 或 compose 启动参数是否偏离。

必须核实:

- test server 实际连接 `mysql-test`,不是 prod mysql。
- test 库名为 `chatsift_test`,不是 `chatsift`。
- test 数据卷路径不是 prod `deploy/data/mysql`。

## 4. 正常共享,不视为问题

以下共享是正常的,不应误判为耦合缺陷:

- test/prod 使用同一份仓库代码。
- test/prod 使用同一套 API path。
- test/prod 使用同一套 Dockerfile。
- test/prod 使用同一套数据库 schema 文件。

关键不在“代码是否同源”,而在运行时入口、配置、数据、产物目录是否隔离。

---

## 5. 建议补入 v0.6.6 的环境隔离矩阵

| 维度 | 必查项 | 通过标准 |
|---|---|---|
| 静态产物 | `/app/public` realpath | prod/test 指向不同宿主目录 |
| 插件元数据 | `metadata.json` realpath + 内容 | test 可变为 0.6.6,prod 保持当前生产版本 |
| 插件 zip | zip sha256 | test/prod 下载各自目录中的 zip,互不覆盖 |
| Nginx | root + `/api` proxy_pass | prod->3100,test->3101;root 各自独立 |
| 服务 | 容器名、端口、compose project | prod/test 容器和端口不重名不互通 |
| 数据库 | DB_HOST/DB_NAME/数据卷 | test 不连接 prod mysql,不使用 prod 库名 |
| JWT | token 互斥 | test token 不能访问 prod,prod token 不能访问 test |
| 插件客户端 | serverUrl + heartbeat/events | test 插件请求只落 test API |
| 发布脚本 | package 输出目录/rsync 目标 | test 发布不会写 `/opt/chatsift/admin/dist` |

## 6. 对 v0.6.6 任务单的补充建议

应补入 Stop Gates:

- 发现 test 发布命令会写入 `/opt/chatsift/admin/dist`。
- 发现 test server 连接 prod DB。
- 发现 test/prod JWT_SECRET 相同。
- 发现 `test-admin` 的 `/api` 反代到 3100。
- 发现插件 test 环境请求落到 `admin.kongyuekeji.com`。

应补入验收标准:

- test/prod `metadata.json` 的 realpath 不同。
- test/prod 插件 zip 的 sha256 各自独立。
- 修改 test metadata 后,prod `/api/dashboard/plugin-update` 响应不变。
- test token 访问 prod API 失败;prod token 访问 test API 失败。
- test 插件 heartbeat/events 只命中 test server。
- `server-access.md` 给出独立 test 发布命令,不复用 prod rsync 目标。

## 7. 建议版本口径

当前 v0.6.6 任务单写“发 v0.6.6 到 test 验证隔离能力”,同时又写“不发布 prod、不打 prod tag,除非 Chase 后续明确要求”。

这会造成版本链不清。

建议 PM 明确二选一:

1. **test-only 环境修复**:不称为正式 v0.6.6 release,只作为 test 环境治理任务,不占正式 tag。
2. **正式 v0.6.6**:形成 release commit/tag,先 test 验收,再由 Chase 决定是否上 prod;即使不改 prod compose,也要写清 prod 是否受影响。

在口径确认前,不建议继续推进 v0.6.7 DOM 适配发版。

---

## 8. 结论

原报告抓住了最直接的静态产物耦合,但 v0.6.6 的真实目标应扩大为“test/prod 环境隔离最小闭环”。

最低完成标准不是“test compose 改挂载”本身,而是证明:

- test 发布不会写 prod 静态目录。
- test API 不会打到 prod 服务。
- test 数据不会进 prod DB。
- test 插件不会向 prod serverUrl 上报。
- test/prod 的版本、metadata、zip 和 token 均可独立验证。
