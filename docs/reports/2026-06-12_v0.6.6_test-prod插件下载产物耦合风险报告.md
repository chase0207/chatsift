## 1. 背景

v0.6.6 原计划发布「抖音私信客服接待模式消息采集适配」到 test 环境。发布前检查发现,插件下载产物可能被 prod/test 共享,存在 test 预发影响 prod 用户插件更新的风险。

经只读核实,该风险真实存在,需要独立版本先修复。

---

## 2. 关键证据

### 2.1 Compose 挂载耦合

`deploy/docker-compose.prod.yml`:

```yaml
server:
  volumes:
    - ../admin/dist:/app/public:ro
```

`deploy/docker-compose.test.yml`:

```yaml
server-test:
  volumes:
    - ../admin/dist:/app/public:ro
```

结论: prod 与 test 的 server 容器都从同一份 `admin/dist` 读取静态资源。

### 2.2 线上只读核实

SSH 只读核实结果:

```text
chatsift-server /app/public      <- /opt/chatsift/admin/dist
chatsift-server-test /app/public <- /opt/chatsift/admin/dist
```

结论: 线上 prod/test 实际确实共享同一磁盘目录。

### 2.3 插件下载元数据共享

插件更新接口从容器内静态目录读取:

```text
/app/public/plugin-downloads/metadata.json
/app/public/plugin-downloads/chatsift-plugin-v*.zip
```

线上核实:

```text
prod 3100 metadata version: 0.6.5
test 3101 metadata version: 0.6.5
```

由于二者读取同一份 `metadata.json`,如果 test 预发把 metadata 改成 `0.6.6`,prod 用户也会看到 `0.6.6` 更新提示。

---

## 3. 风险判断

该问题不是单个 metadata 文件的小问题,而是环境静态产物目录耦合:

- test 发布插件包会影响 prod 下载入口。
- test 更新 `metadata.json` 会影响 prod 自动更新提示。
- `admin/dist` 也被整体共享,理论上 test 后台静态资源也可能误覆盖 prod。
- v0.6.6 如果继续按普通 test 发版流程执行,会破坏「test 先验收、prod 后发布」的基本隔离。

风险级别: P0 发版阻塞。

---

## 4. 决策

不把该问题混入 DOM 采集适配。

版本顺序调整:

1. `v0.6.6`: 独立修复 test/prod 插件下载产物隔离。
2. `v0.6.7`: 原「抖音私信客服接待模式消息采集适配」顺延。
3. `v0.6.8`: 原暂定的「抖音-消息-消息接待」单独处理。

---

## 5. v0.6.6 修复目标

v0.6.6 只做环境隔离,不改业务采集逻辑。

目标状态:

```text
prod:
  /app/public -> /opt/chatsift/admin/dist
  plugin-downloads -> /opt/chatsift/admin/dist/plugin-downloads

test:
  /app/public -> /opt/chatsift-test/admin/dist
  plugin-downloads -> /opt/chatsift-test/admin/dist/plugin-downloads
```

验收要求:

- test `metadata.json` 可独立更新到 `0.6.6`。
- prod `metadata.json` 保持当前生产版本。
- test 下载 v0.6.6 插件不会改变 prod 默认下载版本。
- test/prod 页面均可正常访问。
- 不改 prod compose、不重启 prod server、不替换 prod 插件包。

## 8. 结论

这是一个真实的发版体系风险,不是插件包命名或单次操作问题。根因是 test/prod 共享静态产物目录,导致 test 预发无法做到对 prod 无影响。

必须先完成环境隔离,再恢复正常的插件 test 预发流程。
