# Codex PM 决策偏置复盘

> 版本: v1.0.0 / 2026-06-12  
> 类型: 协作复盘 / 长期思维偏差  
> 状态: 已确认根因,后续作为 Codex PM 决策约束参考  
> 触发事件:
> - v0.6.6 test/prod 插件下载产物耦合风险
> - v0.6.6 test/prod 环境耦合扩展风险
> - v0.6.7 抖音私信客服接待模式消息采集适配顺延

---

## 1. 问题概述

本报告不是单次 v0.6.6 事件复盘,而是对 Codex PM 长期决策偏置的复盘。

核心问题:

- Codex PM 习惯把问题收缩成当前版本的最小可执行补丁。
- 在地基类问题上,仍优先考虑“不扩大改动面”,而不是“长期机制是否正确”。
- 过度依赖任务边界、Stop Gate、人工提醒,没有优先要求机制隔离和自动阻断。
- 面对复杂项目时,倾向于先求当前闭环,没有充分站在系统演进和未来复用角度判断。

用户指出这不是“这一次保守”,而是 Codex PM 根深蒂固的思维方式。该判断成立。

---

## 2. 具体表现

### 2.1 系统性问题局部化

表现:

- 把环境发布模型缺陷简化为 `plugin-downloads` 目录问题。
- 把发版体系缺陷简化为 metadata 不要更新。
- 把多平台 DOM 架构问题倾向拆成单个 selector 修补。
- 把采集数据正确性问题倾向拆成当前 rejected/duplicated 的局部处理。

v0.6.6 中的具体例子:

- 插件下载目录共享;
- metadata 共享;
- test 发插件会影响 prod 插件下载。

后续 PM-工程治理补充后才扩展到:

- 发布脚本偏 prod 单通道;
- Nginx root / API proxy 需线上核实;
- DB / JWT / 数据卷需要实测;
- 插件 serverUrl / heartbeat / events 需纳入验收;
- test/prod 环境隔离矩阵需要完整闭环。

Codex PM 起初没有主动把问题升级到完整环境治理层面。

### 2.2 把“少改”误判为“安全”

Codex PM 多次把“减少当前改动面”误当成“降低风险”。  
这在普通业务 bug 中可能成立,但在以下问题上会造成反效果:

- test/prod 环境隔离;
- 发版脚本;
- metadata / 插件下载入口;
- 租户权限与采集权;
- 本地采集状态隔离;
- message position / message_id 数据契约;
- 多平台 DOM 适配架构。

这些问题的正确目标不是“少改”,而是“机制上长期正确”。

### 2.3 过度依赖 Stop Gate 和人工提醒

早期方案经常偏向:

- 不更新 metadata;
- 直链安装 v0.6.6;
- 在任务单里增加 Stop Gate;
- 提醒 CC4 不要碰 prod。

这些措施能降低单次误操作概率,但不能从机制上消除 test 误伤 prod 的可能。

正确方向应是:

- test/prod 发布目录物理隔离;
- 插件下载目录从 `admin/dist` 解耦;
- 发布脚本按环境显式选择;
- 脚本阻断 test 写 prod 路径;
- 验收矩阵证明 test/prod 独立。

### 2.4 未充分站在长期演进视角

v0.6.6 原本是 DOM 采集适配,发现环境耦合后,更客观的判断应是:

- 暂停 DOM 发布;
- 独立定义环境治理版本;
- 先重建 test/prod 发布隔离机制;
- 后续业务版本再恢复。

Codex PM 初期仍试图让当前版本“最小通过”,没有优先考虑后续所有插件/后台发布都会复用这套机制。

### 2.5 过度害怕任务混入,导致真实问题被切碎

任务边界很重要,但 Codex PM 有时把“不要混入”误用成“不要升级问题”。  
当问题本身跨越版本、环境、脚本、部署和业务验收时,继续强行切小会让根因失真。

正确做法应是:

- 业务任务暂停;
- 地基问题独立成更高优先级任务;
- 原任务顺延;
- 在任务单和状态源中明确依赖关系。

---

## 3. 原因分析

### 3.1 主要原因: 最小变更工程偏置

Codex 作为 coding agent,默认倾向:

- 最小改动;
- 避免扩大范围;
- 避免碰生产;
- 避免引入额外不确定性。

该偏置在普通业务 bug 中通常有效,但在基础设施问题上会导致错误收敛。

更准确地说,Codex PM 没有先判断“问题属于哪一层”,而是直接套用了普通代码修复的最小变更习惯。

### 3.2 次要原因: 将“提速”误读为“快速绕过”

用户希望加快推进,正确理解应是:

- 少走弯路;
- 一次把基础问题做对;
- 降低后续返工。

Codex PM 一度误读为:

- 不扩大 scope;
- 当前版本尽快过;
- 能绕过就先绕过。

这与用户真实目标不一致。

### 3.3 次要原因: 多版本并行导致过度切小

当 v0.6.4 / v0.6.5 / v0.6.6 / v0.6.7、W22、DOM 适配、环境治理并行时,Codex PM 过度担心任务混入,因此倾向把问题拆得过小。

但环境耦合问题本身就是跨版本、跨发布链路问题,过度切小会掩盖真实风险。

### 3.4 次要原因: 对“PM 职责”的理解不充分

Codex PM 不应只是把用户目标拆成最小任务,还应负责:

- 判断问题层级;
- 判断长期架构影响;
- 识别当前需求背后的基础设施缺陷;
- 防止短期版本通过但系统性风险保留;
- 主动提出充分方案,再讨论分阶段落地。

此前 Codex PM 更像执行协调者,没有始终承担足够的产品/架构判断责任。

### 3.5 非主要原因: 上下文过长

上下文过长会增加遗漏风险,但本次不是主要原因。  
Codex PM 已经看到了共享目录、metadata、脚本等证据,仍然先给了保守方案。问题不在信息缺失,而在判断策略。

### 3.6 非主要原因: 项目背景复杂

项目背景复杂确实提高判断难度,但用户和 PM-工程治理已提供足够线索。  
Codex PM 未及时升级问题等级,属于判断框架问题。

---

## 4. 影响

该偏差会带来以下风险:

- test 验收结果不可信;
- test 发布可能误伤 prod;
- 业务版本和环境治理混杂;
- 后续版本继续依赖人工提醒;
- 发版体系缺陷长期存在;
- 用户需要反复纠偏,降低协作效率与信任。

---

## 5. 纠偏规则

后续 Codex PM 在 chatsift 项目中必须采用以下判断顺序:

### 5.1 先判断问题性质

先判断问题属于哪一类:

- 普通业务 bug;
- 采集链路缺陷;
- 数据正确性问题;
- 租户 / 权限 / 账号归属问题;
- test/prod 环境隔离问题;
- 发版脚本 / 生产路径 / metadata 问题;
- 多平台扩展架构问题。

如果属于环境、发版、权限、租户、数据契约、生产安全,默认按基础设施问题处理。

### 5.2 先给长期正确方案

先给客观、长远、充分方案,再讨论是否分阶段。

禁止一开始就把方案压缩成最小 hotfix。

### 5.3 机制优先于提醒

优先级:

1. 机制上不可能误伤;
2. 脚本自动阻断误操作;
3. 自动验收矩阵;
4. 文档说明;
5. 人工提醒。

不能用 Stop Gate 和人工提醒替代机制隔离。

### 5.4 对 test/prod 边界使用高等级默认判断

凡涉及以下内容,默认升级为基础设施风险:

- `/opt/chatsift` / `/opt/chatsift-test`;
- `admin/dist`;
- `plugin-downloads`;
- `metadata.json`;
- release 脚本;
- rsync 目标;
- Nginx root / proxy_pass;
- DB_HOST / DB_NAME / 数据卷;
- JWT_SECRET;
- 插件 `serverUrl`;
- heartbeat/events 实际落点。

### 5.5 业务版本不得掩盖基础设施版本

如果业务发布过程中发现基础设施缺陷:

- 业务版本暂停;
- 基础设施问题独立版本处理;
- 业务版本顺延;
- 状态写入任务单和报告。

### 5.6 决策输出必须包含“充分方案”

后续遇到复杂问题时,Codex PM 的输出顺序必须是:

1. 问题定性:这是普通 bug、业务需求、数据契约、采集链路、权限隔离、发版体系,还是架构地基问题。
2. 长期正确方案:如果不考虑短期成本,系统应该如何设计才正确。
3. 风险与代价:长期方案会影响哪些模块、环境、角色和版本。
4. 分阶段方案:在不牺牲长期方向的前提下,如何拆阶段。
5. 当前版本建议:本版本做什么、不做什么、为什么。

禁止直接从第 5 步开始给“当前版本最小方案”。

### 5.7 识别地基问题的触发器

出现以下信号时,默认不是普通 hotfix:

- test 能影响 prod;
- 一个租户/账号/员工的本地态能影响另一个租户/账号/员工;
- 新平台/新场景需要复制粘贴 selector 而没有统一建模;
- 采集失败原因无法通过单条日志定位,需要跨 DOM/API/DB/本地态联动判断;
- 发布依赖人工记忆路径或手工 copy;
- 修复方案需要“提醒某人不要做某事”才能安全;
- 版本号、tag、metadata、PROJECT_STATUS 或 CHANGELOG 出现事实源不一致;
- 当前解决方案会在下一平台/下一版本复用时再次踩坑。

命中以上任一项,Codex PM 应主动升级为地基/治理问题评估。

---

## 6. 对当前事件的修正结论

v0.6.6 不应定义为“插件下载产物隔离小修”,而应定义为:

```text
v0.6.6 test/prod 发布体系与环境隔离治理
```

目标:

- test/prod 独立部署目录;
- 插件下载目录与 `admin/dist` 解耦或至少按环境独立;
- 发布脚本明确 test/prod 入口;
- Nginx / DB / JWT / serverUrl / metadata / zip 全部纳入验收矩阵;
- 后续业务版本可以复用可靠的 test 预发机制。

后续版本顺序:

1. `v0.6.6`: test/prod 发布体系与环境隔离治理。
2. `v0.6.7`: 抖音私信客服接待模式 DOM 适配。
3. `v0.6.8`: 抖音-消息-消息接待。

---

## 7. 后续约束

Codex PM 后续必须做到:

- 不默认保守收缩;
- 不以“少改”为最高目标;
- 不用文档提醒替代脚本机制;
- 不让业务版本夹带基础设施风险;
- 不把 test 误伤 prod 的问题当作单次操作失误;
- 优先给充分方案,再讨论拆分。
- 明确区分“短期绕过”“阶段落地”“长期正确方案”。
- 当用户要求速度时,默认理解为“减少返工、一次做对”,不是“缩小 scope 先过”。
- 如果 PM-工程治理或用户指出问题更大,先重新定性,不要继续维护旧的小范围方案。

若再次出现同类问题,应按本报告先自查判断框架,再输出方案。
