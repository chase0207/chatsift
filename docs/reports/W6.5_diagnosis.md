# W6.5 Diagnosis — 会话未合并

## 结论

同一个 `chase` 被拆成 3 条会话,不是 W6 页面问题,也不是服务端唯一键失效。根因在 W4 采集侧:当前 `legacy-collector` 没有使用 adapter `detectSessions()` 解析出的会话身份,而是每次从当前页面 DOM 重新读昵称/头像/URL 参数并 hash 成 `conversationId`。其中头像/标题读取不稳定,导致同一客户生成了 3 个不同的 `platform_conversation_id`。

## Dx Task 1-2: conversation_id 生成链路

### 当前实际链路

`plugin/runtime/legacy-collector.js`:

```js
function _readNickname(adapter) {
  var ctx = adapter && adapter.buildRuntimeContext ? adapter.buildRuntimeContext() : {}
  return ctx.sessionTitle ||
    Dom.getText(Dom.queryFirst([
      'div[class*="msgTitle"] span[class*="name"]',
      'div[class*="userInfo"] [class*="name"]',
      'div[class*="conversationName"]',
      '[class*="sessionTitle"]',
    ])) ||
    'unknown'
}

function _buildSessionInfo(adapter) {
  var nickname = _readNickname(adapter)
  var avatar = (Dom.queryFirst(['div[class*="userInfo"] img', 'div[class*="msgTitle"] img']) || {}).src || ''
  var pageKey = adapter && adapter.pageKey ? adapter.pageKey : 'douyin'
  var seed = [pageKey, nickname, avatar, _param('conGroupId'), _param('lifeAccountId'), _param('accountId')].join('|')
  return {
    conversationId: 'douyin_' + pageKey.replace(/[^a-z0-9]+/ig, '_') + '_' + Dom.simpleHash(seed),
    nickname: nickname,
    avatar: avatar || null,
    pageKey: pageKey,
  }
}

async function collectMessageSession(sessionInfo) {
  var adapter = Registry.resolve(location)
  var info = Object.assign(_buildSessionInfo(adapter), sessionInfo || {})
  var rawMessages = await adapter.getMessages(info)
  var events = (rawMessages || [])
    .map(function (m) { return adapter.toConversationEvent(m, info) })
}
```

`plugin/adapters/douyin/private-message.adapter.js`:

```js
function toConversationEvent(rawMsg, sessionInfo) {
  sessionInfo = sessionInfo || {}
  var conversationId = sessionInfo.conversationId || sessionInfo.conversation_id || sessionInfo.session_id || 'douyin-private-' + Dom.simpleHash(sessionInfo.nickname || location.href)
  return {
    platform: 'douyin',
    platform_page: 'private-message',
    conversation_id: conversationId,
    message_id: Dom.synthMessageId({
      conversationId: conversationId,
      direction: direction,
      text: content,
      occurredAt: occurredAt,
    }),
    sender_nickname: direction === 'inbound' ? (sessionInfo.nickname || '') : (sessionInfo.accountNickname || ''),
  }
}
```

`laike-message.adapter.js` 和 `feige.adapter.js` 同样优先使用 `sessionInfo.conversationId`, 只是 fallback 前缀分别是 `douyin-laike-` / `douyin-feige-`。

### 关键判断

- 实际入库的 ID 前缀是 `douyin_douyin_private_message_...`, 说明走的是 `legacy-collector._buildSessionInfo()`。
- adapter 自己的 `detectSessions()` / `_parseContact()` 虽然会读 `data-conversation-id` / `data-session-id` / `data-id`, 但 W4 当前 collector 没有调用它们来生成本次采集的 `conversation_id`。
- `SessionIdentityResolver` 里已有 `nickname+avatar` / stable attr 的能力,但这条 W4 collector 路径也没有用它。

## 完整度异常补充诊断

用户提到的完整预约信息:

```text

姓名：刘思奇
电话：13913972023
上车位置：普陀区镇坪路魔方公寓
车型：轿车
```

这条消息不是被分到了某一条独立会话,而是被重复采进了三条 chase 会话:

```text
conversation_id  platform_conversation_id                intent_label      completeness_score  message_id  occurred_at           content
11               douyin_douyin_private_message_8287ed80  price_inquiry     0                   21          2026-05-27 11:02:00  时间...姓名刘思奇...电话13913972023...
13               douyin_douyin_private_message_92be8f00  price_inquiry     0                   105         2026-05-27 11:02:00  时间...姓名刘思奇...电话13913972023...
14               douyin_douyin_private_message_23831768  simple_inquiry    0                   119         2026-05-27 11:02:00  时间...姓名刘思奇...电话13913972023...
```

### 它属于哪条会话

它同时存在于 11 / 13 / 14 三条拆分会话里。也就是说,会话拆分导致历史消息被重复归档,但这条预约信息没有单独落到一个“主体之外”的会话。

### 所在会话意图

- 会话 11: `price_inquiry`
- 会话 13: `price_inquiry`
- 会话 14: `simple_inquiry`

会话 11/13 被判成询价,主要因为 intent rule 里 `price_inquiry` 的优先级 20 高于 `appointment` 的 30,且关键词 `优惠` 会命中 price 规则。`报名优惠` 同时含 “报名” 和 “优惠” 时,先命中 `price_inquiry`。

### completeness 为什么是 0

`server/src/v1/analyzer.js` 每次分析只取该会话最新 5 条 inbound:

```js
WHERE tenant_id = ? AND conversation_id = ? AND direction = 'inbound' AND content_text IS NOT NULL
ORDER BY occurred_at DESC, id DESC
LIMIT ?
```

当前三条会话最新 5 条上下文分别是:

```text
conversation 11 context ids: 136,143,131,133,144
早上好2 | 早上好3 | 训练时间 | 报名优惠 | 早上好啊
intent: price_inquiry
completeness: city=null, hours=null, score=0

conversation 13 context ids: 113,114,115,103,117
亲爱的客服接待 | 中午好 | 明天上午吧 | 报名优惠 | 报名优惠
intent: price_inquiry
completeness: city=null, hours=null, score=0

conversation 14 context ids: 129,130,138,139,140
明天上午吧 | 早上好 | 早上好2 | 早上好3 | 早上好啊
intent: simple_inquiry
completeness: score=0
```

所以完整预约信息太早,已经不在当前最新 5 条上下文里,后续消息分析把 `completeness_score` 覆盖回 0。

### 多行结构化格式覆盖情况

直接用 completeness engine 测这条多行文本:

```text
appointment => score 60
fields: city=普陀, time=5月17号, contact=13913972023, project=null, store=null
missing: project, store

price_inquiry => score 50
fields: city=普陀, hours=null, project=null
missing: hours
```

结论:

- `电话:13913972023` 这种多行结构可被 `extractContact()` 覆盖。
- `时间:2026年5月17号晚六点` 被 `extractTime()` 部分覆盖为 `5月17号`。
- `上车位置:普陀区...` 会被 `extractCity()` 抽成 `普陀`。
- 当前规则没有抽取 `姓名` 字段,也没有把 `车型:轿车` 映射为 `project`。
- 因此如果意图是 `appointment` 且上下文包含这条消息,理论上完整度不是 0,而是 60。当前显示 0 的主因是上下文窗口和后续覆盖,其次是意图被 `优惠` 抢成 `price_inquiry`。

## 需要阶段二决策的问题

1. conversation_id 修复优先级:是否接受 `nickname + normalized avatar` 作为主键来源,头像缺失时是否退化到 `nickname`。
2. 历史三条 chase 是否合并,还是清空测试数据后重采。
3. completeness 是否要改成“按会话历史累计字段”而不是每次用最新 5 条覆盖。
4. intent rule 是否要处理 `报名优惠` 的优先级冲突。
