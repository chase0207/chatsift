## 3. W17 阶段一审查

### 3.1 P1: seen 早于队列持久化,崩溃可能造成永久漏传

位置:
- `plugin/runtime/event-collector.js`
- `plugin/runtime/event-queue.js`

问题:
- `collect()` 先写 `_seen.add(id)`,再触发 `Queue.enqueue(event)`。
- `enqueue()` 的持久化是异步触发,不保证 seen 与 queue 同步 durable。
- 如果浏览器在 seen 已记录但 queue 未持久化前崩溃,后续会跳过该消息,服务端也收不到。

建议:
- 将 seen 语义改为“已 durable enqueue 或已上传确认”。
- 最小修法: `Queue.enqueue()` 返回持久化 Promise,成功后再写 seen。
- 更稳方案: queue 内部维护 `pending/uploaded` 状态,collector 不单独维护不可回滚 seen。

### 3.2 P1: `uk_conv_position` 冲突会回滚整批并卡队列

位置:
- `server/src/controllers/v1/eventsController.js`
- `server/sql/v1-schema.sql`

问题:
- 服务端入库前只预查 `(tenant_id, platform_message_id)`。
- DB 同时有 `(tenant_id, conversation_id, position)` 唯一键。
- 若同一 position 出现不同 message_id,`INSERT messages` 抛 duplicate key,当前会 rollback 整批并返回 500。
- 上传器会把整批放回队首,可能长期阻塞后续事件。

建议:
- duplicate key 改为 per-event 处理。
- `uk_tenant_msg` 计 duplicated。
- `uk_conv_position` 计 duplicated 或 rejected,记录 reason。
- W17 来源应校验 `position != null`,避免唯一键因 NULL 失效。

### 3.3 P1: 分析上下文排序仍按 `occurred_at`

位置:
- `server/src/v1/analyzer.js`
- `server/src/controllers/v1/conversationsController.js`

问题:
- 展示接口已按 `segment_at, position, id` 排序。
- 分析器上下文仍按 `occurred_at` 排 inbound。
- inbound 缺精确时间、跨段同秒或单调校正时,分析上下文可能和页面真实顺序不一致。

建议:
- 分析上下文排序统一为 `segment_at, position, id`。
- 或补测试证明 inbound `occurred_at` 与 W17 顺序永远等价。

### 3.4 P2: `segment_at=NULL` 的 outbound-only 段排序不稳定

位置:
- `plugin/adapters/douyin/private-message.adapter.js`
- `server/src/controllers/v1/conversationsController.js`

问题:
- 整段无 inbound 时保留 `segment_at=NULL`。
- MySQL `ORDER BY segment_at ASC` 会把 NULL 段排到所有有段时间消息之前。
- position 只能在 NULL 段内部兜底,不能决定 NULL 段相对其他段的位置。

建议:
- 不上传缺排序段的消息。
- 或服务端生成明确 `sort_segment_at`。
- 补 outbound-only 段排序回归测试。

## 4. W19 审查

### 4.1 P1: `service_accounts` 唯一键包含可变昵称

位置:
- `server/sql/02_w19_tenant_asset.sql`
- `server/src/controllers/v1/eventsController.js`

问题:
- 当前唯一键包含 `account_nickname`。
- 同一 `account_biz_id` 的昵称变化或空/非空变化,可能拆成多个 `service_account_id`。
- 影响客服账号筛选、自动绑定和消息归属一致性。

建议:
- 唯一键改为稳定身份维度,例如 `(tenant_id, platform_id, page_id, account_biz_id)`。
- `account_nickname` 只作为展示字段更新。
- 如需历史,另建 nickname history。

判断:
- 这是 schema/data contract 变更,C 类。应并入 W20 schema diff 或单独方案,不要直接改。

### 4.2 P2: `/auth/userinfo` 返回字段低于登录契约

位置:
- `server/src/controllers/authController.js`
- `admin/src/main.js`
- `admin/src/stores/user.js`

问题:
- 登录返回含 `tenant_id/user_type`。
- `/auth/userinfo` 只返回角色权限字段。
- 前端启动时 `refreshUserInfo()` 会覆盖 localStorage,导致前端拿到不完整身份。

建议:
- `/auth/userinfo` 与 `login.userInfo` 对齐,至少补 `tenant_id/user_type/status/expire_at`。
- `/auth/verify` 建议同口径。

## 5. 插件与只读边界审查

### 5.1 C 类待拍板: adapter contract 仍保留主动切会话

位置:
- `plugin/adapters/douyin/private-message.adapter.js`
- `plugin/adapters/douyin/laike-message.adapter.js`
- `plugin/adapters/douyin/feige.adapter.js`

问题:
- `switchSession()` 调用 `Dom.simulateClick(session.dom_ref)`。
- 这属于主动操作页面,触碰 chatsift 当前“只读诊断”边界。
- 当前 live collector 主要采当前会话,但该能力已打进 `content.js`,contract 仍保留切会话语义。

建议:
- 方案 A: W20 前禁用/删除 `switchSession/selectTriggerSession/simulateClick` 暴露。
- 方案 B: 作为主动页面操作能力重新按 C 类过方案和验收。

推荐:
- 当前主线是抖音私信准确性和稳定性,建议先禁用主动切会话能力,保留只读采集。

### 5.2 C 类待拍板: manifest 权限过宽

位置:
- `plugin/manifest.json`

问题:
- 当前权限包含 `tabs/scripting/activeTab/alarms`。
- host permissions 覆盖 `http://*/*`、`https://*/*`。
- content script 匹配全网,并启用 `all_frames`、`match_about_blank`。

影响:
- 插件注入所有站点和 frame,扩大隐私、误采、误触发面。

建议:
- 收窄到抖音相关域名和后台 API 域名。
- 移除未使用权限。
- `all_frames/match_about_blank` 需要真实证据再保留。

### 5.3 P2: feature flag 持久化与注释相反

位置:
- `plugin/runtime/feature-flags.js`

问题:
- 注释说禁止通过 `chrome.storage.local` 持久化解锁 flag。
- 代码实际会读取 storage 并监听变更。

建议:
- 危险 flag 只允许服务端白名单或 DevTools session-only。
- 不从 `chrome.storage.local` 恢复危险 flag。

## 8. W20 开工建议

### 8.1 Gate 顺序

1. 先完成状态源清理: `PROJECT_STATUS.md` + ops 文档当前事实一致。
2. 拍板插件只读边界: 禁用主动切会话,还是按 C 类纳入方案。
3. 拍板 manifest 权限收缩策略: 立即收窄到抖音域名,还是保留到多平台扩展时统一处理。
4. 将 W17/W19 的 C 类 schema 风险并入 W20 schema diff:
   - `service_accounts` 稳定唯一键。
   - W20 的 `collector_id`、`service_account_view`、采集权/查看权字段。
5. 开 W20 Stage A: schema diff + migration 草案 + 回滚策略。
6. 进入 W20 Stage B/C/D 实现。

### 8.2 推荐立刻处理

P0/P1:
- `PROJECT_STATUS.md` 状态冲突。
- `switchSession()/simulateClick()` 只读边界。
- manifest 全网注入权限。
- W17 queue seen 持久化时序。
- events duplicate key per-event 处理。

P2:
- `/auth/userinfo` 契约补齐。
- `pages` 路由权限。
- 知识库死链。
- plugin build 缺失 adapter 清单。

### 8.3 W20 是否可以继续

可以继续做 W20 schema diff 和任务拆分,但不建议直接写 W20 业务代码。原因:
- 当前仍有只读边界和插件注入范围未定。
- W20 的采集权模型会依赖 `service_accounts` 稳定唯一键,而 W19 当前唯一键仍有昵称可变风险。
- 状态文档冲突会导致执行 agent 误判生产/阶段状态。
