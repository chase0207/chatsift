## 1. 等价性确认:排序 == 去重 == 同一个 P
代码实证两者同源,都要"消息在对话内的稳定位置标识 P":
- **去重**完全靠 `messages.platform_message_id` 唯一键(`eventsController.js` 先 `SELECT ... WHERE platform_message_id` 查重,存在即 `duplicated++` 跳过)。→ **P = platform_message_id**。
- **排序**完全靠 `occurred_at`(messages 查询 `ORDER BY occurred_at, id`)。→ **P 若自带顺序即可替代 occurred_at 排序**。
- 故 P 须同时满足:**(a) 幂等**(同消息跨采集算出相同 P)、**(b) 可区分同内容**(2 个"在吗"得不同 P)、**(c) 可排序**(跨采集稳定全序)。

## 2. 现状机制(我核实的代码事实)
- **P 现状 = `syn_ + simpleHash(会话id | 方向 | 内容 | "seq:"+seq)`**。核实 `synthMessageId`(dom-utils):有 seq 用 `seq:N`,无 seq 回退"时间到分钟"(旧口径,已否定)。
- **`seq` = 单次采集 pass 内,同(会话+方向+内容)的出现序号**(legacy-collector 的 `_seqMap`)。
- **★ 关键:P 仍含内容(text)**。seq 是"同内容的出现计数",**不是纯位置**——这正是任务要摆脱的。
- **occurred_at**:inbound 读每条**隐藏精确时间**(class 含 `invisible`+`whitespace-nowrap`+`absolute`,正则到**秒**,`time_source=precise-invisible`);读不到时(outbound 客服 / 部分 inbound)→ **继承上一条 +1s**(`inherited`/`estimated`,我 W12.6+U9 做的)→ 分隔条锚点 → 采集当刻。**outbound 的 occurred_at 是合成的(+1s),非真实**——这是 Y 想消除的"假时间入库"。
- **DOM 逐条消息行无任何稳定 id**:核实 adapter `_scanLifeMessages` 对每个 `div.my-4` 只读 文本(px-3 py-2)、时间(invisible/text-xs)、方向(`_isOutbound` 启发式)、rect、客服名;`raw_payload` 仅记 selector/rect/time_*。**未读任何 `data-*` / `id` / `key`**。`data-conversation-id` 只在**会话列表项**级读到(`:117`),非消息级。

## 3. 现状 P 对 a/b/c(含 W16 探针修正)
- **(a) 幂等 — 不稳,但风险被高估**。seq 依赖"当前 DOM 窗口内同内容相对序"。
  - **★ W16 探针实测(我让 Chase 跑 probeDiff):抖音私信累积加载、不卸载,卸载率 0%**——向上滚只在顶部追加历史,已采节点不删。→ 同内容消息倾向**同屏共存**,seq 实际比"虚拟滚动窗口增删→seq 偏移"假设的**稳**。
  - 残留风险只剩:**向上滚把含同内容的历史追加到前面**时,后面同内容消息的 seq +1 → 新 id → 重复入库(W16 实测**未触发**,因重复内容少且未跨加载边界)。
- **(b) 可区分 — 部分,不卸载下较好**。同 pass 内 2 条"在吗"得 seq 0/1 → 不同 id ✓;但若两条从不在同一 DOM 窗口共存(一条滚出、另一条才载),各 pass 都 seq 0 → 同 id → 第二条被误判 `duplicated` 丢弃,违反"有几条存几条"。**不卸载使共存概率高,(b) 现实较好;仍在"追加历史边界"处可能误删**。
- **(c) 可排序 — 不可靠**。seq 不参与排序;排序靠 occurred_at,而 outbound 的 occurred_at 是 +1s 合成、精度到秒还可能并列 → 合成段 / 同秒顺序不可靠。

**小结**:现状把幂等与可区分耦合进"内容 + 窗口内序号",虚拟列表边界处既可能重复又可能丢失,排序依赖被合成的时间。W16 探针表明现实风险低于理论,但机制本身仍不满足"靠位置不靠内容"的硬原则。

## 4. 锚点窗口对齐评估(核心)
**思路**:弃"pass 内出现序",给每条消息**会话内全局位置序号 gIdx**。持久化每会话已采序列(或尾部 3–5 条 `direction+text` 作锚点 + 高水位 gIdx);每 pass 在当前 DOM 有序消息中定位锚点窗口(连续子序列),其后为新消息、gIdx 续编;`P = f(会话, gIdx)`,**纯位置、与内容无关**。

- **(a) 幂等 ✓**:锚点命中则其及之前不重编、只向后编;无新消息 → 锚点落末尾 → 零新增。
- **(b) 可区分 ✓**:两条"在吗"位置不同 → gIdx 不同 → 不同 P,**靠位置不靠内容**,满足硬原则。
- **(c) 可排序 ✓**:gIdx 本身即会话内全序,server 直接按它排,**不再依赖 occurred_at**(相对 X 的最大收益)。

逻辑上 a/b/c 成立,但有**硬失败模式 + 根本边界**:

- **F1 无重叠 / 冷启动**:两 pass 的 DOM 窗口无共同消息(跳顶看长历史、刷新只载最新 20、久未采)→ 锚点定位失败。降级:持久化**全量已采序列**(纯文本,量小可行)对齐任意重叠窗口。但**真存在"未观测间隙"**(两段之间的消息从未被任何 pass 看到)时,新段的绝对 gIdx 不可知(第 50 还是第 80 位无法判定)。→ **根本边界:位置只在"连续观测区段"内良定义,跨观测间隙的绝对位置不可恢复。**
  - **★ W16 探针修正**:不卸载 + 向上滚追加历史,意味着**只要持续采集,观测区段会向上连续扩展**(历史被逐步看到),间隙风险低于一般虚拟列表;但"久未采 + 用户已手动滚过大段未采历史"仍会留间隙。
- **F2 锚点歧义**:短锚点子序列(连续多条"在吗")可能多处匹配。缓解:窗口 3–5、含 direction 模式、取最末/最长唯一匹配;仍多处则加宽或降级。
- **F3 撤回 / 删除 / 编辑**:抖音可撤回,已采锚点在 DOM 消失 → 子序列错位。缓解:允许 K 处容错失配或重锚。
- **F4 滚动中半渲染**:快滚捕获残缺/乱序窗口。缓解:已有 MutationObserver+debounce,列表稳定后才提交;低置信匹配跳过。
- **★ F5 跨客户端不确定(致命)**:若 gIdx 是**客户端私有自增计数器**,多标签/多设备/换机对同一条算出不同 gIdx → server 出现重复。**真正的幂等(a) 要求 P 是"任何观测者对同一 DOM 都算出相同值"的纯函数**,客户端私有历史计数器不满足。→ 要么 server 另立依据归并(退回识别问题),要么 **P 必须由 DOM 可观测内容确定性导出**,而非客户端历史。

## 5. 决定 Y/X 的唯一经验事实(代码读不出,必须真机)
F5 把问题逼到两个**DOM 经验事实**,只能真机抓 DOM 验(`tools/dom-collector/dom-snapshots/` **我核实为空**,codex 放回的 tools/dom-collector 只有插件代码、无快照,无样本):
- **Q1**:抖音私信**逐条消息行**是否带任一**稳定且观测者一致**的 token(隐藏 id / data-index / React key / 其它 data-*)?代码现在一个都没读,但"**没读 ≠ DOM 没有**"。→ **若有:P = 该 token,a/b/c 立即满足,无需锚点窗口,Y 直接成立。**
- **Q2**:隐藏精确时间(到秒)是否对 **outbound 客服消息**也稳定存在?代码+W12.6 现状是"outbound 常无"。→ **若 outbound 也有:P = f(会话, 精确时间, 方向) 是纯 DOM 函数,a/c 皆真,仅同秒同内容连发碰撞(pass 内序兜底),Y 基本成立。**

## 6. 结论(条件式,诚实)
| 前提 | 方案 | 说明 |
|---|---|---|
| **Q1 成立**(逐条稳定 token) | **Y(token版,最优)** | P = DOM token,outbound `occurred_at` 存 **NULL**,排序按 token/位置,库里**不存合成时间** |
| Q1 否、**Q2 成立**(outbound 也有到秒精确时间) | **Y(时间版)** | P 与排序用真实精确时间,occurred_at 全真;同秒同内容连发用 pass 内序兜底 |
| **Q1/Q2 皆否** | **退 X** | 锚点窗口只在"单端连续观测区段"做出 a/b/c 的 P,受 F5(跨端)+F1(间隙)根本限制。occurred_at 借时间**仅供排序**(承认 outbound +1s 为合成、非真实,不对外当真实);去重用"单端位置 gIdx + 现唯一键"。**不宣称"已造出全局稳定 P"** |

**我的判断(增量)**:即便 Q1/Q2 皆否,W16 探针(不卸载)使单端锚点窗口的**现实可靠性高于一般虚拟列表**(观测区段连续扩展、间隙少)。但 **F5 跨端仍是硬伤**——除非业务能接受"**一个租户的采集只来自单一客户端/单标签**"这个前提,否则跨端去重不可靠,**X 更诚实**。这个"单端前提"是否成立(员工会不会多标签/多设备同时采同一会话),是定 X 可用性的产品问题,请一并定。
