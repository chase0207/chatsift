## 0. 一句话结论

后台**没有一以贯之的主体维度**:五个页面各按不同主体组织(控制台=系统/设备、会话中心=会话、工单中心=工单、线索中心=客户、运营分析=平台页面),且 ① **控制台整个是 chat_rpa 自动回复时代的残留视角**(与 chatsift 业务无关);② 会话中心**平台维度与客户维度同屏混排、无明确主体**;③ **跨页下钻多处断裂**(会话→线索不可点、会话→工单跳到列表丢 id);④ **platform_page 一个字段三种显示**(抖音私信 / private-message / "页面"标签);⑤ lead 模型 C 的"客户作用域"在 UI **零表达**。Chase 感觉的"平台视角和用户视角混乱",属实且有具体出处。

## 一、五页维度速览(主体 / 字段 / 筛选 / 视角)

| 页面 | 文件 | 主体维度 | 列表/卡片字段 | 筛选维度 | 承载的"视角" |
|---|---|---|---|---|---|
| 控制台 | `Dashboard.vue` | **系统/设备**(chat_rpa 残留) | 用户总数、授权插件、今日消息、在线设备 + 运行质量(成功率/AI调用/关键词命中/转人工/响应时长/错误) | 日期 + 平台 | 机器人运营平台视角(过时) |
| 会话中心 | `Conversations.vue` | **会话** | 客户昵称、平台、平台页面、意图、阶段、完整度、诊断、消息数、最后消息时间 | 平台 / 页面 / 意图 / 阶段 / 诊断 / 昵称 / 消息 | 平台 + 客户 + 分析 三视角混合 |
| 工单中心 | `Workorders.vue` | **工单** | 标题、类型、优先级、完整度、状态、SLA、创建时间 | 类型 / 状态 / 优先级 / 超时 | 纯工单属性视角(无主体锚) |
| 线索中心 | `Leads.vue` | **客户/线索** | 客户、意向、评分、意图、城市、电话、状态、诊断、最近跟进 | 状态 / 意向 / 城市 / 诊断 / 关键词 | 纯客户视角(无平台) |
| 运营分析 | `Analytics.vue` | **平台页面 + 时间** | 漏斗(咨询/留资/预约)、意图分布、意向度分布、平台页面对比、趋势 | 日期 / 平台页面 | 平台聚合视角 |

## 二、逐页诊断(Q1 主维度 + Q2 同页多视角混淆)

### 控制台 Dashboard

- **Q1 主维度**:系统/设备运营,**不是 chatsift 业务主体**。四张统计卡 = 用户总数/授权插件/今日消息/在线设备(`Dashboard.vue:139-144`);运行质量监控 = 总处理/成功率/AI调用/关键词命中/转人工/平均响应时长/错误(`:71-122` `:186-195`)。
- **Q2 混淆**:★ 整页是 **chat_rpa 自动回复时代残留**——"关键词命中""转人工""平均响应时长"是回复机器人的指标,**chatsift 只读分拣根本没有转人工/关键词回复**。chatsift 真正的业务主体(会话数、待处理工单、高意向线索、留资/预约)**控制台零体现**。"今日消息"是唯一沾边的,却混在设备/插件统计里。"用户总数"指**系统登录账号**,不是客户(见 Q4 概念撞名)。

### 会话中心 Conversations

- **Q1 主维度**:会话(每行一个 conversation)。列见速览表。筛选 7 项(`:166-174`)。
- **Q2 混淆**:★
  - **视觉主体与数据主体不一致**:行数据主体是"会话",但列表把"客户昵称"加粗当主标识(`:71` font-weight:600),平台/平台页面又各占一列——同屏并排 客户 + 平台 + 平台页面,**没有任何视觉层级说明"谁是这一行的主体"**。
  - **筛选混三类维度**:平台维度(platform / platform_page)+ 客户维度(nickname)+ 分析维度(intent / stage / diagnosis)平铺在一排,无分组。
  - **缺客服账号维度**:虽然 `71faba4` 已采客服账号名,但会话中心列表/筛选都不含客服账号。

### 工单中心 Workorders

- **Q1 主维度**:工单。列只有工单自身属性(标题/类型/优先级/完整度/状态/SLA),筛选也全是工单属性(`:149-154`)。
- **Q2 混淆**:★ **列表完全没有主体锚点**——看不到客户昵称、平台、平台页面、客服。工单"标题"是引擎生成的类型化标题(如"预约工单"),**从列表无法知道"这是谁的工单"**。唯一的主体关联藏在详情弹窗的"关联会话 #id"(`:90-99`),要点开才看到。

### 线索中心 Leads

- **Q1 主维度**:客户/线索(模型 C 一会话一线索≈一客户)。"客户"列加粗(`:45` `:267`)。筛选 5 项(`:149-156`)。
- **Q2 混淆**:
  - **纯客户视角,平台维度整段缺失**——列表/筛选都没有平台、平台页面、客服。同一个"客户"在会话中心带着"抖音/抖音私信"标签,进了线索中心这些维度全消失。
  - 状态列是可直接改的下拉(`:79`),与其它纯展示列混在一起,主体(客户)和操作(改状态)同列。

### 运营分析 Analytics

- **Q1 主维度**:平台页面 + 时间。纯聚合,无单个主体。漏斗/意图/意向/页面对比/趋势(`:29-132`)。筛选 = 日期 + 平台页面(`:17-21`)。
- **Q2 混淆**:本页**维度最清晰**(平台页面 + 时间 + 业务环节,无主体混排)。唯一问题是命名(见 Q4):平台页面下拉用的是**原始值 private-message**,而会话中心同一筛选用的是**中文"抖音私信"**。

## 三、Q3 跨页视角是否一致 / 主体对得上吗

**主维度本就五页五样**(系统/会话/工单/客户/平台页面),跨页时主体频繁切换。更实的问题是**下钻链路多处断裂**:

| 从 | 到 | 实现 | 通不通 |
|---|---|---|---|
| 会话列表 | 会话详情 | `router.push('/conversations/'+id)` (`Conversations.vue:292`) | 通 |
| 会话列表 | 消息记录 | MessageDrawer(会话 id) | 通 |
| 会话详情 | 线索 | 线索ID **纯文本不可点**(`ConversationDetail.vue:26`) | ✗ 断:看到 lead_id 点不进去 |
| 会话详情 | 工单 | `router.push('/workorders')` **不带 id**(`:35`) | ✗ 断:跳到工单列表首页,找不到那个工单(工单中心也不支持按 id 筛) |
| 工单弹窗 | 关联会话 | `router.push('/conversations/'+id)` (`Workorders.vue:266`) | 通 |
| 线索列表 | 线索详情 / 消息 | `/leads/:id` / MessageDrawer(primary_conversation_id) | 通 |
| 线索详情 | 关联会话 | 可点 `#id`(`LeadDetail.vue:98`) | 通 |
| 线索详情 | 关联工单 | 表格**纯展示不可点**(`:110-126`) | 半:看得到点不进 |
| 顶栏铃铛 | 线索 | `/leads?ids=...` | 通 |

**结论**:可靠下钻只有"线索→会话""工单→会话"(都汇到会话)。**反向(会话→线索/工单)断裂**:会话详情虽列了 lead_id/工单,但线索不可点、工单跳错(到列表丢 id)。用户从会话很难走到对应线索/工单,主体在这里"对不上"。

> 主体语义切换的例子(Q3 原问):在会话中心看的是"某页面的某会话",点"看记录"是会话消息;但同一行没有入口到"这个客户的线索";要到线索中心重新搜昵称才找得到——中间"会话↔客户"的对应关系 UI 没有打通(只有线索详情单向能回看会话)。

## 四、Q4 "平台/平台页面/客服账号/客户"的命名与概念混淆

### platform_page(同一字段,三种显示)
| 位置 | 显示 | 出处 |
|---|---|---|
| 会话中心 筛选标签 | "页面" | `Conversations.vue:10` |
| 会话中心 列 / 值 | "平台页面" / **"抖音私信"**(映射 page_name) | `:79-83` `:267-270` |
| 会话详情 | **"private-message"**(原始值,未映射) | `ConversationDetail.vue:19` |
| 运营分析 | 筛选标签"平台页面" / 值 **"private-message"**(原始) | `Analytics.vue:17` `:100` |

同一个 `platform_page`,列表显示中文"抖音私信"、详情和分析显示英文 code、筛选标签时而"页面"时而"平台页面"。★ 命名不统一。

### 客户(一个概念,五种叫法)
客户昵称(会话列表)/ 客户(线索列表)/ 抖音昵称(线索详情 `LeadDetail.vue:23`)/ 真实姓名(线索)/ 客户ID(会话详情 = customer_platform_uid `ConversationDetail.vue:20`)。同一主体在不同页叫法分散。

### "用户" vs "客户"(概念撞名)★
- 控制台"用户总数"(`Dashboard.vue:140`)= **系统登录账号**(后台用户)。
- 业务里"客户"= 抖音对话对象。
- 两者都可能被读成"用户",一个是平台账号、一个是对话客户,**最容易混的概念撞名**。

### 客服账号(几乎不可见)
所属客服账号已采(`71faba4`),但四个业务页**列表/筛选都不展示**;只在会话详情消息流里 outbound 气泡显示 `sender_nickname`(回退"客服",`ConversationDetail.vue:120`)。作为一个维度,UI 上基本缺席。

### 客户ID
会话详情"客户ID" = `customer_platform_uid`,但采集侧未稳定写入(同 dom-collector 调研:稳定 accountId 在 URL、当前未采),实际多为空显示"-"。

## 五、Q5 lead 模型 C(单页面按客户聚合)在 UI 的暴露

- **模型事实**:lead 一会话一线索(`primary_conversation_id`),按"平台页面内的客户(nickname)"聚合;模型 B(跨平台合并)仅 DB 预留。
- **UI 表现**:线索中心/线索详情把客户呈现为一个**孤立的昵称/姓名**,**完全不显示它的"作用域"**——既不显示属于哪个平台页面,也不显示是否可能跨平台。线索详情连"平台/平台页面"都没有(只有写死的"抖音昵称"标签 `LeadDetail.vue:23` 暗示抖音)。
- **导致的困惑**(正是 Q5 担心的):用户会把"客户"当成**全局唯一的一个人**,但它实际是"**某平台页面下、某昵称**"聚合出来的;同名不同人会被合并(conversation_id 用 nickname),UI 无任何提示。客户到底是"一个页面下的"还是"跨平台的一个人",界面**没有表达**。
- 关联会话块也只有会话ID/客户/阶段/完整度,**不带平台页面**(`:96-103`),进一步让"这个客户在哪个页面"无处可见。

## 六、关键发现汇总(按严重度)

1. ★★★ **控制台是 chat_rpa 残留视角**:统计卡(用户/插件/设备)+ 运行质量(AI/关键词/转人工/响应时长)全是自动回复机器人指标,与 chatsift 只读分拣业务脱节;chatsift 真正概览(会话/线索/工单/漏斗)零体现。
2. ★★★ **五页主体五样、无统一视角**:系统/会话/工单/客户/平台页面;尤其工单中心无主体锚、线索中心无平台维度。
3. ★★ **跨页下钻断裂**:会话→线索(不可点)、会话→工单(跳列表丢 id);可靠下钻只有"→会话"单向。
4. ★★ **platform_page 一字段三显示** + 客户五种叫法 + "用户/客户"概念撞名。
5. ★★ **模型 C 的客户作用域 UI 零表达**:客户像全局唯一的人,实为"页面+昵称"聚合,同名合并无提示。
6. ★ **客服账号维度基本缺席**:已采但四个业务页不展示。

## 七、给"视角梳理"方案的输入(待 Chase 拍板,我不改 UI)

需要 Chase 先定的主体观:
1. **后台到底以谁为中心组织?**(候选:以"客户"为中心,会话/线索/工单都挂客户下;还是保持会话/工单/线索三个并列中心)。这决定要不要把"客户"提升为贯穿主维度。
2. **平台/平台页面/客服账号**这三个维度,是作为**筛选维度**统一进每页,还是只在分析页出现?
3. **控制台**是否整页重做成 chatsift 业务概览(今日新会话/待处理工单/高意向线索/留资预约漏斗),砍掉 chat_rpa 残留(用户/插件/设备/转人工/关键词)?
4. **命名统一**:platform_page、客户、客服账号、用户(系统账号)各定一个标准展示名。
5. **模型 C 的作用域**要不要在 UI 显式标注(如客户卡片显示"抖音私信 · 昵称",并提示"同名可能合并")?

> 本报告只诊断、不改 UI。回报后停下,等据此出"视角梳理"产品方案。
