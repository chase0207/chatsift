## 3. 测试反馈与处理

### 问题1:角色管理「数据范围」是平台级还是租户级?(已分析,记 W22)
- **结论:系统里有两套互不相干的"范围"机制**。
  - 业务数据(会话/线索/工单/分析/首页)只认 **W19 `scope()`**([server/src/controllers/v1/_shared.js:23-63](../../server/src/controllers/v1/_shared.js#L23-L63)),判据 `user_type+role_code+tenant_id`,**完全不读 `roles.data_scope`**。
  - 角色编辑的「数据范围」= `roles.data_scope`,只经 **`applyDataScope()`**([server/src/utils/data-scope.js](../../server/src/utils/data-scope.js))作用于 `/api/plugins` + `/api/logs` + 插件配置(owner=user_id)。`all`=不加任何过滤,`self`=`AND user_id=本人`。
- **回答**:① 租户用户选"全部数据"对业务数据无影响(恒本租户);对 plugins/logs 是**平台级(跨租户全表)**——这两个查询除 `applyDataScope` 外**无 tenant 兜底**。② 平台用户(internal)业务数据默认 `1=0`,带 `?tenant_id` 才看那一个租户。
- **隐患(记 W22)**:租户管理员若 data_scope='all' 且能调到 plugins/logs,会跨租户看到别租户数据(UI 菜单未给入口,接口层缺兜底)。"数据范围"UI 挂在角色编辑里但对业务数据无效,有误导。

### 问题2:租户管理员添加员工提示「无权限」(已解决/正常)
- 机制:创建用户走 [`perm('user:create')`](../../server/src/routes/users.js#L14),非超管需角色在 `role_has_permissions` 有该权限。复测正常。

### 问题3:插件授权是 user 级非租户级?(已确认 = chat_rpa 遗留,记 W22)
- `plugins` 表([server/sql/00_reused_tables.sql:80-89](../../server/sql/00_reused_tables.sql#L80-L89))`user_id NOT NULL` **无 tenant_id** → 用户级。下拉跨租户列人是因 internal/超管在 [userController.list](../../server/src/controllers/userController.js#L16) 不加租户过滤。
- **关键**:`plugin_key`/`plugins` **不参与 chatsift 现采集链路**(采集走 JWT + service_account + W20 collect-permission;`server/src/controllers/v1/` 不引用 plugin_key)。是 chat_rpa 遗留面。W22 方向:退役该页或补租户感知。

### 问题4:关闭自动采集仍采集 → 修正为「auto_switch 关了但红点消失」(已定性=抖音原生)
- 面板两个独立开关:**启动/停止按钮**=`collector_v1_enabled`(基础采集);**「自动切换会话」开关**=`auto_switch_session`(W21 主动切换)。关后者不影响前者。
- **红点消失**:经代码穷举,auto_switch 关闭时插件唯一会点击会话的 `switchSession` 被 flag 硬闸([adapter:152-155](../../plugin/adapters/douyin/private-message.adapter.js#L152-L155)),`detectSessions` 只读,无任何 markRead API。**Chase 自查定位:红点消失的会话在另一浏览器页打开 → 抖音服务端跨标签页已读同步**。**非插件,红线 intact**。
- **W22 UX 文案建议**(Chase 给):① 启动/停止 → "开始采集/停止采集";② "自动切换会话" → "自动切换红点会话";③ 描述 → "人工无操作 1 分钟后,开始自动切换红点会话"。

- 见第 4 节。

## 4. 反馈1 时区 bug 根因与修复(已闭环,供对照)

- **现象**:会话列表"最近时间"显示比真实早 ~8h(如真实 13:09 显示"8小时前")。
- **根因链**:
  1. server 容器跑 **UTC**(`TZ` env 空)。
  2. 入库走 [`toMysqlDate`](../../server/src/controllers/v1/_shared.js#L91-L97),用 **Node 本地时区**的 `getHours()` 拼裸串入 DATETIME;插件发的是 `occurred.iso`(`toISOString()`=UTC 绝对时刻)→ 容器 UTC 时存成 **UTC 墙钟**。
  3. 前端 [`relativeTime`](../../admin/src/views/Aggregate.vue#L191-L201) `new Date("...T...")` 按**浏览器本地(CST)**解析裸串 → 比真实早 8h。
  4. `occurred_at`/`last_message_at` 均为 **DATETIME**(MySQL 不做时区转换),DATE_FORMAT 返回裸串。
- **修复(v0.6.3)**:server 容器加 `TZ=Asia/Shanghai`。Node 自带 ICU 时区数据(容器无 OS tzdata 也认 `TZ` env),`toMysqlDate` 改按 CST 拼串。**实证**:容器内 `new Date('2026-06-10T13:10:00Z')` 的 `getHours()`=21 → 入库 `2026-06-10 21:10:00`(CST)。
- **旧数据**:发版前 UTC 墙钟行 +8h 原地修正(第 2 节)。
- **codex 复核点**:`db.js` 有 `timezone:'+08:00'` + `SET time_zone='+08:00'`,但入库用的是 `toMysqlDate` 拼**字符串**(非 Date 参数),故 driver 的 timezone 选项不介入,容器 TZ 才是决定因素。此判断是否成立?

## 5. ★当前未决:prod 采集失效 — 根因分析(codex 重点审查)

### 5.1 现象
开启采集后,prod `messages` 计数停在 **67 不增**;插件能采到新消息但入不了库。

### 5.2 插件 console 实证(账号 空月01 = employee 4 = 该账号 collector)
```
图1: [LegacyCollector] collectMessageSession {messages:17, collected:2, skipped:15}
     [EventUploader]   uploaded {accepted:0, duplicated:2, rejected:0, reject_reasons:[]}
图2(收到新消息"666"):
     [LegacyCollector] collectMessageSession {messages:18, collected:1, skipped:17}
     [EventUploader]   uploaded {accepted:0, duplicated:1, rejected:0, reject_reasons:[]}
```
→ 插件**采到新消息**(collected:1),上传后 server 判 **duplicated(已存在)→ accepted:0 不入库**;`rejected:0`(非采集权)。

### 5.3 server 侧排查(均健康,排除以下)
| 排查 | 证据 | 结论 |
|---|---|---|
| 采集权(W20) | SA `1858797317227848`:lifecycle=active,collector_id=**4**;心跳 employee=4 | 本人即 collector,闸门会**接受**,非 reject |
| 实例冲突 block | 用 `SET time_zone='+08:00'` 复算仲裁:实例885 age=2s 活跃,其它同员工同账号实例已 7h 过期 → **n=0,primary,不 block** | 不 block |
| audit | `service_account_audit` 最新只有手动 confirm/reassign,**无 reject_collect / instance_conflict** | 上传未被拒、也未触发冲突 |
| 网络/鉴权 | 心跳实例 885 持续更新(到达 server) | events/batch 同 URL+token 必能到 |
| W22 是否碰采集路径 | `git diff bb8366d..81de0b8 -- eventsController.js _shared.js` **空** | W22 未碰 |
| server 日志 | 仅启动行,无 error | 无崩溃 |

> ⚠️ 排查中一个**自身坑**:首次跑仲裁查询用 ad-hoc `docker exec mysql`(session TZ=UTC),NOW()=UTC 而 `last_seen_at` 存的是 CST,差 8h 导致过期实例被误判"活跃"(假阳性 n=1)。`SET time_zone='+08:00'` 对齐 app 连接后 n=0。**app 连接本就 `SET time_zone='+08:00'`,故实际仲裁不受影响**。

### 5.4 根因:W17 position 冷启动撞号
**server 去重键** = `platform_message_id`([eventsController.js:42-47](../../server/src/controllers/v1/eventsController.js#L42-L47),`SELECT id FROM messages WHERE tenant_id=? AND platform_message_id=?`)。

**message_id 合成** = `syn_hash(conversationId | pos:N)`(纯位置)。证据:DB 中 content="1" 的多条消息有**不同** message_id 且呈位置递增(inbound id47-51 = `syn_42.../43/44/45/46`),证明 id 含 position 而非纯内容。
- **链路(已核实)**:adapter 先给 message_id 一个内容 id([private-message.adapter.js:489](../../plugin/adapters/douyin/private-message.adapter.js#L489),未传 position);随后 **[legacy-collector.js:126-130](../../plugin/runtime/legacy-collector.js#L126-L130)** 调 `PositionTracker.assign(conversationId, events)` 赋 `event.position`,并**重写** `event.message_id = Dom.synthMessageId({conversationId, position})` → 覆盖为位置 id。
- 合成函数 [Dom.synthMessageId](../../plugin/shared/dom-utils.js#L76):传 `position` 时走 `'syn_'+simpleHash(conversationId+'|pos:'+position)`。
- position 由 [PositionTracker](../../plugin/runtime/position-tracker.js) 锚点窗口分配,状态 `{nextPos, seq:[{k,p}]}` **持久化在 chrome.storage**。

**撞号链**:
1. **重装插件 → chrome.storage 清空 → PositionTracker `seq=[]` → 冷启动**([position-tracker.js](../../plugin/runtime/position-tracker.js) `computeAssignments` 的 `seq.length===0` 分支:给当前可见消息从 `nextPos=0` 重新编号)。
2. 抖音私信是虚拟列表,只渲染最近 ~17 条。冷启动把这 17 条重编 `pos:0..16`——但它们在库里早已以历史 position 存过(早前会话采过更多条,position 0..K)。
3. 新消息"666"(第 18 条可见)拿到接续的 position,**正好等于库中某条历史消息的 position** → 同 `syn_hash(conv|pos)` → server 命中已存行 → **duplicated → accepted:0**。

**console 实证即证明**:全新"666"能被判 duplicated,只可能是其 position-hash 撞了已存行(position-hash = f(conv, position),内容/时区都不进 hash 的位置路径)。

### 5.5 与 v0.6.3 / 时区 / +8h 的关系:**无关**
- message_id 是**客户端**算的,position 来自 PositionTracker(chrome.storage),与 server 容器时区无关。
- 第 2 节的 **+8h UPDATE 只改了 `occurred_at/segment_at/last_message_at/last_inbound_at`,未动 `platform_message_id`**,不影响去重键。
- W22 未碰采集路径(`git diff` 空)。
- **触发点是「重装插件」**(chrome.storage 清空),非任何发版。

### 5.6 修复方向(待拍板)
- **A 立即/止血**:清 prod 测试会话数据(`messages`/`conversations`,已备份 `preV063`)重采。空库后冷启动 position 不撞,正常入库。属 prod 删数据,需明确授权。
- **B 根治(W17/W22 代码)**:PositionTracker 冷启动不从 0 乱编。候选:
  - 冷启动时向 server 查该 `(tenant, conversation_id)` 已有 `MAX(position)`,`nextPos` 从其后续编;
  - 或 server 去重键不纯靠 position(叠加 content/occurred_at 等),区分"同 position 不同内容";
  - 或 position 状态改为可跨重装恢复(如以 server 为准回灌)。
  - 本质:**position 持久化在 chrome.storage,重装/换浏览器/换设备都会冷启动撞号**——是 W17 的设计局限,非偶发。
- **codex 复核点**:
  1. 上述"冷启动重编 position 与历史 position 撞号"是否确为 duplicated 的唯一可能原因?有无其它路径(如 PositionTracker `degrade` 分支续编却仍撞、或 server 端 message_id 二次改写)导致同样现象?
  2. 修复方向 B 的几个候选哪个最稳、是否有副作用(如"查 server MAX(position)"与"有几条存几条/重复连发各自 position"语义冲突)?
  3. 是否需要同时给 server 去重加"内容兜底",避免纯 position 撞号在多端场景反复发生?
