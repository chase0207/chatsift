# 抖音私信准确性统计方案

> 日期: 2026-06-07
> 范围: 第一阶段试点,仅统计“抖音-抖音私信”(`platform_page='private-message'`)。
> 目标: 用页面真值、插件采集结果、服务端入库结果三方对账,计算准确性和稳定性指标。

---

## 1. 统计原则

统计以“页面真值 vs 系统结果”为核心。

```text
页面真值
  -> 插件采集事件
  -> 服务端 messages/conversations
  -> 后台展示/分析结果
```

不能只看“服务端入库了多少条”。如果页面真值缺失,无法判断完整率、方向准确率、顺序准确率和时间准确率。

## 3. 指标计算口径

| 指标 | 计算方式 |
|---|---|
| 会话识别准确率 | 正确归入目标会话的消息数 / 页面真值消息数 |
| 消息完整率 | DB 入库消息数 / 页面真值消息数 |
| 消息去重准确率 | 1 - 重复消息数 / DB 入库消息数 |
| 方向准确率 | 方向正确消息数 / 抽样消息数 |
| 顺序准确率 | 顺序正确消息数 / 抽样消息数 |
| inbound 时间准确率 | 时间正确 inbound 数 / inbound 抽样数 |
| 上传成功率 | accepted / collected events |
| rejected 比例 | rejected / uploaded events |
| duplicated 比例 | duplicated / uploaded events |
| 分析完成率 | done jobs / accepted inbound messages |
| 长跑稳定性 | 按小时统计新增、重复、失败、积压趋势 |

## 4. 推荐统计 SQL

以下 SQL 以当前库为测试库为前提。生产库不得直接执行清理类 SQL。

### 4.1 抖音私信会话概览

```sql
SELECT
  c.id,
  c.tenant_id,
  c.service_account_id,
  c.platform,
  c.platform_page,
  c.platform_conversation_id,
  c.customer_nickname,
  c.message_count,
  c.last_message_at,
  c.last_inbound_at,
  c.intent_label,
  c.completeness_score
FROM conversations c
WHERE c.platform = 'douyin'
  AND c.platform_page = 'private-message'
ORDER BY c.last_message_at DESC, c.id DESC;
```

### 4.2 单会话消息明细

```sql
SELECT
  m.id,
  m.platform_message_id,
  m.position,
  m.direction,
  m.sender_nickname,
  m.content_type,
  m.content_text,
  m.occurred_at,
  m.segment_at,
  JSON_UNQUOTE(JSON_EXTRACT(m.raw_snapshot, '$.position_source')) AS position_source,
  JSON_UNQUOTE(JSON_EXTRACT(m.raw_snapshot, '$.time_source')) AS time_source,
  JSON_UNQUOTE(JSON_EXTRACT(m.raw_snapshot, '$.time_estimated')) AS time_estimated
FROM messages m
WHERE m.conversation_id = ?
ORDER BY m.segment_at ASC, m.position ASC, m.id ASC;
```

### 4.3 重复 message_id 检查

```sql
SELECT
  tenant_id,
  platform_message_id,
  COUNT(*) AS cnt
FROM messages
GROUP BY tenant_id, platform_message_id
HAVING COUNT(*) > 1;
```

正常应为空。

### 4.4 重复 position 检查

```sql
SELECT
  tenant_id,
  conversation_id,
  position,
  COUNT(*) AS cnt
FROM messages
WHERE position IS NOT NULL
GROUP BY tenant_id, conversation_id, position
HAVING COUNT(*) > 1;
```

正常应为空。

### 4.5 position 来源分布

```sql
SELECT
  JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.position_source')) AS position_source,
  COUNT(*) AS cnt
FROM messages
WHERE conversation_id = ?
GROUP BY JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.position_source'))
ORDER BY cnt DESC;
```

关注点:

- `cold`: 首次采集。
- `aligned`: 命中锚点,幂等状态较好。
- `degrade`: 无唯一锚点,需要抽样复核是否导致重复或错序。

### 4.6 时间来源分布

```sql
SELECT
  JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.time_source')) AS time_source,
  JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.time_estimated')) AS time_estimated,
  COUNT(*) AS cnt
FROM messages
WHERE conversation_id = ?
GROUP BY
  JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.time_source')),
  JSON_UNQUOTE(JSON_EXTRACT(raw_snapshot, '$.time_estimated'))
ORDER BY cnt DESC;
```

目标:

- inbound 应以 `precise-invisible` 为主。
- outbound 允许无精确 `occurred_at`,但排序必须可解释。

### 4.7 outbound 时间检查

```sql
SELECT
  COUNT(*) AS outbound_total,
  SUM(CASE WHEN occurred_at IS NULL THEN 1 ELSE 0 END) AS outbound_null_time,
  SUM(CASE WHEN occurred_at IS NOT NULL THEN 1 ELSE 0 END) AS outbound_has_time
FROM messages
WHERE conversation_id = ?
  AND direction = 'outbound';
```

W17 口径下,outbound 无精确时间时允许 `occurred_at=NULL`。

### 4.8 analysis_jobs 状态

```sql
SELECT
  status,
  COUNT(*) AS cnt
FROM analysis_jobs
WHERE conversation_id = ?
GROUP BY status;
```

正常完成后,pending/processing/failed 应为 0。

### 4.9 每小时采集趋势

```sql
SELECT
  DATE_FORMAT(uploaded_at, '%Y-%m-%d %H:00:00') AS hour_bucket,
  COUNT(*) AS message_count,
  COUNT(DISTINCT conversation_id) AS conversation_count
FROM messages
WHERE tenant_id = ?
  AND uploaded_at >= ?
GROUP BY DATE_FORMAT(uploaded_at, '%Y-%m-%d %H:00:00')
ORDER BY hour_bucket;
```

用于长跑观察是否突然中断、爆发重复或消息量异常。

## 5. 页面真值对账方法

建议把页面真值整理为 `truth_messages` 临时表或 CSV:

```sql
CREATE TEMPORARY TABLE truth_messages (
  sample_id VARCHAR(32),
  message_index INT,
  direction_expected VARCHAR(16),
  content_expected TEXT,
  time_expected DATETIME NULL
);
```

对账逻辑:

1. 按 `message_index` 与 DB 排序结果对齐。
2. 文本完全一致优先。
3. 文本重复时按 position 顺序对齐。
4. inbound 时间以页面隐藏精确时间为准。
5. outbound 时间不强制精确,只检查顺序。

## 7. 长跑统计方法

长跑期间每 30 分钟记录一次:

```text
当前时间
插件是否在线
当前页面 URL
queue size
messages 总数
最近 30 分钟新增 messages
duplicated/rejected 变化
analysis_jobs pending/failed
最新 last_message_at
后台是否可打开会话
```

长跑异常判定:

| 异常 | 判定 |
|---|---|
| 采集中断 | 页面有新增消息,30 分钟内 DB 无新增 |
| 重复爆发 | 同一会话短时间内 message_count 异常增长且页面无对应新增 |
| 队列积压 | queue size 持续增长且上传无 accepted |
| 分析堆积 | pending/processing 持续增长 |
| 会话错归 | 新消息进入错误 customer_nickname 或 conversation_id |
