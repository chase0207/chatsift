# 浏览器 RPA 客服消息采集主线评估与分阶段计划

> 日期: 2026-06-07
> 范围: 浏览器 RPA 做客服消息采集的工程难点、chatsift 当前实现评估、业务目标分阶段计划。
> 口径: 以当前业务主线为准:先跑通“抖音-抖音私信”,再扩展抖音系其他页面,最后批量化扩展国内主流平台。

---

## 1. 背景

chatsift 当前定位是只读会话诊断系统:浏览器插件在客服原生页面中做 DOM 采集,将消息上报到 server,再进入五引擎分析、后台展示、工单和线索流程。

浏览器 RPA 做客服消息采集的难点不是“能不能读到 DOM”,而是如何在平台页面持续变化、虚拟列表、会话切换、插件生命周期变化、DOM 漂移的情况下,稳定地产生可信的消息事件流。

因此,当前业务目标不应按“平台数量”优先,而应按“单平台准确稳定样板”优先。

---

## 2. 核心工程难点

| 层级 | 难点 | 影响 |
|---|---|---|
| 平台识别 | 判断当前 URL/页面是否属于目标客服页面 | 错页采集、漏启动 |
| 会话识别 | 判断消息属于哪个客户会话 | 串会话是最高风险 |
| 消息容器定位 | 找到稳定消息区域,避免页面噪声 | 误采系统区域、列表预览、客服自身信息 |
| DOM 快照 | 保留足够证据用于回放和排错 | 出问题后无法定位根因 |
| 消息解析 | 提取方向、文本、时间、类型、附件 | 漏采、方向反、类型错 |
| 消息指纹 | 为每条消息生成稳定身份 | 重采重复、重复连发丢失 |
| 去重/断点 | 插件刷新、页面重载、网络失败后保持连续性 | 重复入库或漏采 |
| 上传队列 | 本地队列、失败重试、token 缺失处理 | 网络波动下数据丢失 |
| 服务端幂等 | server 再兜一层唯一约束 | 防止插件侧重复造成脏数据 |
| 日志/自检 | 分阶段定位采集失败点 | 重复 bug 只能猜修 |

一句话:客服消息采集不是爬虫问题,是浏览器内状态同步系统问题。

---

## 3. 当前代码评估摘要

| 页面/模块 | 完成度 | 结论 |
|---|---:|---|
| 抖音私信 `private-message` | 80-85% | 当前主路径,已覆盖会话、时间、position 去重、段排序、账号归属 |
| 抖音来客 `laike-message` | 45-55% | 能采文本,但时间、账号归属、快照和真机证据弱 |
| 抖音飞鸽 `feige` | 40-50% | 基本是选择器级适配,稳定事件流能力不足 |
| 通用 runtime | 65-70% | 主采集链路清楚,但旧 V1.9 runtime 混杂 |
| 服务端事件链路 | 75-80% | 入库、幂等、队列、分析闭合较好;云端对账未完成 |

### 3.1 抖音私信

抖音私信是当前唯一适合作为试点样板的页面。

已有能力:

- 能通过 adapter 匹配 `life.douyin.com/cs/web/clue_private_message`、`im.douyin.com` 等私信路径。
- `legacy-collector` 构造 `conversation_id`,并已把 `account_biz_id` 纳入会话维度。
- `private-message.adapter.js` 对 `div.my-4` 消息行做专门扫描。
- inbound 优先读取隐藏精确时间。
- W17 后 `message_id` 走 `conversationId + position`,支持重复连发保留和重采幂等。
- 服务端有 `platform_message_id` 唯一键和 `(tenant_id, conversation_id, position)` 唯一键双保险。
- W19 阶段B已把 private-message 的客服账号归属链路接上。

主要风险:

- 还缺云端对账,无法系统发现“本地已见但服务端缺失”或“服务端多出重复”的情况。
- 采集日志仍偏工程 console,没有形成产品化诊断事件。
- 清库重采、清 storage、插件重载之间仍依赖操作纪律。
- 附件、卡片、系统消息还没有成为稳定消息类型体系。

### 3.2 抖音来客

来客当前适合保留为后续扩展对象,不建议与抖音私信并列验收。

主要短板:

- `account_biz_id` 来源未打通,`service_account_id` 可能为空。
- 时间解析弱,非 life 分支会落到采集时刻。
- raw_snapshot 信息较少。
- 真机稳定性证据不足。

### 3.3 抖音飞鸽

飞鸽当前更像早期适配器。

主要短板:

- 账号归属未完整闭合。
- 时间、segment、direction 证据弱于 private-message。
- 缺真实 DOM 样本库和回放验证。
- 适配层能入库,但尚未达到“准确稳定样板”标准。

## 4. 业务目标分阶段计划

## 阶段 1: 以“抖音-抖音私信”为试点跑通全流程

目标:只聚焦 private-message,不分散到来客、飞鸽和其他平台。先把一个页面做到准确、稳定、可验收、可复现。

建议验收指标:

| 指标 | 建议口径 |
|---|---|
| 会话识别准确率 | >= 99%,不能串会话 |
| 消息采集完整率 | >= 98%,真实新增消息不漏 |
| 消息去重准确率 | >= 99.5%,重复重采不重复入库 |
| 消息方向准确率 | >= 99%,inbound/outbound 不反 |
| 消息顺序准确率 | >= 98%,后台展示顺序符合原页面 |
| inbound 时间准确率 | >= 95%,优先使用页面隐藏精确时间 |
| 连续运行稳定性 | 前台打开 4-8 小时无明显漏采/重复爆发 |
| 恢复能力 | 页面刷新、插件重启、网络失败后可恢复 |

阶段 1 必做:

1. 建立抖音私信真机验收清单。
2. 建立清库重采流程:清 server 数据、清插件 `chrome.storage` 中 `w17_pos_*`、清 EventQueue、清 seen cache。
3. 补运行日志分阶段字段:platform、page、adapter、conversation_id、account_biz_id、raw_count、event_count、position_source、accepted、duplicated、rejected。
4. 做 W17 阶段二云端对账,发现漏采、重复、position 不一致。
5. 建立异常样本回放机制,把真实 DOM 样本沉淀为可重复验证资产。

阶段 1 不做:

- 不扩新平台。
- 不做自动回复。
- 不追求来客/飞鸽同等可用。
- 不把旧 V1.9 runtime 清理作为前置。

阶段 1 完成标准:

抖音私信从“能采集”升级为“可证明采得准、采得稳、出错可定位”。

---

## 阶段 2: 扩展到抖音系其他页面

目标:把 private-message 的工程标准复制到抖音系其他页面,优先来客、飞鸽。

每个页面必须补齐同一套 adapter 契约:

```text
matchPage
session identity
account_biz_id
message container
message parser
direction parser
time/segment parser
raw_snapshot
position assignment
adapter self-check
真实 DOM 样本
```

阶段 2 重点:

| 页面 | 优先补齐 |
|---|---|
| 来客 | account_biz_id、时间/segment、raw_snapshot、真机回归 |
| 飞鸽 | account_biz_id、方向判定、时间/segment、真实 DOM 样本 |

阶段 2 验收口径:

- 每个页面都必须能独立统计准确率和稳定性。
- 不能只用“能入库”作为完成标准。
- 与 private-message 共用 runtime,但 adapter 选择器、身份、时间规则必须页面级独立。

---

## 阶段 3: 批量化扩展国内主流平台

目标:把平台接入从“手写单个 adapter”升级为“平台接入工厂”。

需要沉淀三类资产。

### 3.1 平台接入规范

每个平台接入前必须确认:

```text
platform_page 命名
URL 匹配规则
会话 ID 来源优先级
账号 ID 来源优先级
消息 DOM 容器
方向判定规则
时间判定规则
附件/卡片类型
raw_snapshot 必填字段
验收样本格式
```

### 3.2 DOM 样本库

每个平台至少保留:

```text
空会话
单条 inbound
单条 outbound
连续多条
重复文本
图片/卡片/系统消息
历史滚动
会话切换
刷新恢复
```

### 3.3 自动化验收

每接一个平台,都跑同一套:

```text
adapter 静态检查
DOM snapshot 回放
message parser 单测
position 去重测试
events/batch 入库测试
后台排序测试
长时间运行测试
```

阶段 3 的核心不是平台数量,而是让新增平台的接入成本和质量变得可控。

## 5. 推荐优先级

| 优先级 | 任务 |
|---|---|
| P0 | 抖音私信准确性验收体系 |
| P0 | 抖音私信稳定性长跑 |
| P0 | 云端对账 / 重复漏采检测 |
| P1 | 抖音私信日志分阶段可观测 |
| P1 | 来客/飞鸽补 account_biz_id 和时间解析 |
| P2 | 抖音系 adapter 接入规范 |
| P2 | DOM 样本库和回放工具 |
| P3 | 小红书、快手、美团、微信等平台扩展 |

---

## 6. 当前判断

当前最合理的主线是:

```text
抖音私信试点闭环
  -> 抖音系页面复制
  -> 平台接入规范化
  -> 主流平台批量扩展
```

短期不要追多平台数量。先把“抖音-抖音私信”做成可验收、可复现、可解释的样板页面。只有这个样板跑稳,后续平台扩展才不会变成不断猜修 DOM 的人力项目。
