# 抖音私信试点验收标准

> 日期: 2026-06-07
> 范围: 第一阶段试点,仅覆盖“抖音-抖音私信”(`private-message`)。
> 目标: 以准确性和稳定性为核心,把抖音私信做成后续抖音系和多平台扩展的样板页面。

---

## 1. 试点目标

本阶段只验证一条主线:

```text
抖音私信原生页面
  -> 插件 DOM 采集
  -> 本地 position 去重
  -> /api/v1/events/batch 上报
  -> conversations/messages 入库
  -> analysis_jobs 消费
  -> intent/completeness/workorder/lead 产出
  -> 后台会话/聚合/线索/工单正确展示
```

本阶段不追求来客、飞鸽、小红书、快手等页面可用。来客/飞鸽只作为后续复制对象,不参与本阶段通过判定。

---

## 2. 验收指标

| 指标 | 口径 | 目标 |
|---|---|---:|
| 会话识别准确率 | 页面真实客户消息是否进入正确 `conversation_id` | >= 99% |
| 消息采集完整率 | DB 入库消息数 / 页面真值消息数 | >= 98% |
| 消息去重准确率 | 重采/刷新后未重复入库的比例 | >= 99.5% |
| 方向准确率 | inbound/outbound 与页面真实方向一致 | >= 99% |
| 顺序准确率 | 后台消息顺序与页面顺序一致 | >= 98% |
| inbound 时间准确率 | inbound 入库时间与页面精确时间一致或可解释 | >= 95% |
| 上传成功率 | 服务端 accepted / 插件 collected events | >= 99% |
| 分析完成率 | `analysis_jobs.done` / accepted inbound messages | >= 99% |
| 连续运行稳定性 | 前台打开 4-8 小时,无明显漏采/重复爆发/采集中断 | 通过 |
| 恢复能力 | 页面刷新、插件重启、网络失败后可恢复采集并不重复爆发 | 通过 |

---

## 3. 失败等级

| 等级 | 判定 | 处理 |
|---|---|---|
| P0 | 串会话、方向大面积反、重复爆库、持续无法入库、插件采集完全停止 | 阻塞试点,立即修 |
| P1 | 少量漏采、错序、时间明显错误、position 不稳定、analysis_jobs 堆积 | 本阶段必须修 |
| P2 | 日志不足、个别样本无法复现、附件/卡片识别不完整 | 记录并排期,不一定阻塞试点 |
| P3 | 后台展示文案、轻微 UI、非主线统计项 | 不阻塞试点 |

P0/P1 未关闭时,不得进入来客/飞鸽扩展阶段。

---

## 4. 样本集要求

第一轮试点至少准备 10 组真实样本。

| 样本 | 目的 | 最低要求 |
|---|---|---|
| S01 单条 inbound | 基础采集 | 客户发 1 条文本 |
| S02 单条 outbound | 方向识别 | 客服发 1 条文本 |
| S03 inbound/outbound 交错 | 方向和顺序 | 至少 6 条交错消息 |
| S04 重复文本连发 | position 去重 | 连续发送相同文本 >= 3 条 |
| S05 长会话 | 完整率和长列表 | 消息 >= 50 条 |
| S06 跨天历史消息 | 时间解析 | 包含今天/昨天/完整日期 |
| S07 时间分隔条 | segment 排序 | 至少 2 个时间段 |
| S08 页面刷新重采 | 幂等 | 刷新后重复采集同一会话 |
| S09 插件重启重采 | 本地状态恢复 | 重载插件后继续采集 |
| S10 网络失败恢复 | 上传队列重试 | 模拟短时上传失败后恢复 |

每个样本必须记录:

```text
sample_id
页面 URL
accountId
客户昵称
截图或 DOM snapshot
页面真值消息数
页面真值 inbound 数
页面真值 outbound 数
特殊点说明
采集开始时间
采集结束时间
```

---

## 5. 试点前置条件

试点开始前必须确认:

1. 插件版本和 server/admin 版本一致。
2. 使用租户外部账号登录插件,不能用 internal 平台方账号上报。
3. 只打开目标抖音私信页面,避免跨页面噪声。
4. 抖音私信页面保持前台打开。
5. 清库重采前已确认目标库不是生产库,生产数据不参与本阶段。
6. 清理插件本地状态:

```text
w17_pos_*
chatsift_event_queue
chatsift_event_seen_ids
```

---

## 6. 基线验收流程

```text
1. 备份/确认测试库
2. 清理 conversations/messages/leads/workorders/analysis_jobs 测试数据
3. 清理插件 chrome.storage 采集状态
4. 重载插件
5. 登录租户账号
6. 打开抖音私信页面
7. 对 S01-S10 样本逐项采集
8. 导出 DB 统计
9. 对照页面真值
10. 产出问题清单
```

第一轮基线只允许做事实统计和问题分级,不在统计未完成前边测边改。

---

## 7. 问题闭环顺序

修复顺序固定为:

1. 会话身份: `account_biz_id`、`conversation_id`、客户昵称。
2. 消息完整率: 是否漏采真实 DOM 消息。
3. 去重与 position: 重采、刷新、重复文本是否稳定。
4. 方向: inbound/outbound 是否准确。
5. 时间和顺序: `occurred_at`、`segment_at`、position 排序是否符合页面。
6. 上传和恢复: queue、token、events/batch、网络失败。
7. 分析链路: jobs、intent、completeness、workorder、lead。
8. 日志和自检: 每个 P0/P1 修复必须补定位证据。

---

## 8. 长跑验收

短样本通过后进行三轮长跑:

| 轮次 | 时长 | 目标 |
|---|---:|---|
| 短跑 | 30 分钟 | 验证基础链路持续运行 |
| 中跑 | 2 小时 | 验证重复采集、页面刷新、队列恢复 |
| 长跑 | 4-8 小时 | 验证真实工作日稳定性 |

长跑必须记录:

```text
采集开始/结束时间
插件版本
server/admin 版本
页面 URL
accountId
conversation_count
message_count
duplicated_count
rejected_count
queue 最大积压
analysis_jobs pending/failed
插件是否停止采集
后台展示是否正常
```

---

## 9. 通过标准

抖音私信试点通过必须同时满足:

1. 所有 P0 关闭。
2. P1 要么关闭,要么有明确不阻塞试点的产品确认。
3. S01-S10 样本统计达标。
4. 4-8 小时长跑通过。
5. 后台会话、聚合、线索、工单展示链路可用。
6. 形成最终《抖音私信试点验收报告》。
