## 2. B1 — 插件抓 account_biz_id + 坐席昵称,独立上报

### 2.1 account_biz_id 来源(URL accountId)
- **历史线索**:W6.5 曾用 `_param('accountId')` 从 URL 抓 accountId,后在 W6.5 移除(只留 pageKey+nickname,见 [W6.5_tasks.md:127](docs/prd/V1.0/W6.5_tasks.md#L127))。→ **B1 恢复抓 accountId**。
- **实现**:新增 `_readAccountBizId()`,从 `location.href` 解析 query 参数 `accountId`(URLSearchParams 或正则)。Q1 实测已确认 accountId 是"商家账号"稳定键(换客户/换坐席不变)。
  - ★参数名/位置以**真机为准**(B1 第一步打印 location.href 核对;design Q1 实测过)。若私信页用 path 段而非 query,正则适配。
- **落点**:`legacy-collector._buildSessionInfo`(主合成点,所有 adapter 共用 sessionInfo),把 `accountBizId` 放进返回的 sessionInfo;**不在各 adapter 各抓一遍**(收口单点,避免漂移)。

### 2.2 坐席昵称独立上报
- 现状:坐席昵称只在 outbound 时混进 `sender_nickname`([adapter:464](plugin/adapters/douyin/private-message.adapter.js#L464) `rawMsg.agent_name || sessionInfo.accountNickname`)。
- **改**:`toConversationEvent` 的 event 新增**独立字段** `account_biz_id`(来自 sessionInfo)、`account_nickname`(= sessionInfo.accountNickname,坐席名)。sender_nickname 保留不动(兼容/展示)。

### 2.3 透传与范围
- **透传**:event-collector/event-queue/event-uploader 是通用透传(不挑字段),B1 在 event 上加字段即自动随上报——**B1 验证一次即可,无需改 collector/uploader**。
- **★范围决策(Q1)**:`private-message`(抖音私信,主路径)必改。`laike-message`/`feige` 两个 adapter 也有 conversationId+accountNickname([laike:311](plugin/adapters/douyin/laike-message.adapter.js#L311) / [feige:208](plugin/adapters/douyin/feige.adapter.js#L208)),但它们的 URL 结构不同、account_biz_id 抓法待定。**若 B2 对"缺 account_biz_id"一律拒绝,这俩页面的采集会全废**。→ 见 Q1:B 阶段是否只做 private-message、laike/feige 标后续(且 B2 拒绝按 page 放行)?

## 3. B2 — server upsert service_account + 挂归属 + lead/workorder 继承

### 3.1 platform/page 字符串 → id 映射(新依赖)
- service_accounts FK 要 `platform_id`/`page_id`(INT),但 event 只带 `platform`(douyin)/`platform_page`(private-message)字符串。
- **B2 需查映射**:`platforms WHERE platform_key=?` → platform_id;`platform_pages WHERE platform_id=? AND ...` → page_id。
  - ★ page_id NOT NULL(A 已定 Q3)。`platform_page` 字符串(private-message/laike-message/feige)到 `platform_pages.id` 的映射要有确定规则。现 platform_pages seed 的 page_name 是中文(来客私信/飞鸽/抖音私信),与 event 的 platform_page 英文 key **对不上** → **B2 要建一张映射或给 platform_pages 加 page_key**。见 Q2。

### 3.2 upsert service_accounts(按 conversation/batch 粒度,codex#9)
- 在 batch 事务内,**按 (tenant,platform_id,page_id,account_biz_id,account_nickname) 去重后 upsert**(一个 batch 内同账号只查一次,不逐条消息打库):
  ```sql
  INSERT INTO service_accounts (tenant_id,platform_id,page_id,account_biz_id,account_nickname,first_seen_at)
  VALUES (?,?,?,?,?,NOW())
  ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id), updated_at=NOW();  -- 命中 uk_account 取回 id
  ```
  得 `service_account_id`,batch 内 memoize。

### 3.3 缺 account_biz_id 拒绝(codex#4,不兜底)
- event 缺 `account_biz_id` → 该 event **reject + 计数**(沿用现有 `rejected`),返回里带明确原因(如 `reason:'missing_account_biz_id'`)+ 可选"插件最低版本"提示。**绝不写 unknown 账号**(否则脏归属)。
- ★阶段边界(你的补充):A 阶段 eventsController 不做此拒绝,**B 才做**。

### 3.4 service_account_id 注入 5 处
| 表 | 注入点 | 取值 |
|---|---|---|
| conversations | INSERT([:74])/UPDATE([:52]) | 本次 upsert 的 sa_id(最近坐席,见 Q3) |
| messages | INSERT([:94]) | 本条消息坐席的 sa_id |
| analysis_jobs | INSERT([:113]) | 同 message |
| leads | lead-engine INSERT([lead-engine.js:51]) | ctx.conversation.service_account_id 继承 |
| workorders | workorder-engine INSERT([workorder-engine.js:44]) | 同上继承 |
- **lead/workorder 继承路径**:analyzer.buildContext 的 conversation SELECT([analyzer.js:95])加 `service_account_id` → `ctx.conversation.service_account_id` → 两个 engine INSERT 带上。

### 3.5 自动归属(codex#5,限角色)
- 首次见某 service_account 时,**仅当上报者角色=客服**,upsert `employee_service_account(tenant_id, employee_id=req.user.id, service_account_id, assigned_by=NULL/系统)`(uk_assign 幂等)。
- **租户超管不自动绑**(默认看全租户);assigned_by 标系统来源,租户超管后续可人工调整。
- 防共用电脑/代操作误授权:只在"客服"上报时建。

## 4. B3 — conversation_id 纳入 account_biz_id(重改动核心)

### 4.1 现状合成
- 主合成在 `legacy-collector._buildSessionInfo`([:65]):`conversationId = 'douyin_'+pageKey+'_'+simpleHash(pageKey+'|'+nickname)`,**不含账号** → 同 pageKey+客户昵称、跨不同商家账号会**误并**。

### 4.2 改法
- 改为:`conversationId = 'douyin_'+pageKey+'_'+account_biz_id+'_'+simpleHash(pageKey+'|'+account_biz_id+'|'+nickname)`。
  - 纳入 **account_biz_id(商家账号)** 维度。
  - **★坐席(account_nickname)不进**:同一商家账号下换坐席接待同一客户,业务上仍是同一会话,不因换坐席分裂(design §4.3)。坐席体现在 `service_account_id` 字段(消息级精确),不进 conversation_id。
- adapter 内 fallback 合成([private-message.adapter.js:452])同步纳入,口径一致。

### 4.3 与 W17 的连锁(必须一起清库)
- message_id = `syn_hash(conversationId|pos:position)`([dom-utils.js:80])→ **conversationId 变 ⇒ 全部 message_id 变**。
- position-tracker storage key = `'w17_pos_'+conversationId`([position-tracker.js:102])→ **conversationId 变 ⇒ 旧 position 序列作废**(等价换 key,见 B4)。
- → **B3 落地后,旧库的 conversation/message 全部对不上新 id**。**不可在线迁移,只能清库重采**(留阶段E,与 W17 position 一次清库一起生效——design §8 已定)。
- ★B3 是改会话标识的**重改动**,本方案即 tasks 要求的"先出方案审了再写"。

### 4.4 account_biz_id 缺失时 conversation_id 怎么办
- 若某 event 抓不到 account_biz_id:与 B2 拒绝一致——**该 event 不入库**(不会走到合成),因此 conversation_id 合成里 account_biz_id 恒非空。保证合成键完整(呼应 Q3 page_id NOT NULL 的同款"恒有"前提)。

## 5. B4 — M24 position-tracker 存储键隔离

- **关键洞察**:storage key 已是 `'w17_pos_'+conversationId`。B3 把 account_biz_id 纳入 conversationId 后,**换账号 ⇒ 不同 conversationId ⇒ 不同 key ⇒ 自动不串号**。M24 调研的"换账号 conv#4 残片"由 B3 顺带消除。
- **B4 仍要做的**:
  1. **跨租户硬隔离**:key 再前置 tenant 维度更稳妥(同一浏览器若先后登录不同租户员工)。建议 key = `'w17_pos_'+tenantHint+'_'+conversationId`,或确认 conversationId 已足够(pageKey+account_biz_id 实际已跨租户唯一)。→ 见 Q4。
  2. **清库连带清本地**(codex#6,阶段E 执行,B4 提供清单):重载插件 + 清 `chrome.storage` 中 `w17_pos_*` + 清 EventQueue/seen cache。否则新库 + 旧 position 序列错乱。
- B4 基本是"确认 + 文档化清理清单",代码改动小。
