## 0. 结论先行(一句话)

**租户改造面小而集中(单点 `tenantId()` + 登录链路 + schema + 清库,无历史数据迁移负担);真正的大缺口在 Dx3 —— "客服账号"零实体,对话/线索/工单完全不挂客服账号,`conversation_id` 合成键也不含账号维度,"资产原点"要从头建。** 唯一卡设计的未知是:客服账号用什么做**稳定键**(现在只有昵称文本,无稳定 UID,与 M1 消息位置同类困境)。

目标资产层级:`租户 > 平台 > 页面 > 客服账号(原点) > 对话/线索/工单`;员工 ↔ 客服账号多对多。
下面逐层对照"现状有什么 / 差什么"。

## 1. Dx1 — 租户表达现状 + 引入独立租户表的改动面

### 现状
- **"租户"= `tenant_id = req.user.id`,无独立租户表。** `_shared.js:9-11` `tenantId(req){ return req.user && req.user.id }`;`v1-schema.sql:7` 注释明写"单级租户 (user_id 即 tenant_id)"。
- 所有业务表都带 `tenant_id INT UNSIGNED`,注释"租户=users.id":conversations / messages / leads / workorders / intent_rules / price_table / tenant_llm_config / analysis_jobs。唯一键、索引一律 `tenant_id` 打头(如 `uk_platform_conv (tenant_id, platform, platform_conversation_id)`)。
- 业务查询**全部** `WHERE tenant_id = tenantId(req)`,已核实 conversations(`:9`)、leads(`:10`)、workorders(`:8`) 三个 controller;无越权(与 W16 调研一致)。
- `users` 表(`00_reused_tables.sql:15-26`)**没有 tenant_id 列** —— 用户自己即租户,员工不归属任何上级租户。

### 引入独立租户表的改动面评估(★小而集中★)
| 改动 | 位置 | 量 |
|---|---|---|
| 新建 `tenants` 表(企业主体:名称/状态/到期/...) | schema | 新增 1 表 |
| `users` 加 `tenant_id` FK(员工归属租户) | schema + 注册逻辑 | 加 1 列 |
| 登录 payload 带 `tenant_id` | authController.login/userinfo/verify payload | 3 处 |
| auth 中间件补全 `tenant_id`(旧 token 兼容) | auth.js(已有 is_super/permissions 补全范式,照抄) | 1 处 |
| **`tenantId(req)` 由 `req.user.id` → `req.user.tenant_id`** | `_shared.js` **单点** | **1 处** |
| 业务表 `tenant_id` 列**不动**(仍 INT),只是语义从 users.id → tenants.id | — | 0(靠清库重建,不迁移) |

**关键**:所有 controller 取租户都走 `tenantId(req)` 这**一个函数**,改语义只改它一处,controller 无须逐个动。生产无真实数据(产品决策7),**不需要数据迁移**,清库重建即可。改动主要落在 schema + 登录链路。**评估:低风险、改动面集中。**

## 2. Dx2 — 用户/角色/权限现状 + 角色清洗影响面

### 现状
- **users**(`00_reused_tables.sql:15`):id/username/password/`role`(TINYINT 1普通/9管理员,**兼容字段**)/`role_id`(FK roles)/status/expire_at。**无 tenant_id**。种子仅 1 个:`admin`(role=9,role_id=1)。
- **roles**(`:4`):id/name/`is_super`/`data_scope`(self/dept/all)/status。种子仅 **2 条**:`1=超级管理员`(is_super=1,all)、`2=普通用户`(is_super=0,self)。
- **登录 payload**(authController.login `:75-83`):id/username/role/role_id/is_super/data_scope/permissions。`is_super=1` 时 `permissions=null`(放行不看,`:73`)。
- **鉴权两道**:
  - `auth.js`:验 JWT → `req.user`;旧 token 补 is_super/data_scope(`:16`)、permissions(`:32`,W16 加)。
  - `permission.js`:`requirePermission(code)` —— **is_super 直接放行**(`:18`);否则查 `permissions` 数组含不含 code(`:21`)。
- **数据隔离与角色无关**:业务查询按 `tenant_id=req.user.id` 过滤,纯按登录 user,不看角色。
- W16:前端 `entry.js` 按域名分入口;后端 `is_super` 分"内部/外部"两档。

### 角色清洗(管理员→内部用户、普通用户→租户管理员、新增客服)影响面
| 影响项 | 说明 |
|---|---|
| **角色数量** | 现仅 2 条。需扩 ≥3:内部用户(原超管 is_super=1)、租户管理员(租户内最高,管本租户员工/客服账号分配)、客服(普通员工,只看自己客服账号资产)。 |
| **缺租户内分层** | 现 `is_super` 只分内部/外部两档,**没有"租户管理员 vs 客服"的租户内层级**。"租户管理员"和"客服"都是外部(is_super=0),**仅靠 is_super 区分不了** → 需落到 role_id/role_name 或新增标志。 |
| **data_scope 不够用** | self/all 已接入、dept 当 self(技术债)。W19"员工只看自己客服账号的资产"是**按客服账号过滤**,现有 self/dept/all 三档**不直接表达**这个维度。 |
| **登录域名判断** | Login.vue 现按 `is_super` 判内部/外部(W16)。清洗后"租户管理员/客服"都外部,域名分流不变;但若前端要按"租户管理员 vs 客服"显示不同菜单,需更细角色信息(不能只靠 is_super)。 |
| **role/role_id 双轨** | `role`(1/9)与 `role_id` 并存(技术债);**Dashboard.vue:137 还用 `role===9` 判超管**。清洗时建议统一口径到 role_id/is_super,否则两处易漏。 |
| **权限点配置** | 新角色要配 `role_has_permissions`(role↔menu)。现 role 2 权限 = dashboard/conversation:list/lead:manage/workorder:handle/analytics:view/aggregate:view(`00_reused_tables.sql:168,195`)。 |

## 3. Dx3 — ★平台/页面/客服账号现状 + 离"资产层级"差多少★(核心)

### 平台 / 页面:有表,但是**全局字典、无 tenant**
- **platforms**(`00_reused_tables.sql:56`):id/platform_name/platform_key/url/enabled/dom_status/sort_order。种子 8 个(douyin/xiaohongshu/...)。**无 tenant_id** —— 系统级字典,非租户资产。
- **platform_pages**(`:69`):platform_id FK/page_name/url/sort_order。抖音下:来客私信/飞鸽/抖音私信。**也全局、无 tenant_id**。
- 业务侧 `conversations.platform` / `platform_page` 是**字符串字段**(douyin / private-message),**不外键** platforms/platform_pages —— 平台/页面在会话里只是文本标签,不是实体引用。

### 客服账号:**零实体,只散落为文本**(★最大缺口★)
- **没有任何"客服账号"表。**
- 客服账号信息仅两种形态:
  1. `messages.sender_nickname`(outbound 行)= 客服名**文本**(eventsController `:104` 入库)。
  2. `conversations` 上**完全没有 agent/客服/account 字段**(只有 platform/platform_page 字符串 + customer_*)。
- **对话/线索/工单怎么挂客服账号 → 不挂**:
  - conversations:无 agent 字段。当前"按客服筛选"靠 `req.query.agent` → `messages WHERE direction='outbound' AND sender_nickname = ?`(**纯文本匹配**,conversationsController `:33-39`);客服下拉选项也是 `SELECT DISTINCT sender_nickname ... outbound`(`:180`)。
  - leads/workorders:有 `assigned_to`=**users.id**(后台员工负责人/派单),**不是抖音客服账号**;无 agent 字段。
- **`conversation_id` 合成键不含客服账号**:插件 `legacy-collector.js:65` `conversationId = 'douyin_'+pageKey+'_'+hash(pageKey|客户昵称)`,**只含页面+客户昵称**。→ 同一客户被**不同客服账号**接待时,会被合并成**同一条会话**(归属歧义)。

### 离"客服账号作资产原点"差多少(差距清单)
| # | 缺什么 | 现状 |
|---|---|---|
| 1 | `service_accounts` 实体表(tenant, platform, page, 账号名/UID) | 完全没有 |
| 2 | `conversations.service_account_id` FK | 没有(只有 platform_page 文本) |
| 3 | leads/workorders 的客服账号归属 | 没有(assigned_to 是后台员工,语义不同) |
| 4 | `conversation_id` 纳入账号维度 | 不含,跨账号会误并 |
| 5 | 员工 ↔ 客服账号 多对多分配表 | 没有 |
| 6 | 平台/页面归到资产层级(租户>平台>页面) | platforms/pages 是全局字典、无 tenant,需定复用策略 |

**可复用的**:platforms/platform_pages 字典本体;`messages.sender_nickname` 作账号名来源;conversationsController 已有的 `agent` 文本筛选可平滑升级为 `service_account_id` 筛选。

## 4. Dx4 — 客服账号名来源(插件链路)+ 能否自动建归属

### 抓取:两条来源(已实现)
1. **逐条 outbound**:`_extractAgentName(el)`(private-message.adapter.js `:295`)从消息行 `p.text-right.text-gray-2` 取文本节点(排除时间 span)。
2. **会话级登录账号名**:`_readAccountNickname()`(legacy-collector.js `:33`)从 `[class*="imUserName"]` 或来客 outbound 行 `p.text-right` 取 → 存入 `sessionInfo.accountNickname`(`:67`)。**这就是"当前登录是哪个客服账号"的天然原点。**

### 上报:客服账号名**只混在 sender_nickname,无独立维度**
- `toConversationEvent`(adapter `:442`)组装 event,字段:platform/platform_page/conversation_id/message_id/direction/**sender_nickname**/content_*/occurred_at/raw_snapshot。
- 客服名只进 `sender_nickname`(outbound = `rawMsg.agent_name || sessionInfo.accountNickname`,`:464`)。**event 没有独立的"客服账号"字段**(无 account_name/account_uid),`conversation_id` 也不含账号。

### "默认谁采集归谁"能否自动建立 → **能拿到,但当前没上报、server 无处接、键不稳**
- ✅ 插件**能拿到**当前登录客服账号 = `sessionInfo.accountNickname`,链路里已用作"自己"(legacy-collector `:59` 客户昵称==登录账号名 → 判误读跳过)。
- ❌ 当前**没把它作为独立维度上报**;server `batch` 入库也无 `service_accounts` 可 upsert。
- ⚠️ **稳定性风险(关键未知)**:`accountNickname` 只是**昵称文本**,非稳定 UID —— 抖音昵称可改、可能重名。用昵称做"资产原点"的主键**不稳**(与 W17/M1 对消息稳定标识的困境同类)。当前 DOM 只抓到昵称文本,**没抓到稳定账号 ID**。

要自动建归属,需三步(留给设计):① 插件 event 加独立字段(account_nickname / 若能抓到 account_uid)② server batch upsert `service_accounts` 并把 `conversation.service_account_id` 指过去 ③ `conversation_id` 合成键纳入账号维度,避免跨账号误并。**前提**:先定账号用什么做稳定键(见待定 Q1)。

## 5. Dx5 — admin / mychat 页面现状 + 离目标差多少

### admin 现有页面(16 views)+ 入口分流
- views:Dashboard / Users / Plugins / Platforms / Roles / Menus(平台·系统组)+ Conversations(+Detail) / Leads(+Detail) / Workorders / Analytics / Aggregate / LlmConfig(租户·客服组)+ Logs + Login。
- 路由全挂 MainLayout,`/`→`/dashboard`。`entry.js` 按域名分:
  - PLATFORM_ROUTES(admin 可见):dashboard/users/plugins/platforms/roles/menus/logs。
  - TENANT_ROUTES(mychat 可见):conversations/leads/workorders/analytics/aggregate/settings。
  - `defaultPath`:**mychat → `/conversations`**;admin → `/dashboard`。

### "租户管理"页:**没有**
- 现"用户管理"(Users.vue, `user:list`)管的是 users 账号(无租户维度);"平台管理"(Platforms.vue)管全局平台字典。
- 加"租户管理"应放 **admin(平台入口)**,与 Users/Platforms 平级(系统设置组或独立菜单),超管录入企业主体。

### mychat 首页:**当前无首页 + Dashboard 是 chat_rpa 残留**
- mychat 登录后 `defaultPath=/conversations`,**直接进会话中心,没有"首页"**;且 `/dashboard` 属 PLATFORM_ROUTES,**被 entry.js 过滤,mychat 根本看不到 Dashboard**。
- **Dashboard.vue 现状 = chat_rpa 残留**(W15 已提):欢迎卡 + 4 统计卡(用户总数/授权插件/今日消息/在线设备)+ **插件更新下载** + **运行质量监控**(成功率/AI 调用/**关键词命中**/**转人工**/平均响应时长 —— 这些是**自动回复时代死指标**,chatsift 只读无转人工/关键词回复);`roleLabel` 还用 `role===9`。
- **离"mychat 首页(主体信息 + 插件下载 + 企业级/员工级看板)"的差距**:
  1. mychat 当前**无首页**(直进会话)→ 需新增 mychat 专属首页路由 + 改 `defaultPath`/`entry.js` 归类。
  2. 现 Dashboard 是 **admin 视角 + chat_rpa 死指标**,**不能直接复用**,需重做:企业主体(来自新 tenants 表)+ 员工数 + 资产看板(企业级 / 按登录员工客服账号的员工级)。
  3. **可复用**:插件下载组件(`getPluginUpdate`/`downloadPluginZip` 已有,Dashboard `:132,211`)。

## 6. 关键发现汇总 + 待 Chase/Claude 定的点

### 关键发现
1. **租户改造面小而集中**:`tenantId()` 单点 + 登录链路 + schema + 清库,**无历史数据迁移**(生产可清空)。低风险。
2. **Dx3 是最大缺口**:客服账号**零实体**,对话/线索/工单**全不挂**客服账号,`conversation_id` 不含账号维度 → 资产原点要从头建(service_accounts 表 + 各业务表加 service_account_id + 合成键纳入账号)。
3. **插件已能抓登录客服账号名**(`accountNickname`),但只作文本兜底、未独立上报;**账号标识只有昵称文本、无稳定 UID** —— 与 M1 同类困境,是"能否自动建稳定归属"的关键未知。
4. **角色体系只有 is_super 两档**,缺"租户管理员 vs 客服"的租户内分层;role/role_id 双轨待统一;data_scope 不直接表达"按客服账号"过滤。
5. **platforms/platform_pages 是全局字典、无 tenant**;`conversations.platform(_page)` 只是字符串、不外键。资产层级"租户>平台>页面"要定复用策略。
6. **mychat 无首页**(直进会话),Dashboard 是 chat_rpa 残留死指标,需重做。

### 待定点(Q# 临时编号,本轮有效)
- **Q1(最关键)**:客服账号"原点"用什么做**稳定键**?(a)昵称文本(不稳/可重名) (b)插件去抓更稳的账号 UID(需 W17/M1 式真机 DOM 调研确认能否抓到) (c)接受昵称 + 人工校正。**这决定自动建归属能不能落地。**
- **Q2**:资产层级"租户>平台>页面"——复用现有**全局** platforms/platform_pages 字典(客服账号带 platform/page 外键引用)?还是给每租户建平台/页面实例?
- **Q3**:员工"只看自己客服账号资产"的数据过滤走哪条?扩 `data_scope` 维度,还是新增"员工↔客服账号"分配表 + 查询按分配的账号集过滤?(后者更贴多对多模型)
- **Q4**:角色清洗时是否一并统一 `role`(1/9)↔`role_id` 双轨为单一口径(并修 Dashboard `role===9`)?
- **Q5**:清库重建的范围与时机(生产无真实数据,建模可干净,但需明确"清哪些库/何时清/test 同步")。
