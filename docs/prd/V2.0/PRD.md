## 1. 项目目标与范围

### 1.1 目标

为抖音、小红书、淘宝、美团等 6 个电商平台的客服团队提供 AI 辅助客服系统，承接标准化售前售后问答，减轻人工负担、提升响应效率。

- **成功标准**：节省人力、提升效率。本期不以「效果优于人工」或「完全无人化」为目标。
- **定位**：AI 主力承接 + 人工在岗辅助。人工保留账号登录维持、复杂会话兜底、质量监督职能。

### 1.2 本期范围

| 模块 | 本期 | 说明 |
|---|---|---|
| A 消息抓取引擎 | ✅ | Chrome 扩展形态 |
| B AI 回复引擎 | ✅ | 含上下文管理与用户画像 |
| C 人工兜底 | ✅ | 转人工触发 + 企业微信 webhook 通知，无人工后台开发 |
| D 知识库迭代闭环 | ⏳ 二期 | 见 §7，本期预留数据埋点 |
| E 数据复盘后台 | ⏳ 二期 | 见 §7，本期预留数据埋点 |

### 1.3 平台策略

- 架构按**多平台通用**设计：平台差异收敛到「平台适配层」（PlatformAdapter）。
- 本期只细化并落地**抖音来客**适配（含抖音私信 + 客服接待两个场景），作为首个适配层。
- 其余 5 平台二期按相同适配接口扩展，核心引擎不改。

## 2. 系统形态与总体架构

### 2.1 形态

Chrome 浏览器扩展（Manifest V3）。客服本人登录浏览器，扩展在已登录的真实页面环境内运行，做会话检测与自动回复。

不采用 Playwright / Selenium 自动化或指纹浏览器——本项目是人工登录 + 插件辅助，自动化登录会引入风控风险，且非必要。

### 2.2 总体架构

```
┌─────────────────────── Chrome 扩展（客服浏览器内）───────────────────────┐
│                                                                          │
│  Content Script（注入平台页面）                                          │
│   ├── 模块 A：消息抓取引擎                                                │
│   │     SessionDetector → SessionParser → DiffEngine → SessionQueue       │
│   │     LoginMonitor / DOMValidator / PlatformAdapter                     │
│   │                                                                      │
│   ├── 模块 C：人工兜底（前端部分）                                        │
│   │     兜底关键词拦截 / 转人工提示语注入                                 │
│   │                                                                      │
│  Background Service Worker                                                │
│   ├── 模块 B：AI 回复引擎调度                                             │
│   │     上下文组装 → 调用后端 → 回复下发                                  │
│   ├── 模块 C：转接包组装 → 推送企业微信 webhook                           │
│   └── 与后端通信、本地存储管理                                            │
│                                                                          │
└──────────────┬──────────────────────────────────┬────────────────────────┘
               │ HTTPS                            │ HTTPS POST
   ┌───────────┴───────────────┐      ┌───────────┴────────────┐
   │        后端服务            │      │   企业微信群机器人      │
   │  ├── AI 回复 API（Claude） │      │   webhook（转人工通知） │
   │  ├── 知识库检索服务        │      └─────────────────────────┘
   │  ├── 用户画像 / 上下文存储 │
   │  └── 数据存储（会话/消息/日志）
   └────────────────────────────┘
```

> 说明：扩展负责「页面侧的检测与执行」，后端负责「AI 调用、数据存储」。AI 调用放后端，避免在扩展内暴露 API Key。转人工不开发后台界面——直接 POST 到企业微信群机器人 webhook，人工收到群消息后自行用原平台后台接待该用户。

### 2.3 模块职责边界

| 模块 | 运行位置 | 职责 | 不负责 |
|---|---|---|---|
| A 消息抓取 | Content Script | 检测新消息、解析会话、维护队列、执行回复下发到页面 | 不生成回复内容、不判断是否转人工 |
| B AI 回复 | Service Worker + 后端 | 组装上下文、调用 AI、知识库检索、生成回复文本、维护画像 | 不接触页面 DOM |
| C 人工兜底 | Content Script + Service Worker | 判断是否转人工、组装转接包、推送企业微信 webhook | 不做常规回复生成、不开发人工后台 |

## 3. 核心业务流程（端到端）

单条消息从进入到闭环的完整链路：

```
[1] SessionDetector 检测到会话列表 DOM 变化
        ↓
[2] SessionParser 重新解析会话列表 → 生成 SessionSnapshot
        ↓
[3] DiffEngine 与历史快照 Diff → 识别"真正的新消息"
        （四信号叠加：红点变化 + 末条消息变化 + 时间戳变化 + 未处理）
        ↓
[4] 命中的会话进入 SessionQueue（串行，防串号/重复回复）
        ↓
[5] 出队 → DOMValidator 校验（DOM 稳定、输入框存在、会话正确）
        ↓
[6] 读取该会话全部未读消息 → 提交模块 B
        ↓
[7] 模块 C 前置检查：是否命中兜底关键词/转人工词
        ├── 命中 → 转人工流程（§5），AI 不回复该会话
        └── 未命中 → 继续
        ↓
[8] 模块 B：组装上下文（会话内 + 历史画像）→ 知识库检索 → 调用 AI 生成回复
        ↓
[9] 回复文本回传扩展 → 模拟真人输入节奏填入输入框 → 发送
        ↓
[10] 确认发送成功 → 标记会话已处理 → 更新 SessionSnapshot
        ↓
[11] 会话静默 ≥1h 或每日零点 → 生成上下文压缩包 + 更新用户画像
```

### 3.1 多会话调度规则（来自调研发现 1）

SessionQueue 出队策略，不是纯 FIFO：

- 处理 1 条最新消息后，穿插处理 1 条积压最久的消息（时间轮转），避免队尾会话饿死。
- 单会话设等待上限：超过 10 分钟未处理的会话提升优先级。
- 单会话处理设超时（建议 1-2 分钟）：超时则标记待办、释放队列，不阻塞后续。

### 3.2 会话完整性规则（来自调研发现 2）

- 一个会话的全部未读消息必须合并处理、一次性回复（见 §3 步骤 6、调研发现 3）。
- 不依赖平台红点判断会话是否处理完——以系统内 SessionSnapshot 的「已处理」状态为准。

## 4. 模块间接口约定

模块解耦的关键。三个子文档须遵守以下接口契约。

### 4.1 模块 A → 模块 B：回复请求

A 检测到需回复的会话后，向 B 提交：

```json
{
  "session_id": "string，会话唯一标识",
  "platform": "douyin | xiaohongshu | taobao | meituan",
  "agent_id": "string，所属客服标识",
  "user": { "nickname": "string", "platform_user_id": "string" },
  "unread_messages": [
    { "msg_id": "string", "text": "string", "timestamp": "ISO8601" }
  ],
  "scene": "presale | aftersale"
}
```

### 4.2 模块 B → 模块 A：回复结果

```json
{
  "session_id": "string",
  "reply_text": "string，待发送的回复内容",
  "reply_source": "kb_hit | ai_generated",
  "status": "ok | failed",
  "fail_reason": "string，status=failed 时填"
}
```

### 4.3 模块 C 拦截接口：转人工信号

C 在流程步骤 [7] 介入。A 在调用 B 之前先经 C 检查：

```json
// C 的返回
{
  "session_id": "string",
  "need_handover": true,
  "trigger_type": "complaint_keyword | user_request | ai_uncertain",
  "action": "stop_ai_reply"
}
```

`need_handover=true` 时，A 跳过模块 B，触发转人工流程（§5）。

### 4.4 状态约定

会话状态机（SessionSnapshot 中维护）：

```
new（检测到新消息）
  → queued（已入队）
  → processing（出队处理中）
  ├─→ ai_replied（AI 已回复）→ done（已闭环）
  ├─→ handover（已转人工，终态）
  └─→ todo（超时挂起，待跟进）
```

状态说明：

- `handover` 为**终态**——会话一旦转人工，AI 永久不再接管该会话，包括该用户的后续咨询（采用方案一）。
- `done`、`todo` 在会话结束结算（静默 ≥1h 或每日零点）时生成上下文压缩包；`handover` 会话不参与 AI 接管，但仍记录日志供二期统计。

## 5. 人工兜底（模块 C 完整规格）

模块 C 逻辑较轻，不单独成文，完整规格在此。

### 5.1 触发条件

会话在主流程步骤 [7] 经模块 C 检查，命中以下任一条件即触发转人工：

| 触发类型 | trigger_type | 说明 |
|---|---|---|
| 命中兜底/投诉关键词 | `complaint_keyword` | 词表来自已有配置入口，运行时读取，不在代码写死 |
| 用户明确要求转人工 | `user_request` | 命中"转人工""人工客服"等词，同属配置词表 |
| AI 判断无法处理 | `ai_uncertain` | 模块 B 返回低置信或无法回答时回传 |

> 词表由业务方已有的配置入口维护，模块 C 只负责「读取配置 + 匹配」。黑名单词同理。

### 5.2 转人工动作

1. **提示用户**：扩展向当前会话用户发送提示语（如"我将请专员协助您，请稍等"），提示语文案可配置。
2. **暂停 AI**：该会话状态置为 `handover`（终态），AI 永久不再接管该会话。
3. **推送通知**：Service Worker 组装转接包，POST 到企业微信群机器人 webhook。

### 5.3 转接包（webhook 推送内容）

POST 到企业微信群机器人 webhook URL，消息体采用企业微信 markdown 消息格式，内容包含：

```
- 平台 + 客服：哪个平台、哪个客服的会话
- 用户昵称
- 最后发送时间
- 上下文摘要：对话核心内容，≤300 字
- 用户画像标签：如"价格敏感型""投诉历史"
- 触发类型：complaint_keyword / user_request / ai_uncertain
```

webhook URL 为可配置项。人工收到群消息后，**自行打开对应平台后台接待该用户**——系统不提供接管界面，职责到「发出通知」为止。

### 5.4 隔离与恢复规则

- **隔离**：转人工仅作用于该会话，同客服其他会话、其他平台会话 AI 照常处理。
- **恢复**：不恢复。`handover` 为终态，该会话及该用户后续咨询均不再由 AI 接管（方案一）。
- **多客服可见**：同一用户被多个客服接待过时，各客服可见完整历史对话（数据层支持，展示依赖已有管理后台）。

### 5.5 webhook 推送失败处理

webhook POST 失败时，需重试（建议 3 次，指数退避）；仍失败则记录告警日志，并通过扩展桌面通知提示客服「转人工通知发送失败，请手动关注该会话」。不可静默失败。

## 6. 数据模型（核心实体）

本期需落地的核心数据表/结构（字段为最小集，子文档可扩展）：

### 6.1 会话 Session

```
session_id        会话唯一标识
platform          平台
agent_id          所属客服
platform_user_id  平台侧用户标识
status            会话状态（见 §4.4）
scene             presale | aftersale
created_at / updated_at
```

### 6.2 消息 Message

```
msg_id            消息唯一标识
session_id        所属会话
direction         inbound（用户）| outbound（客服/AI）
text              消息内容
sender_type       user | ai | human_agent
reply_source      kb_hit | ai_generated | human（仅 outbound）
hit_blacklist     bool，是否触发黑名单词
hit_handover      bool，是否触发转人工词
timestamp
```

> 注：reply_source、hit_blacklist、hit_handover 等字段本期即埋点，供二期模块 E 统计使用。

### 6.3 用户画像 UserProfile（细节见 PRD-B）

```
platform_user_id
tags              标签数组（价格敏感型/投诉历史/高意向/售后履约 等）
context_summary   最近一次上下文压缩包
notes             用户备注
updated_at
```

### 6.4 SessionSnapshot（细节见 PRD-A）

```
session_id
last_message_text
last_timestamp
unread_count
processed         bool
snapshot_at
```

## 7. 二期占位说明

本期不实现，但本期需为其预留数据埋点，避免二期返工。

### 7.1 模块 D：知识库迭代闭环

- 每日零点 AI 总结当日对话，生成知识库优化建议。
- 人工审核通过后入库。
- **本期预留**：Message 表完整记录所有对话，供二期总结取数。

### 7.2 模块 E：数据复盘后台

- 按 平台 → 客服 → 会话 三层聚合。
- 支持按用户、时间、人工接管状态筛选。
- 统计维度：回复来源、会话状态、是否触发黑名单/转人工词。
- **本期预留**：§6 数据模型中的 reply_source、hit_blacklist、hit_handover、status 等字段本期即写入。

## 8. 非功能性要求

| 项 | 要求 |
|---|---|
| 风控 | 模拟真人输入节奏、操作间隔随机化；被动监测登录态，不主动刷新试探 |
| 登录态 | 掉线即桌面通知人工重登；会话快照持久化，重登后 Diff 找回掉线期间消息 |
| 抗 DOM 改版 | 选择器配置化集中管理，支持 CSS/XPath/文本匹配；失效即告警并记录 DOM 快照 |
| 稳定性 | 任何环节不静默失败；MutationObserver 失效降级到轮询，轮询异常降级到人工告警 |
| 安全 | AI API Key 仅存后端，扩展不接触 |
| 成本 | 主力问答用 Sonnet 4.6，离线任务用 Haiku 4.5；启用 Prompt Caching |
