# W12 设计说明:准实时时序 + 后台主动提醒

> **周次**:W12(后续路线图阶段三,收官)
> **范围**:把链路四段延迟控制住 + 补上后台主动提醒(关键缺口),达成”留资后 1-5 分钟内联系”
> **关联**:W4/W5 采集、W2 analyzer、W11 诊断颜色、后续路线图
> **目标值**:正常 30-45 秒、最坏 ~1 分钟(满足 1-5 分钟且有余量)
> **本周不做**:SSE/WebSocket 服务端推(轮询够用,过度设计)、改诊断逻辑(W11已做)

-----

## 0. 四段延迟与本周目标

客户发预约信息 → 客服在后台看到这条高意向线索,穿过四段:

```
①采集延迟  插件多久"看到"新消息       目标 ~10秒
②上报延迟  采集后多久打包上报         目标 ~15秒
③分析延迟  服务端多久跑完分析         规则毫秒/LLM 1-10秒
④呈现延迟  分析完到客服在界面看到     目标 ~30秒(轮询)
                                    ────────────
                                    合计 正常30-45秒,最坏~1分钟
```

**①②③ 是优化(调参数),④ 是从零补(后台现在没有主动提醒,是关键缺口)。**

前提条件(写进用户手册):**插件运行时抖音页面必须保持前台打开**,最小化/切后台标签会被浏览器休眠,DOM 不刷新就采不到——这是 W4 竞品调研就确认的硬约束,准实时的前提。

-----

## 1. ① 采集节流

插件 MutationObserver 监听 DOM 变化。设计:

- 触发后**节流 ~10 秒再采集**(不是 DOM 一变就立即采)
- 原因:抖音消息常分多个 DOM 节点陆续渲染,等几秒让它渲染完整,避免采到半条消息
- 节流期内多次触发只采一次,减少重复处理

实现:在 W4 的采集触发处加节流(debounce/throttle ~10s)。这碰 W4 采集代码(C类),小心不要破坏现有采集逻辑,只加节流包装。

-----

## 2. ② 上报触发

W4 的 EventQueue 已是批量结构。明确它的 flush 触发条件:

```
满足任一条件就上报:
  - 攒满 N 条(如 10 条)
  - 距上次上报满 ~15 秒
先到先发
```

- 不是单条即发(太频繁),也不是攒太久(吃掉 SLA)
- 确认 EventQueue 现在的 flush 是怎么触发的(W4 建的,可能已有定时 flush,也可能只在攒满时 flush)。如果没有定时 flush,补一个 ~15 秒定时器

-----

## 3. ③ 分析时序与优先级

analyzer 是串行队列(W2)。正常规则分析毫秒级,但 W8 接了 LLM——规则没命中要调 DeepSeek 的,一次 1-10 秒。

**风险**:大量需要 LLM 的消息涌入时,串行队列积压,后面的消息等前面 LLM 调用完,分析延迟从秒级涨到分钟级,吃掉 SLA。

**本周的处理(轻量,不重构队列)**:

- 评估当前队列在真实量下会不会积压(W8 的省钱约束已经让 LLM 调用量不大——规则能判的不调)
- 如果会积压:给”已判出是预约意图/高意向”的消息**更高分析优先级**(优先处理高意向,让最该快的最快)。实现可以是简单的双队列(高优先 + 普通)或排序,不要重构整个 analyzer
- 如果不会积压(LLM 调用量本就小):本周不动队列,只记录观察

这一段先以”评估 + 必要时加优先级”为度,不做重队列改造(那是未来的事)。

-----

## 4. ④ 后台主动提醒(本周核心,从零补)

这是达成 SLA 的命门。现在后台是静态页面,客服不手动刷新就永远看不到新线索——前三段再快也白搭。

### 4.1 用轮询,不用 SSE/WebSocket

后台前端定时轮询,问服务端”有没有新的高意向线索”。

- 轮询间隔 ~30 秒(满足 SLA 且不给服务端太大压力)
- 不用 SSE/WebSocket:那要服务端长连接支持,复杂度高,对”1-5分钟”SLA 是过度设计。轮询 30 秒足够。未来要秒级再升级

### 4.2 提醒什么

复用 W11 的诊断颜色,提醒”值得马上跟的新线索”:

```
轮询接口:GET /api/v1/leads/recent?since=<上次轮询时间>&min_level=high
  返回:since 之后新产生/更新的高意向线索(lead_level=high 或 诊断红/绿完整预约)
```

提醒优先级建议:

- 新的**完整有效预约**(6字段全valid,诊断绿)→ 最值得马上跟,重点提醒
- 新的**高意向线索**(lead_level=high)
- (可选)新的红色硬伤(如投诉)→ 也提醒,因为投诉要快速处理

### 4.3 提醒形式

- 后台顶部/角落红点 + 数字(N 条新线索待跟进)
- 可选:提示音(新高意向线索来时响一声,客服在忙别的也能注意到)
- 点提醒 → 跳到线索中心,筛选出这些新线索

### 4.4 已读/未读

- 提醒的线索有”未跟进”状态,客服处理后(改 status 为 following)不再重复提醒
- 轮询用 since 时间戳,只拿增量,不重复提醒老线索

## 5. 时序串起来(端到端)

```
客户发"约车,刘思奇,上海,明天3点,13800138000,普陀区镇坪路666号,轿车"
  ↓ ①插件节流10秒后采集
  ↓ ②EventQueue 15秒内 flush 上报
  ↓ ③analyzer 分析(规则抽字段+有效性,可能调LLM补) ~数秒
     → 6字段全valid → 高意向完整预约 lead
  ↓ ④后台30秒轮询拿到这条新的完整预约 → 红点+提示音
客服看到提醒(总耗时正常30-45秒)→ 点开 → 看到诊断绿色完整预约 → 立即电话联系
```

整个链路在 1 分钟内,远在”5 分钟”SLA 内,且客户的预约信息是经 W10 验证有效的、W11 诊断清晰的。

-----

## 6. 验证(W12 结束应看到)

```
1. 采集节流:连续 DOM 变化,采集不是每次都触发,节流~10秒一次
2. 上报:EventQueue 满N条或~15秒 flush 一次(查上报日志间隔)
3. 后台轮询:挂着后台不动,新线索进来后~30秒内出现红点提醒
4. 提醒内容:新的完整预约/高意向线索被提醒,普通咨询不打扰
5. 端到端计时:制造一条预约消息,记录"客户发出→后台提醒出现"总耗时,应在1分钟左右
6. 已读:处理线索(改following)后不再重复提醒
7. 回归:时序改动不影响采集准确性(W4/W5)、分析正确性(不漏采、不重复)
```

-----

## 7. 风险与注意

第一,**采集节流碰 W4/W5 采集代码(C类)**:只加节流包装,不破坏现有采集逻辑。改完重跑 W4/W5/W6.5 验收,确认不漏采、不重复采、会话仍正确合并。

第二,**④后台提醒是核心**,不是①②③的优化。即使前三段不动,补上④也能大幅改善”客服不知道有新线索”。如果时间紧,①②③可保守(用现有参数),④必须做。

第三,**轮询不用 SSE**:轮询 30 秒对 1-5 分钟 SLA 足够,SSE 是过度设计,本周不做。

第四,**分析优先级先评估再决定**:LLM 调用量本就被省钱约束压低,可能根本不积压。先评估,真积压才加优先级,不预先重构队列。

第五,**提醒不打扰**:只提醒值得马上跟的(完整预约/高意向/投诉),普通咨询不提醒,否则客服被无效提醒淹没反而忽略。

第六,**前提是页面前台**:准实时依赖抖音页面保持前台打开(浏览器休眠后台标签),这写进用户手册,不是代码能解决的,要让客服知道。

第七,**端到端 SLA 验证**:不只验单段,要制造真实预约消息、计时”发出→提醒”全程,确认 1 分钟左右。这是 W12 真正的成败标准。
