# W20 PRD:客服账号采集权与查看权治理

> **解决什么**:把"谁负责采集某个客服账号"和"谁可以查看该账号数据"拆开治理,并解决首次客服账号录入成本高、名称不一致、多人多设备重复采集的问题。
> **核心决策**:一个客服账号同一时间只有一个采集负责人;查看权可以分配给多人;首次账号由系统自动发现,进入待确认,当前采集人获得临时采集权,租户管理员确认后转正式采集权。
> **性质**:B/C 类边界。PRD 本身不改代码;后续若涉及 schema、权限契约、采集入库拦截、租约表,DEV 必须先出技术方案 + schema diff,过 Claude + 用户审后再实现。

---

## 1. 背景

以抖音私信为试点时,实际使用关系不是"一个租户一个账号一台电脑",而是:

- 一个租户下有多个员工。
- 一个员工通常一台电脑,少数场景有两台电脑。
- 一个员工可能负责多个抖音客服账号。
- 同一台电脑可能有多个浏览器、多个浏览器 Profile、多个页签。
- 一个抖音客服账号原则上只由一个员工负责采集,但租户管理员可以重新分配。

如果只靠插件采集自动入库,会出现三类问题:

- 账号归属不清:谁先采、谁能采、谁能看没有系统事实。
- 重复采集:同一客服账号、同一会话被多个设备/浏览器/页签同时写入。
- 首次录入困难:纯人工录入容易录错 `account_biz_id`、账号名称、坐席昵称,启动成本高。

W20 的目标是先建立客服账号治理,再让采集链路在这个治理框架下运行。

---

## 2. 目标

### 2.1 产品目标

1. **采集权单人化**
   - 一个客服账号同一时间只有一个采集负责人。
   - 采集负责人可以由租户管理员重新分配。
   - 非采集负责人即使有查看权,也不能采集入库。

2. **查看权多人化**
   - 查看权与采集权分离。
   - 租户管理员可以把某个客服账号的数据查看权分配给多个员工。
   - 租户管理员默认可查看本租户全部客服账号数据。

3. **首次账号自动发现 + 管理员确认**
   - 不要求管理员首次手工录入全部客服账号。
   - 插件首次识别到未知客服账号时,系统自动创建"待确认账号"。
   - 当前采集员工获得临时采集权。
   - 租户管理员确认后,临时采集权转为正式采集权。

4. **多设备/多页签采集冲突可控**
   - 登录可以多设备并存。
   - 采集需要按客服账号、会话、采集实例做冲突检测。
   - 同账号同会话多实例采集默认阻止或强提醒。

### 2.2 非目标

- 不做平台账号密码托管。
- 不做抖音登录自动化。
- 不做绕过抖音风控。
- 不在 W20 做完整云端消息对账。
- 不把"登录多设备"等同于"采集冲突"。

## 3. 核心概念

### 3.1 客服账号

客服账号是租户的数据资产原点。

```
tenant_id
platform
platform_page
account_biz_id
account_nickname
```

其中:

- `account_biz_id`:平台侧稳定业务账号 ID,优先从抖音 URL `accountId` 识别。
- `account_nickname`:页面展示名称/坐席昵称,用于展示和人工校正,不作为唯一可信身份来源。

### 3.2 采集权

采集权表示"谁可以把该客服账号的数据写入系统"。

规则:

- 一个客服账号同一时间只有一个采集负责人。
- 采集负责人必须是本租户员工。
- 租户管理员可以重新分配采集负责人。
- 采集权变更后,旧负责人插件继续采集时应被拦截或强提醒,不应继续静默入库。

### 3.3 查看权

查看权表示"谁可以在后台查看该客服账号的数据"。

规则:

- 一个客服账号可以分配给多个查看人。
- 查看权不包含采集权。
- 有查看权的员工不能因此启动采集。
- 租户管理员默认拥有本租户全部查看权。

### 3.4 临时采集权

临时采集权用于首次自动发现账号。

规则:

- 仅在客服账号处于 `pending` 待确认状态时存在。
- 当前首次采集员工获得临时采集权。
- 临时采集权不是永久归属。
- 租户管理员确认后,可以把正式采集权给当前员工,也可以改分配给其他员工。

## 4. 账号生命周期

### 4.1 状态

| 状态 | 含义 | 是否允许采集 | 谁可操作 |
|---|---|---|---|
| pending | 系统首次发现,待管理员确认 | 仅临时采集人可采 | 租户管理员确认/改分配 |
| active | 已确认正式账号 | 仅正式采集负责人可采 | 租户管理员重分配/停用 |
| disabled | 已停用 | 不允许采集 | 租户管理员恢复/查看历史 |

### 4.2 首次发现流程

```
员工打开抖音私信
插件识别 account_biz_id / account_nickname
服务端发现该账号未录入
创建 pending 客服账号
当前员工获得临时采集权
允许当前员工继续采集
租户管理员后台看到待确认账号
管理员确认采集负责人和查看人
账号转 active
```

### 4.3 已确认账号采集流程

```
插件识别当前客服账号
服务端校验该员工是否为采集负责人
是:允许采集入库
否:拒绝入库并提示联系管理员重新分配采集权
```

### 4.4 采集权重分配流程

```
租户管理员打开客服账号管理
选择新的采集负责人
系统记录 assigned_by / assigned_at / old_collector / new_collector
旧负责人后续 heartbeat 或上传时收到权限变更提示
新负责人可采集
查看权不随采集权自动变化,由管理员单独配置
```

## 5. 权限规则

### 5.1 角色规则

| 角色 | 采集权 | 查看权 | 管理权 |
|---|---|---|---|
| 租户管理员 | 默认不采集,可给自己或他人分配采集权 | 默认看本租户全部 | 管理客服账号、采集权、查看权 |
| 客服员工 | 只采自己负责的客服账号 | 看被分配查看权的客服账号 | 无管理权 |
| 平台内部用户 | 不参与采集 | 默认不看租户业务数据,除非显式进入租户视角 | 平台级管理 |

### 5.2 采集权与查看权组合

| 场景 | 是否允许 |
|---|---|
| 员工是采集负责人,无显式查看权 | 允许采集;默认应拥有该账号查看权 |
| 员工有查看权,不是采集负责人 | 允许查看,不允许采集 |
| 员工既无采集权也无查看权 | 不允许采集,不允许查看 |
| 租户管理员重新分配采集权 | 允许 |

### 5.3 默认策略

- 采集负责人默认自动拥有该客服账号查看权。
- 查看人不会自动获得采集权。
- 租户管理员默认拥有全部查看权,但不自动成为采集负责人。

## 6. 多设备与采集冲突

### 6.1 登录层

员工账号登录 chatsift 时:

- 允许多设备并存。
- 新设备登录时强提醒:"该账号已在其他设备登录"。
- 记录设备、浏览器、IP、登录时间、最后活跃时间。
- 第一阶段不做"继续登录踢掉另一侧"。

### 6.2 采集层

采集层按采集实例治理,而不是按登录会话治理。

采集实例至少包含:

```
tenant_id
employee_id
device_id
browser_profile_id
tab_id
platform
platform_page
account_biz_id
conversation_id
last_seen_at
status
```

冲突 key:

```
账号级观察:
tenant_id + platform + platform_page + account_biz_id

会话级冲突:
tenant_id + platform + platform_page + account_biz_id + conversation_id
```

### 6.3 冲突处理规则

| 场景 | 处理 |
|---|---|
| 同员工多设备登录 chatsift | 允许,强提醒和审计 |
| 同采集负责人多设备打开同一客服账号 | 提醒 |
| 同采集负责人多实例采同一会话 | 默认阻止或强提醒 |
| 非采集负责人打开已归属客服账号 | 提示无采集权,不入库 |
| 非临时采集人打开 pending 账号 | 提示该账号正在待确认,不允许抢占 |
| 管理员重分配后旧负责人继续采 | 提示采集权已变更,不入库 |

## 7. 后台页面需求

### 7.1 客服账号管理

面向租户管理员。

列表字段:

- 平台
- 页面
- `account_biz_id`
- 客服账号名称/坐席昵称
- 状态:待确认/已启用/已停用
- 当前采集负责人
- 查看人数
- 首次发现人
- 首次发现时间
- 最近采集时间

操作:

- 确认待确认账号
- 修改展示名称
- 分配/重分配采集负责人
- 分配查看人
- 停用/恢复账号
- 查看采集冲突记录

### 7.2 待确认账号提醒

租户管理员首页或客服账号管理页应有待办入口:

- 待确认账号数量
- 账号首次发现人
- 首次发现时间
- 建议采集负责人
- 一键确认
- 改分配后确认

### 7.3 员工侧提示

插件或 mychat 侧需要明确提示:

- 账号首次发现,等待管理员确认。
- 你拥有临时采集权。
- 你不是该账号采集负责人。
- 该账号采集权已被管理员转移。
- 同一会话已有其他采集实例运行。

## 9. 验收标准

### 9.1 首次发现

- 未录入抖音客服账号首次采集时,系统自动创建 pending 账号。
- pending 账号带有 `account_biz_id`、识别到的名称、首次发现人、首次发现时间。
- 首次采集员工获得临时采集权。
- 租户管理员可以确认该账号,并指定正式采集负责人。

### 9.2 采集权

- active 账号只有正式采集负责人可以采集入库。
- 非采集负责人上传数据时被拒绝,并返回明确错误。
- 管理员重分配采集权后,旧负责人不再能采集入库。
- 采集负责人默认拥有该账号查看权。

### 9.3 查看权

- 同一客服账号可以分配多个查看人。
- 有查看权但无采集权的员工可以查看数据,不能采集。
- 无查看权员工看不到该账号数据。
- 租户管理员可查看本租户全部账号数据。

### 9.4 多设备冲突

- 同一员工多设备登录允许并存,有提醒和审计。
- 同一客服账号同一会话被多个采集实例同时采集时,系统能识别并提示。
- 非临时采集人不能抢占 pending 账号。
- 冲突事件可在后台审计中查到。

### 9.5 回归

- 抖音私信试点采集链路可继续跑通。
- W17 position/message_id 逻辑不被 W20 直接改动。
- W19 租户/客服账号资产模型不被破坏。
- 后台无发送入口,仍保持只读诊断定位。

## 10. 分阶段建议

### 阶段 A:产品规则与数据方案

- 固化采集权单人、查看权多人。
- 明确 pending/active/disabled 生命周期。
- DEV 出技术方案,列 schema diff、接口变更、受影响调用点。

### 阶段 B:首次发现与确认

- 插件识别未知客服账号。
- 服务端创建 pending 账号。
- 当前员工获得临时采集权。
- 租户管理员确认账号和采集负责人。

### 阶段 C:采集权/查看权分离

- 后台支持采集负责人单选。
- 后台支持查看人多选。
- 服务端采集入库前校验采集权。
- 后台查询按查看权过滤。

### 阶段 D:采集实例冲突检测

- 插件生成设备/实例标识。
- 服务端维护采集 heartbeat。
- 同账号同会话多实例采集时提醒或阻止。
- 记录冲突审计。

### 阶段 E:验收与试点回归

- 用抖音私信试点账号完成首次发现、确认、重分配、查看权、多设备冲突全流程验收。
- 输出 W20 acceptance report。

## 11. 与 W17/W19 的关系

- W19 已建立租户资产模型和客服账号归属基础,W20 在此基础上细化"采集权"和"查看权"。
- W17 阶段二云端对账不作为 W20 前置。W20 先从源头减少多实例重复采集。
- 如果 W20 的冲突审计证明同账号同会话多实例采集高频且造成真实数据错乱,再启动 W17 阶段二完整云端对账。

---

## 12. 待 Claude/用户确认点

1. pending 账号阶段是否允许临时采集数据进入正式业务表,还是先进入待确认区。
2. 同一采集负责人多设备采同一账号但不同会话时,第一阶段是只提醒还是限制并发数量。
3. 同账号同会话多实例采集时,默认"阻止继续"还是"强提醒后允许继续"。
4. 查看权是否支持按客服账号分配即可,还是需要进一步支持按会话/工单/线索类型分配。
