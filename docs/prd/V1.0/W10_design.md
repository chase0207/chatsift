# W10 设计说明:字段有效性校验

> **周次**:W10(后续路线图阶段一,MVP 之后)

## 0. 为什么要有效性(背景)

之前 completeness 只看字段**非空**。但非空 ≠ 有效:

- 联系方式填”回头给你” → 非空,但无法联系
- 上车地址填”市区” → 非空,但不是具体点,司机找不到
- 时间填”改天” → 非空,但没法排班

对”准实时催单”的租车业务,无效信息等于没信息。W10 让机器判定字段**有效性**,只有有效的才算数。

-----

## 1. 各字段的有效性标准

|字段                   |有效标准                       |判定方式                          |
|---------------------|---------------------------|------------------------------|
|contact(联系方式)        |是真实手机号或微信号                 |规则:手机号正则 `1[3-9]\d{9}`;微信号格式  |
|name(姓名)             |像真实人名,非”不知道/老板/问问”/纯数字/表情  |规则挡明显无效 + AI 判”像不像真名”         |
|city(城市)             |真实城市名                      |规则:城市词表                       |
|time(时间)             |能定位到具体日期+小时,非”改天/有空/最近”    |规则解析常见格式 + AI 处理相对时间(这周六)和模糊判断|
|pickup_location(上车位置)|具体的点(门牌号级),非”市区/某区/某条路”这种片区|主要靠 AI(规则难判”点vs片”)            |
|car_type(车型)         |真实车型(轿车/SUV/商务/7座等)        |规则:车型词表                       |

### 1.1 有效性三态

每个字段的有效性不是简单 true/false,用三态更准:

```
valid    有效(规则或AI确认有效)
invalid  无效(规则或AI确认无效,如"市区"当地址)
unknown  未校验(配额耗尽时AI那部分没跑,或无法判断)
```

unknown 的意义:配额耗尽降级时,AI 判不了的字段标 unknown(而不是当成 invalid 或报错)。报表/诊断里 unknown 单独显示(如”待核对”),不冤枉也不放过。

-----

## 2. 规则 vs AI 的分工(成本关键)

复用 W8 “规则优先、LLM 兜底、配额受限”。分工:

**纯规则判(免费,不调 AI):**

- contact:手机号正则、微信号格式
- city:城市词表
- car_type:车型词表
- name / time / pickup 的**明显无效**先用规则挡一道(纯数字姓名、“改天”这种时间关键词、空地址)

**规则判不准 → 调 AI(花租户钱,值得):**

- pickup_location 的”点 vs 片”:规则几乎做不了,AI 判
- time 的相对表达转具体日期 + 是否到小时:AI 更准
- name 的”像不像真名”:AI 判

**省钱铁律(和 W8 一致):**

- 规则能确定的(有效或无效)不调 AI
- 只对”规则判不准、且字段非空”的才调 AI(空字段直接 invalid,不浪费 AI)
- 配额耗尽 → AI 那部分标 unknown,规则部分照常
- **有效性结果存库,报表/界面只读不重算**(绝不在看报表时实时调 AI)

-----

## 3. 何时算、存哪里(成本关键)

### 3.1 在分析时算一次,存下来

有效性在 **completeness 抽字段的同时判定并存库**,不在看报表时算。流程:

```
completeness 分析一条会话:
  1. 规则抽字段(W3 已有)
  2. 规则判每个字段有效性(免费)
  3. 规则判不准的非空字段 → 调 AI 判有效性(受配额约束)
  4. 把字段值 + 每个字段的有效性三态 一起存库
```

### 3.2 schema 增量

存每个字段的有效性。两个方案(选 B 更省事):

- 方案A:每字段加一列(name_valid/contact_valid/…)。直观但加 6+ 列
- 方案B(推荐):加一个 JSON 列 `field_validity`,存 `{name:'valid', contact:'invalid', pickup_location:'unknown', ...}`。一列搞定,灵活

存在哪张表:completeness 结果现在存哪(conversations 还是 leads 还是分析快照),field_validity 就跟着存哪,和现有字段值放一起。

## 4. 漏斗预约口径升级(并入 W9 v1.1.0)

W9 funnel 的”预约”判定,一步到位做成有效性:

```
预约 = 6 个字段全部 valid 的会话
  (不是"非空",是"有效"。name=valid AND city=valid AND time=valid
   AND contact=valid AND pickup_location=valid AND car_type=valid)
```

- 留资也升级:留资 = contact 字段 valid(不只是非空,要是有效手机号/微信)
- 仍按实体字段判定,不按 score/stage(W9 v1.1.0 的原则保留)
- 真包含关系仍成立:预约(6字段valid)⊂ 留资(contact valid)⊂ 咨询
- unknown 怎么算:严格起见,unknown 不算 valid(即配额耗尽没校验的,暂不算进预约,显示”待核对”)。这样漏斗只统计”确认有效”的,不虚高

-----

## 5. completeness 评分也跟着有效性走

W6.5 的 completeness_score 是”已填字段数/总数”。W10 后改成”**有效字段数**/总数”:

```
completeness_score = round(valid字段数 / 总字段数 × 100)
```

即只有有效字段才算”已完成”。填了但无效(如地址填”市区”)不计入分子。这样 completeness 反映的是”真正可用的信息完整度”,更贴合业务。

## 7. 风险与注意

第一,**有效性结果必须存库、报表只读**。绝不能在看报表时实时调 AI——漏斗会被反复刷新,实时调 AI 会让租户成本失控。这是 W10 第一铁律。

第二,**改 completeness 引擎(C类)+ schema 增量**,改完重跑 W3/W7/W9 验收。

第三,**配额耗尽降级为 unknown**,不是 invalid、不是报错。AI 判不了就老实标”待核对”,交人工。

第四,**省钱**:规则能判的不调 AI,空字段直接 invalid 不调 AI,只对”非空且规则判不准”的调 AI。

第五,**unknown 不算 valid**:漏斗预约只统计确认有效的,unknown 显示”待核对”单列,不虚高也不漏。

第六,**AI 判有效性的 prompt 要专门设计**:地址判点/片、时间判具体度、姓名判真伪,各有各的 prompt,要让 AI 返回结构化的 valid/invalid + 理由(理由供 W11 诊断显示用)。
