## 1. 背景

v0.6.5 已完成客户端本地态隔离与冷启动 re-align:插件在本地 position 状态缺失时,先向 server 查询已入库消息,再尝试把当前 DOM 可见消息与 server recent 消息对齐。该设计避免了“插件重装/换电脑后从 0 重新编号,导致 position 撞历史”的严重问题。

但生产验收中继续暴露两个问题:

1. 某些会话出现控制台日志:

```text
[LegacyCollector] skip collect: position re-align unavailable {reason: 'realign-no-anchor'}
```

这表示插件已经进入采集链路,但因为当前可见 DOM 消息无法与 server 已有消息建立锚点,为避免重复或错位入库,本轮采集被跳过。

2. 生产库按客户昵称 `go on` 查询发现,部分会话没有 DB 唯一键重复,但存在“同内容、不同 position”的内容级重复:

| 页面 | 会话 | 现象 |
|---|---|---|
| 抖音私信 `private-message` | `go on` | 同一 outbound 卡片内容出现在 position `0,20` |
| 抖音消息接待 `laike-message` | `go on` | `预约`、欢迎语、预约信息模板分别出现在多个 position |

这说明问题不只是“无法采集”,还包括“页面重复 DOM 或采集器重复识别导致同一可见消息被当成多条不同 position 入库”。

W23 的目标是把这两个问题纳入同一条采集可靠性主线:冷启动时不能静默卡死,重复 DOM 不能无诊断地进入正式数据,用户和后台都必须看得见当前状态。

---

## 2. 目标

W23 目标:

1. 让 `realign-no-anchor` 从“控制台内部日志”变成用户可见、后台可诊断的采集状态。
2. 在安全边界内提供 re-align 恢复路径,避免新电脑、新 tab、清 storage、自动切换后的会话长期无法采集。
3. 对“内容级重复入库”建立诊断和治理规则,避免页面重复 DOM 被误认为多条不同消息。
4. 保持 W17 “有几条存几条”的业务原则:真实重复发送的消息必须保留,不能用简单内容去重破坏业务数据。
5. 不引入发送、回复、输入、自动处理能力。

---

## 3. 非目标

W23 不做以下事项:

- 不改 W17 的 message_id / position 基本规则。
- 不用内容 hash 替代 position 做消息身份。
- 不做全平台通用采集重构。
- 不做抖音“消息-消息接待”新页面适配;该任务顺延为 v0.6.9。
- 不修复来客 `NULL-SA` 展示权限问题;该问题另案处理。
- 不改 W20 采集权 / 查看权 / lifecycle 规则。
- 不改 W21 自动切换开关和节奏策略,但 W21 必须消费 W23 的采集状态。
- 不在后台新增发送、回复、输入框或自动回复入口。

## 4. 问题定义

### 4.1 re-align 跳过

当本地 position 状态缺失或不可用时,插件需要把当前 DOM 消息与 server 已有消息对齐。若 server 已有历史消息,但当前可见 DOM 中没有任何可匹配锚点,就会出现 `realign-no-anchor`。

当前问题:

- 用户不知道为什么没有采集。
- 插件只在 console 输出,租户后台没有状态。
- W21 自动切换可能把该会话当作“已处理过”,实际没有入库。
- 反复重试仍可能继续跳过,没有恢复策略和失败计数。

### 4.2 内容级重复入库

内容级重复指数据库中没有唯一键冲突,但同一会话内存在高度相同的消息内容,分别占用不同 position。

这类重复有两种来源:

| 类型 | 示例 | 处理原则 |
|---|---|---|
| 真实重复发送 | 客户连续发两次“预约” | 必须保留,不能删除 |
| DOM/采集重复 | 页面镜像 DOM、卡片重复节点、同一消息被 scanner 扫两次 | 应诊断并避免重复入库 |

W23 不能简单按内容去重,否则会违反 W17 “有几条存几条”。W23 要做的是识别“同一轮采集内的重复 DOM 候选”与“跨轮冷启动错位造成的伪新增”,并给出安全处理。

## 5. 状态模型

W23 将采集状态分为 5 类:

| 状态 | 说明 | 用户可见结果 | 是否上传 |
|---|---|---|---|
| `first_collect` | server 无历史消息,本地也无 position 状态 | 正常首次采集 | 是 |
| `aligned` | 当前 DOM 与 server recent 成功对齐 | 正常采集 | 是 |
| `recovering` | 暂未找到锚点,系统正在尝试恢复 | 显示“正在对齐历史消息” | 否 |
| `needs_user_action` | 需要用户停留、滚动或重新打开会话辅助对齐 | 显示明确提示 | 否 |
| `blocked_no_anchor` | 多次恢复失败,进入保护状态 | 显示“该会话暂无法安全采集” | 否 |

状态必须能被插件面板和后台诊断读取。

## 6. 产品规则

### 6.1 首次采集

若 server 确认该会话没有任何历史消息:

- 允许建立新的 position 链。
- 不需要 re-align。
- 正常上传。

### 6.2 可对齐采集

若 server 有历史消息,且当前 DOM 可见消息能匹配 server recent:

- 复用历史 position。
- 仅真新消息续编 position。
- 正常上传。

### 6.3 无锚点恢复

若 server 有历史消息,但当前 DOM 没有可匹配锚点:

插件不得直接从 0 开始重编,也不得简单 `max(position)+1` 把当前可见历史全当新消息上传。

必须进入恢复流程:

1. 记录本轮状态为 `recovering`。
2. 扩大可用 recent 窗口或重新拉取 position-state。
3. 等待页面 DOM 稳定后重试。
4. 若由 W21 自动切换触发,暂停该会话的自动切换成功标记。
5. 若仍失败,提示用户停留当前会话或滚动到更早消息辅助对齐。
6. 多次失败后进入 `blocked_no_anchor`,等待人工处理或后续技术兜底。

### 6.4 内容级重复治理

采集器在单轮生成待上传事件前,应判断是否存在明显重复 DOM 候选。

判断目标不是删除真实重复消息,而是识别低风险的“同一 DOM 被扫两次”:

- 同一轮采集内,同方向、同内容、同时间元信息、同 DOM 稳定标识高度一致。
- 同一轮采集内,卡片类消息被不同 selector 同时命中。
- 同一轮采集内,页面同时存在主消息区与镜像/缓存消息区,导致同一消息出现两份。

处理规则:

- 若能确认是同一 DOM 消息重复命中,只保留一个候选进入 position 分配。
- 若无法确认,不得按内容删除,必须保留并写入诊断。
- 对已入库数据,W23 不自动改写历史消息。

### 6.5 W21 自动切换联动

当 W21 自动切换到某会话后触发 `recovering` / `needs_user_action` / `blocked_no_anchor`:

- 该会话不得记为“已成功采集”。
- 本轮可以继续处理其它候选,但必须记录该会话失败原因。
- 若同一会话连续失败,进入冷却,避免反复切换同一问题会话。

### 6.6 用户提示

插件面板需要展示采集状态,至少包含:

| 场景 | 文案口径 |
|---|---|
| 正在对齐 | 正在对齐历史消息,请保持当前会话打开 |
| 需要用户辅助 | 暂未找到历史锚点,请停留或向上滚动后重试 |
| 自动切换跳过 | 该会话暂未安全采集,已跳过自动切换成功标记 |
| 多次失败 | 该会话暂无法安全采集,请联系管理员或技术排查 |

具体文案可由 UI 方案微调,但不能只写入 console。

## 7. 后台诊断

W23 需要让运营或技术能定位“为什么没采集/为什么重复”。

最小诊断字段:

| 字段 | 说明 |
|---|---|
| tenant_id | 租户 |
| service_account_id / account_biz_id | 客服账号 |
| conversation_id | 系统会话 ID |
| platform_conversation_id | 平台会话 ID |
| customer_nickname | 客户昵称 |
| employee_id | 当前采集员工 |
| page_key / scene_key | 平台页面与场景 |
| collector_mode | 手动采集 / 自动切换 |
| status | aligned / recovering / needs_user_action / blocked_no_anchor |
| reason | realign-no-anchor / duplicate-dom-candidate / scanner-empty 等 |
| fail_count | 连续失败次数 |
| last_failed_at | 最近失败时间 |
| sample_message | 可脱敏样例,用于排查 |

第一版可以先进入插件日志与 server 日志;若技术方案评估成本可控,再进入后台诊断页或会话详情侧栏。

## 8. 数据与展示影响

### 8.1 对消息入库

W23 不改变正式消息表的核心身份规则。

要求:

- 不允许因恢复策略导致历史消息被重复续编为新 position。
- 不允许因内容相同误删真实重复发送。
- 不允许 outbound 无精确时间时写入采集当刻冒充消息时间。
- 不允许 re-align 失败时继续上传不可信 position。

### 8.2 对租户后台消息重复

如果租户后台看到重复消息,需先区分:

| 类型 | 判断方式 | 归属 |
|---|---|---|
| DB 已有内容级重复 | 同一会话内相同内容占不同 position | 采集链路问题,W23 诊断治理 |
| DB 无重复但页面显示重复 | SQL 返回正常,前端渲染重复 | 后台展示问题,不归 W23 |
| 平台真实重复发送 | 原生平台确有两条相同消息 | 正常数据,不得删除 |

生产 `go on` 样本属于“DB 已有内容级重复”,其中来客/消息接待会话更像 DOM/采集重复风险,需要 W23 在诊断中覆盖。

## 9. 验收标准

### 9.1 re-align 可恢复

| 编号 | 场景 | 预期 |
|---|---|---|
| R1 | 新电脑/新浏览器首次打开已有会话 | 不再长期只输出 `realign-no-anchor`;插件显示对齐状态 |
| R2 | 清空插件 storage 后打开已有会话 | 不从 0 重编历史 position;不产生历史重复入库 |
| R3 | 当前可见 DOM 无 server 锚点 | 进入 recovering/needs_user_action,不上传不可信消息 |
| R4 | 用户按提示停留或滚动后出现锚点 | 可恢复对齐并继续采集真新消息 |
| R5 | 多次恢复失败 | 进入 blocked_no_anchor,后台可查原因和次数 |

### 9.2 内容级重复治理

| 编号 | 场景 | 预期 |
|---|---|---|
| D1 | 单轮采集同一 DOM 消息被两个 selector 命中 | 只生成一个候选或写入重复候选诊断 |
| D2 | 平台真实连续发送两条相同内容 | 两条都保留,position 不同 |
| D3 | 卡片/模板消息在页面镜像区重复出现 | 不应无诊断地入库为两条正式消息 |
| D4 | 生产 `go on` 类样本复测 | 不再新增同内容伪重复;历史重复不自动改写 |

### 9.3 W21 联动

| 编号 | 场景 | 预期 |
|---|---|---|
| A1 | 自动切换遇到 no-anchor 会话 | 不标记成功,进入冷却并记录原因 |
| A2 | 自动切换处理其它正常会话 | 不被单个 no-anchor 会话阻塞全局 |
| A3 | 用户接管页面 | 人工互锁仍优先生效 |

### 9.4 红线复核

- 不新增发送、回复、输入框能力。
- 不改 message_id / position 的业务原则。
- 不按内容做最终去重。
- 不自动删除或改写历史消息。
- 不绕过 W20 采集权。
- 不把采集当刻写成消息真实发生时间。
