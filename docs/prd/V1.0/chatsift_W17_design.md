# W17 设计:消息位置标识(排序 + 去重统一)

> **解决什么**:消息的"身份(去重)"和"顺序(排序)"统一靠一个"会话内位置标识 position",取代旧的"hash 内容 + seq"(会误删重复内容、排序依赖合成时间)。
> **真机已验证**(html.txt,2026-06-04):Q1 逐条消息行无任何 data-*/id/key 稳定 token;Q2 outbound 客服消息全无精确时间(时间 span 为空),inbound 全有到秒精确时间;时间条覆盖好(超5分钟一条);重复连发真实存在(客服连发"你好/你好/1/1/1")。
> **结论**:Q1/Q2 皆否 → 位置标识无法从 DOM 直接导出,只能"锚点窗口对齐"算出;又因可能跨设备采集 → 采用 **本地实时 + 云端异步对账** 两层。
> **数据策略**:清空重采(现无真实客户)。新逻辑直接跑干净,不迁移历史。
> **变更性质**:C 类(动采集核心 + 数据契约),见 AGENTS §3。

---

## 1. 真机验证的事实(方案依据)

| 事实 | 证据 | 对方案的影响 |
|---|---|---|
| 逐条消息行无稳定 token | 全文无 data-*/id/key | 不能用 DOM token 做身份;走"位置标识" |
| outbound 无精确时间 | 11 条客服消息时间 span 全空 | outbound 排序/身份只能靠位置 |
| inbound 有到秒精确时间 | 6 条客户消息全有 | inbound 可用精确时间辅助定位 |
| 重复连发真实存在 | 客服连发"你好/你好/1/1/1" | 必须靠位置区分,绝不靠内容去重 |
| 时间条密集(超5分钟一条) | 8 个时间条覆盖 4 天 | 天然分段,作段间排序 + 对账锚 |

---

## 2. 核心原则

1. **身份和顺序统一靠 position**:每条消息有一个"会话内位置 position",既做去重身份、又做排序依据。**position 不含内容**(纯位置)。
2. **有几条存几条**(硬原则):连发的重复内容(3条"1")position 不同 → 不同身份 → 都保留。绝不用内容做去重依据。
3. **不存假时间**:outbound 无精确时间 → occurred_at 存 NULL,不再合成"+1s"假时间。展示时 outbound 不显示时间。
4. **本地实时 + 云端最终一致**:本地快速入库展示(接受单端小瑕疵),云端异步对账纠正到最终一致(根治跨设备)。

## 3. 本地层(实时)

### 3.1 位置标识:锚点窗口对齐
- 弃旧的"pass 内同内容 seq",改为**会话内位置号 position**(纯位置)。
- 持久化每会话已采序列(或尾部锚点窗口 + 高水位 position),用 chrome.storage。
- 每次采集:取当前 DOM 消息序列里**连续 3-5 条**做锚点窗口,在已采序列匹配定位 → 锚点之后为新消息、position 续编。
- `message_id = f(conversationId, position)`(基于位置,不含内容)。

### 3.2 段间排序:用时间条
- 消息被时间条天然分段(超5分钟一条时间条)。
- **段与段之间**:按时间条时间排序(到分钟,跨采集一致)→ 解决 F1(新采的历史段按时间条插到正确时间位置,不堆末尾)。
- **段内逐条**:按 position 排。

### 3.3 时间
- inbound:读 invisible 精确时间(到秒,W12.6 逻辑),occurred_at 存精确时间,辅助定位。
- outbound:无精确时间 → occurred_at 存 **NULL**(不合成假时间),排序靠 position + 所在段时间条。

### 3.4 重复内容
- 连发的"1/1/1":各自 position 不同 → message_id 不同 → 三条都入库(满足"有几条存几条")。

### 3.5 失败降级
- 锚点窗口匹配不到(无重叠/冷启动)→ 按时间条把整段作为新段,排到对应时间位置(F1);段内按 DOM 顺序。
- 锚点歧义(窗口内有重复内容)→ 加宽窗口(含方向模式)、取最长唯一匹配;仍歧义则按时间条分段处理。

### 3.6 F1 观测间隙(已定口径)
- 两段之间有"从未被采到"的间隙时:**按段落时间条评估,把段插到正确时间位置**(不堆末尾)。
- 已知局限(登记备查):若真有历史段从未被任何采集看到、且本该插在中间,"按时间条插位"已能正确归位;极端情况下间隙内绝对位置不可恢复,可接受(不卸载+持续采集下极少发生)。

## 4. 云端层(异步对账,每1h,最终一致)

> 根治跨设备重复(F5)。对账单位 = **"段"(时间条之间)**,不是单条 —— 整段对齐比逐条对账简单可靠。

### 4.1 源头预防(先挡住大部分)
- 插件开启时检测:**"该客服账号已在 xx 设备上采集,确定开启吗?"** 强提醒,劝阻多设备同时采同一账号 → F5 大部分不发生。

### 4.2 对账逻辑
- **单位**:以"段"为单位(时间条之间的一串消息),不逐条。
- **跨设备重复识别**:两段若 [租户+平台+页面+客服账号+客户+段时间条边界 + 段内消息序列] 一致 → 同一段 → 合并(只留一份)。
- **顺序纠偏**:按时间条 + position 重排。
- **段间拼接(F1)**:新段按时间条插到正确时间位置。
- **对不齐兜底**:整段对不齐的(极少)→ **丢弃**(宁可丢边界消息,不错误归并)。

### 4.3 对账安全底线
- **幂等**:对账跑多次结果一致(靠"段稳定标识"判断处理过没,处理过跳过)。
- **只补不乱改已确认**:主要处理新采的未稳定数据;对已展示给用户的历史,尽量不重排。

### 4.4 频率
- 每1h(起步值,可调),或触发式(某会话新数据积累到阈值)。

## 5. 归并键设计(未来 b 方案,现登记)

当前 a 方案(每客服采自己账号 + 强提醒)够用。未来真需跨设备真归并(b 方案)时,归并键层级:

```
租户 → 媒体平台 → 对话页面 URL(取稳定部分,去掉易变参数)
  → 客服账号 → 客户昵称(★已知弱点:同名会撞,届时若有稳定客户ID则升级)
  → 段时间条(+段内消息序列兜底,处理同分钟跨段边界)
```

## 6. 数据契约变更(★C 类,改前列 schema diff 报 Chase 确认)

| 变更 | 说明 |
|---|---|
| messages 加 `position` 字段 | 会话内位置号,排序 + 身份依据 |

| 唯一键 | 可能需调整为基于新 message_id / (conversation_id, position) |

migration SQL 只增不改,同步 prod/test compose init 挂载(见 prod-safety §5)。

## 8. 数据策略:清空重采
- 现无真实客户:**清空现有 messages + 相关分析数据,用新逻辑重采**(不迁移历史)。
- 清空属破坏性操作,虽是测试数据,仍走 prod-safety §4 破坏性三问 + 先备份。

## 9. 范围与风险
- **C 类**(动采集核心 + 数据契约)。改完重跑采集回归 + 真实重采验证。
- **不影响分析**:intent(最近20条inbound)、completeness(全量inbound)用 inbound,inbound 时间逻辑不变;但要确认它们读消息的"顺序"改成新 position 后仍正确。
- **本地层先做、能独立验证**;云端对账层第二阶段(本地稳定后再上,a 方案 + 强提醒下 F5 暂不高发)。
- 时间条覆盖度依赖抖音(超5分钟一条),某些段无时间条时靠相邻段推断。
