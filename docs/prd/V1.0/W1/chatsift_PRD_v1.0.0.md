# Chatsift 产品需求文档 (PRD)

> **版本**:v1.0.0
> **状态**:Draft
> **适用范围**:Chatsift V1.0.0 MVP
> **命名**:Chatsift · 会话分拣 (Conversation Sifting Platform)

---

## 第 1 章 产品定位与命名

### 1.1 一句话定位

Chatsift 不替平台 AI 回复每一句话,而是帮助企业从多平台客服会话中筛分高价值线索、补齐预约信息、生成业务工单,并持续提升会话转化率。

### 1.2 命名来源

Sift 意为"筛分、过滤"。产品的核心动作不是"自动回复"(reply),而是从大量客服会话里"筛"出有价值的信息:哪些客户有意向、哪些预约信息不全、哪些是投诉风险、哪些在问价。这与"AI 自动客服"是两个不同赛道:前者是数据工具,辅助人;后者是替代人力。Chatsift 选择前者。

### 1.3 与 chat_rpa 的关系

Chatsift 是 chat_rpa 项目的产品形态升级。chat_rpa(截至 V1.8.2)定位为"多平台 AI 自动回复插件",随着业务认知深化,产品方向调整为"会话智能运营",遂另起新项目 chatsift。chat_rpa 已停止演进,无真实用户。chatsift 复用了 chat_rpa 中经过验证的部分代码(DOM 适配器、运行时基础设施),但版本号、数据库、部署全部独立,从 v1.0.0 重新开始。

### 1.4 设计原则

第一原则是 Observe First。系统默认静默观察,不主动发送任何消息。这是与 chat_rpa 最根本的区别——chat_rpa 的核心是"自动发送回复",而 chatsift V1.0.0 完全不发送,只采集与分析。自动回复能力推迟到远期的 AI Gap Fill 阶段,且仅在严格受限场景下启用。

第二原则是业务逻辑上移。插件只做采集,不做任何判断;所有意图识别、完整度评分、工单生成都在服务端完成。这样业务逻辑变更不需要更新插件,大幅降低多平台 DOM 适配的维护成本。

第三原则是轻量优先。V1.0.0 不引入 Redis、消息队列、WebSocket、ORM、向量数据库等重型依赖,全部用 Node 进程内能力 + MySQL 单库实现。这是被部署环境(单机)的现实约束决定的,也符合 MVP 阶段"先跑通再优化"的节奏。

## 第 2 章 核心业务场景

Chatsift 的业务核心是把客服会话按意图分成四类,每类走不同的处理流程。四类意图的占比是基于真实业务估算,用于指导开发优先级。

### 2.1 简单咨询(占比约 70%)

用户只是泛泛了解,没有明确的预约或购买动作。例如"你们这个怎么收费""在哪里上课"。系统目标不是替人回答,而是判断用户的意向度(高/中/低),给用户打标签,生成一张线索跟进单,交给人工后续跟进。这类占比最大,但单条价值最低,系统处理的重点是分级,把高意向的挑出来。

### 2.2 预约下单(占比约 35%)

用户表达了明确的预约或报名意愿。系统需要从对话中抽取预约相关字段:城市、时间、联系方式、项目、门店。然后检查这些字段的完整度,生成预约确认单。完整度评分是关键产出——如果用户说"我想约这周末",但没说城市和联系方式,系统标记为"完整度 40%,缺城市、缺联系方式",提示人工补齐或后续触发 Gap Fill。

### 2.3 投诉建议(占比约 1%)

用户表达不满或投诉。命中"投诉/售后/退款/差评"等关键词进入此类。系统自动归类投诉类型,总结投诉内容,标记风险等级,生成投诉处理单并标为高优先级,确保人工第一时间介入。占比虽低但风险高,SLA 时限最短。

### 2.4 询问价格(占比未明确,高频)

用户明确问价,命中"多少钱/价格/费用/报价"等关键词。系统需要从对话中提取课时、城市等关键字段,查询企业配置的价格表,生成报价建议,交人工确认后回复。这一类的特点是答案高度结构化(价格表查询),不需要 LLM,纯规则即可。

## 第 3 章 系统组件与边界

Chatsift 由三个组件构成,职责严格分离。

### 3.1 插件(Plugin)

Chrome MV3 扩展,作为只读探针运行在客服的浏览器里。职责仅限三件:用 DOM Adapter 采集多平台客服消息并标准化为 ConversationEvent;用 Event Queue 管理上报队列(去重、重试、离线缓冲);用 Uploader 批量上报到服务端。插件不调 LLM,不做关键词匹配,不写输入框,不模拟发送。V1.0.0 只支持抖音(来客私信 / 飞鸽 / 私信),其他平台后续迭代。

### 3.2 服务端(Server)

Node + Express + MySQL,是 chatsift 的业务核心。职责包括:接收并去重 ConversationEvent,持久化消息;运行分析流水线(Intent → Goal → Completeness);生成 Lead 和 WorkOrder;按规则派单;为后台提供查询 API。所有"智能"都在这里。V1.0.0 的分析流水线用进程内串行 worker 驱动,不引入消息队列。

### 3.3 管理后台(Admin)

Vue 3 + Element Plus,供运营人员使用。职责包括:会话中心(查看采集到的会话)、线索中心(管理线索和意向度)、工单中心(处理和流转工单)、运营分析(转化漏斗、平台对比)、系统设置(意图规则、价格表、LLM 配置)。

### 3.4 组件边界

插件与服务端之间只有一条数据通道:HTTP 批量上报 ConversationEvent。服务端与后台之间是标准 REST API。三个组件可以独立部署、独立升级。插件不直接访问数据库,后台不直接和插件通信,所有交互都经过服务端。

## 第 4 章 核心数据模型

Chatsift 有四个核心业务概念,理解它们的关系是理解整个系统的关键。

### 4.1 Conversation(会话)

一个 Conversation 代表"一个客户在一个平台上的一段持续对话"。用 platform + platform_conversation_id 唯一标识。Conversation 持有分析结果:意图标签、当前阶段、完整度评分。一个客户如果在抖音和小红书都来咨询,会产生两个 Conversation。

### 4.2 Message(消息)

一个 Message 是会话里的一条消息,有方向(inbound 用户发来 / outbound 客服发出)。用 platform + platform_message_id 唯一标识,用于去重。Message 是分析的原料,Conversation 的意图和完整度都是基于其下所有 Message 计算的。

### 4.3 Lead(线索)

一个 Lead 代表"一个潜在客户"。它从 Conversation 中提炼,但维度更高——一个 Lead 可能关联多个 Conversation(同一个人多次来咨询)。Lead 持有客户档案(昵称、电话、微信、城市)、意向度评分、跟进状态、负责人。Lead 是 chatsift 交付给业务的最终价值产物。

### 4.4 WorkOrder(工单)

一个 WorkOrder 是"一件需要人处理的事"。由分析流水线根据意图自动生成,分四类:线索跟进单(inquiry)、预约确认单(appointment)、投诉处理单(complaint)、报价回复单(pricing)。工单持有结构化字段(payload)、完整度、缺失字段、优先级、SLA 时限、负责人、状态。工单是驱动人工动作的载体。

### 4.5 概念关系

```
Customer (隐含,不单独建表,用 platform_uid 表示)
  └── Conversation (一个客户在一个平台的对话)
        └── Message (会话里的每条消息)

Conversation ──分析──> Lead (潜在客户,可合并多个 Conversation)
Conversation ──分析──> WorkOrder (待处理事项,按意图分四类)

WorkOrder ──派单──> Assignment (谁来处理,记录在 workorder.assigned_to)
```

## 第 5 章 工作流

### 5.1 消息采集流

客服在浏览器收到客户消息,页面 DOM 变化触发插件的 MutationObserver,DOM Adapter 提取消息并标准化为 ConversationEvent,进入 Event Queue,Uploader 批量 HTTP 上报到服务端。服务端 Gateway 鉴权后,Conversation Runtime 去重并持久化消息,投递到分析流水线。

### 5.2 分析流水线

消息入库后,异步投递给 analyzer。analyzer 是进程内的串行 worker:对每条新消息,先过 Intent Engine 得到意图标签,再过 Goal Engine 判断对话推进到哪个阶段,再过 Completeness Engine 抽取字段并评分。分析结果写回 Conversation,并按意图触发 Lead 更新和 WorkOrder 生成。

### 5.3 工单生成与派单

WorkOrder Engine 根据意图类型生成对应工单,设定优先级和 SLA。投诉类优先级最高、SLA 最短。生成后 Assignment Engine 按规则派单(V1.0.0 按城市路由到对应人员,无人员配置时进入待分配池)。运营人员在后台工单中心看到新工单,处理后更新状态。

### 5.4 LLM 降级流

Intent Engine 采用 Rule + LLM Hybrid。先用关键词规则做粗分类,命中规则的直接出结果(覆盖约 60-70% 的高频场景)。未命中规则的丢给 LLM 兜底分类。如果企业的 LLM 月度配额已耗尽,系统降级为"仅规则模式",未命中规则的标记为 simple_inquiry(默认类),并在后台提示"请联系平台管理员"。配额耗尽不会中断采集。

## 第 6 章 多租户与权限模型

### 6.1 租户模型

V1.0.0 采用单级租户:一个 user 就是一个 tenant。所有业务数据(会话、消息、线索、工单)按 user_id 隔离。这是基于当前 chat_rpa 没有"企业账号 / 员工子账号"两级结构的现实。未来若需要员工子账号,通过给 users 表加 parent_user_id 字段扩展,不影响现有数据结构。

### 6.2 权限模型

沿用 chat_rpa 已有的 RBAC(roles + role_has_permissions + menus)。V1.0.0 新增以下权限点:会话查看(conversation:list)、线索管理(lead:manage)、工单处理(workorder:handle)、工单派单(workorder:assign)、意图规则配置(intent-rule:config)、价格表管理(price:manage)、LLM 配置(llm:config)。新增对应的后台菜单项。

## 第 7 章 LLM 配额管理与降级策略

### 7.1 企业级 LLM 配置

每个企业(user)独立配置 LLM:接口地址、API Key、模型名称、月度 Token 配额。不同企业可接不同模型(DeepSeek / Kimi / 私有模型)。配置存在服务端,插件不接触 LLM。

### 7.2 配额扣减

每次 LLM 调用后,按返回的 token 数累加到 monthly_token_used。每月 1 日重置。

### 7.3 降级策略

当 monthly_token_used >= monthly_token_quota,Intent Engine 不再调用 LLM,降级为纯规则模式。规则未命中的消息标记为 simple_inquiry(默认意图),保证采集和基础分类不中断。后台对该企业显示提示:"LLM 配额已用尽,请联系平台管理员"。这是用户明确要求的文案。

## 第 8 章 非功能需求

### 8.1 性能

V1.0.0 目标支撑单机部署下数千家企业的采集量。消息上报采用批量(默认每批最多 50 条或每 5 秒触发一次)。分析流水线串行处理,单条消息分析延迟目标 < 2 秒(规则命中) / < 5 秒(LLM 兜底)。

### 8.2 可用性

插件离线时,Event Queue 本地缓冲(chrome.storage.local),恢复后批量补传。服务端重启后,analyzer 从数据库恢复未分析的消息队列。

### 8.3 可观测性

沿用 chat_rpa 的 LK Tracer 和 runtime_logs。插件健康状态(observer 数、queue 积压、上报延迟、断线重连)上报到服务端,后台 Runtime Monitor 可视化。

### 8.4 DOM 隔离

插件必须使用 scoped DOM 操作,禁止全局 document.querySelector。每个会话维护独立的 DOM scope,observer 只观察对应子树。这是根治"会话切换误读""observer 污染"两个老问题的措施。

## 第 9 章 V1.0.0 范围与不做清单

### 9.1 V1.0.0 做什么

V1.0.0 交付一条完整的单平台(抖音)闭环:插件静默采集抖音客服消息,上报服务端,服务端做四类意图识别和完整度评分,生成四类工单,后台能查看会话、处理工单、管理线索。包含 LLM 配额管理和规则降级。

### 9.2 V1.0.0 不做什么

不做自动回复(任何形式的消息发送)。不做抖音以外的平台。不做图片消息的内容分析(只存档,不 OCR)。不做向量检索知识库(意图规则用关键词)。不做客服工作台(后台不提供"直接回复"入口)。不做工单 SLA 的短信/邮件提醒(只做后台红点)。不做员工子账号(单级租户)。

## 第 10 章 后续路线预览

V1.1 计划加入 AI Suggest:在工单里给客服推荐回复话术,但仍由人工决定是否发送。

V1.2 计划加入工作流自动化:工单状态流转自动化、自动派单规则可配置、SLA 提醒。

V1.3 及以后计划探索 AI Gap Fill:在严格受限场景(预约信息缺失、用户长时间未回复)下,经人工授权后由 AI 补发有限的补漏消息。这是 chatsift 第一次真正"发送消息",需要重新引入此前被砍掉的 Send Runtime,且必须有完善的人工管控。

远期计划扩展更多平台(小红书、美团经营宝、快手等),引入向量检索知识库,以及多平台数据打通的统一客户视图。

## 附录 A:术语表

ConversationEvent — 插件上报的标准化消息事件,是插件与服务端之间的数据契约。

Intent Engine — 意图识别引擎,Rule + LLM Hybrid。

Completeness Engine — 完整度评分引擎,针对预约场景抽取字段并评分。

Gap Fill — 补偿式自动回复,远期能力,仅在信息缺失等受限场景启用。

LK Tracer — Lifecycle Kernel Tracer,运行时生命周期日志追踪,沿用自 chat_rpa。

DOM Scope — 作用域化的 DOM 操作封装,禁止全局选择器,防止跨会话污染。
