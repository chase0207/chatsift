## 4. 本轮治理计划与进度账本

**现状**:八环里只有 ⑥⑦ 有机器在守(`release.sh` guard、`check-env-isolation.sh`、版本校验脚本——均已落地)。其余各环规则齐全,但强制者是人。本轮治理把"靠人/缺口"逐格转成"机器强制 + 明确登记",**一格一格做,不一次全动**(稳定性优先)。

### "治理完毕、无漏洞"的定义(可验证)

每条规则都满足两条才算无漏洞:① **只有一个家**(不重复);② **有一个明确的强制者**——要么机器查,要么是写进登记册、有意识保留的人工检查点。
漏洞 = 出现"没有家""多个家""没人强制且没人知道靠人"的规则。
注:无漏洞 ≠ 全自动。本质靠人判断的规则(如"这改动算 A 还是 C 类")只要在登记册里被标成"靠人",就不算漏洞;**掉下去而无人发现,才是漏洞**。

### 四阶段计划(每完成一张任务单标 ✅)

> 状态:⬜ 待出单 · 📝 已出单待执行 · ✅ 已验收

**阶段 A — 先装摄像头(脚本基建,先建机器检查再动文档)**

| 序 | 项 | 交付 | 状态 |
|---|---|---|---|
| A1 | 版本号单一真源 + 文档新鲜度检查 | 只读检查(版本写死告警 + 文档头==changelog) | 📝 |
| A2 | 任务单字段/状态一致性检查([§6.6](./task-doc-workflow.md)) | 检查 active 字段齐全、done 不留 active、状态与记录匹配 | 📝 |
| A3 | main 业务代码提交守卫 | 禁 server/admin/plugin 直进 main | ⬜ |

**阶段 B — 规范化(摄像头到位后改文档)**

| 序 | 项 | 交付 | 状态 |
|---|---|---|---|
| B1 | "先判层"提到 [AGENTS.md](../../AGENTS.md) 一线 + 触发器清单(补①) | 升为一线规矩 | ⬜ |
| B2 | 去重归一(5 条重复规则各归一个家,别处只留链接) | SSOT 落地 | ⬜ |
| B3 | README 全量校准(删过期内部状态,回归对外简介) | — | ⬜ |
| B4 | deploy.md 拆分(现行事实留、chat_rpa 重置方案移 archive) | — | ⬜ |

> B1、B2 都动 AGENTS,**必须串行、各一个 commit,不并行**。B2–B4 每份文档一个 commit。

**阶段 C — 补流程缺口**

| 序 | 项 | 交付 | 状态 |
|---|---|---|---|
| C1 | 复盘强制触发规则(prod 事故 / 发版 abort / 事实源不一致 → 必复盘)(补⑧) | 规则 + 检查 | ⬜ |
| C2 | 并行发版冻结/合入顺序机制化(终结被记两遍的教训) | 轻量机制 | ⬜ |

**阶段 D — 收口(这一步才让"完毕"成立,且后续不回潮)**

| 序 | 项 | 交付 | 状态 |
|---|---|---|---|
| D1 | 规则登记册(每条规则 → 唯一的家 → 强制者) | `docs/ops/rules-index.md` | ⬜ |
| D2 | 统一检查门(A 阶段各检查并入一个 runner,接进 pre-commit/CI) | 每次提交自动跑 | ⬜ |
| D3 | 完整性终验 + 维护规约:遍历登记册确认每条规则都有家+有强制者;立规矩——以后新增/改规则必须登记并声明强制者,否则门拦下 | 终验报告 + 规约 | ⬜ |

> 注:**worktree / 多工作区隔离**属于第④环"执行"的基础设施,在路线推进到 ④ 时一并落地,不单独成线。
> 完成判据:阶段 D 全绿,即登记册里没有一条"无家/无强制者"的规则,且该状态由机器每次提交守着。

## 5. 与其他文档的关系 / 维护规约

- 本文与 [AGENTS.md](../../AGENTS.md) 的分工:AGENTS = "每次都要遵守的核心规矩"(一屏);本文 = "这些规矩串成的流程地图"。两者都不复述对方,互相链接。
- **单一真源纪律(本文自身也守)**:本文不复述任何规则正文、不写死任何版本号或状态。规则正文改动 → 改它的家(上表"权威文档"列),本文通常不动;仅当流程顺序、环的拆分、或链接路径变化时才更新本文,并提升版本号 + 补 changelog。
- 文档头 `版本:` 必须与本文 changelog 顶行一致(纳入路线 1️⃣ 的新鲜度检查)。
