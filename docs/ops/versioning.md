# 编号与版本规范(versioning.md)

> 解决"W 编号 / M 编号 / git tag / VERSION 对不上"的混乱。基于 2026-06-04 现状核实定稿。
> 版本:v1.4.0 / 2026-06-11

---

## 1. 三套编号,各管各的

| 编号 | 管什么 | 例 |
|---|---|---|
| **W 系列** | 产品迭代(对话里的周次/功能任务) | W13 消息聚合、W16 双入口、W17 消息位置 |
| **M 系列** | 技术债 | M1-M21(见 tech-debt-master-plan) |
| **vX.Y.Z** | git tag / VERSION(发版产物) | v0.3.1、v0.4.0 |

## 2. 版本号(vX.Y.Z)规则
- chatsift 独立 v0.x 版本线(与 chat_rpa 的 v1.x 无关)。
- **W 大功能 → minor**(`0.x.0`);**补丁/小修复 → patch**(`0.x.y`)。
- 单一真源 VERSION,同步规则见 release.md。
- `tools/dom-collector` 独立版本线(1.0.0),不并入产品版本。

## 3. W ↔ tag 对应:历史模糊,从 W17 起严格

### 3.1 历史现状(承认模糊,不强行补)
现状核实发现:**历史 tag 不是按 W 周次 1:1 的**。
- v0.2.0~v0.2.8(均 06-02):W1-W12 早期工作累积进 v0.2.0 基线后的增量补丁,**无明确 W 归属**。
- **W13 = v0.2.5 / v0.2.6**(commit 明确)。
- v0.2.7/v0.2.8:RBAC 修复,推断 W15 邻域,无明确 W。
- v0.2.9~v0.2.12:客户昵称修复链,**无明确 W**(补丁波)。
- **W16 = v0.3.0 / v0.3.1**(commit 明确)。

→ 历史不强行补 W 归属(那样是编造)。以现状核实文档 `docs/research/2026-06-04_版本与编号现状核实.md` 为历史依据。

### 3.2 从 W17 起的严格规约
- **每个 W 大功能发版,commit message 和 CHANGELOG 必须标注关联的 W 编号。**
- 发版时在 PROJECT_STATUS 的发版记录表里写明 tag ↔ W 对应。
- 这样从 v0.4.0(W17)起,W ↔ tag ↔ VERSION 三者可一一对应、可追溯。

## 5. 维护规约
- 每次发版,QA 更新本表(加新 tag ↔ W 行 + **是否单独部署**)。
- VERSION 同步生产(release.md §2),不再出现"生产版本戳与代码脱节"。
- 编号变更(如未来引入新编号系列)先更新本文件。
- **patch 版本(`0.x.y`)可以包含前序"已 tag 但未单独部署"的内容**(如 v0.6.3 包含 v0.6.2/W22);此时 **PROJECT_STATUS 必须写清每个 tag「是否单独部署」**,避免"tag 存在 = 已上线"的误读。并行发版时,正在 hotfix 的 release 分支与功能分支需明确冻结/合入顺序。
