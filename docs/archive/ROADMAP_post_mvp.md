# chatsift 后续路线图(MVP 之后)

> **背景**:W0-W9 的 MVP 主线已完成(采集→分析→线索→工单→运营报表),W9 已验收通过。用户提了 4 条新需求(补充2-5),共同指向”让诊断更准、更快、且人工能高效复核”——从”能跑通”到”真正好用”。
> **本文状态**:**已定稿**。顺序、节奏已确认。三个阶段 W10→W11→W12 依次执行,每阶段单独出 design+tasks 后交 cc 实施。
> **当前进度**:W9 已完成,**立即进入 W10**。

## 1. 四条补充的依赖关系(为什么不能按 2→3→4→5 顺序做)

```
补充2 字段有效性 ─────┬──→ 补充4 诊断分类+颜色(颜色标签的数据来源是有效性判定)
(地址/时间/号码有效性) │         例:"地址不准确"橙色,前提是补充2先判出地址无效
                      │
                      └──→ 补充5 快速看记录(复核的是有效性诊断对不对)

补充3 准实时时序 ──────── 相对独立(时序优化,不依赖2/4/5,但④后台提醒和4/5的界面相关)
```

关键依赖:**补充4 和 补充5 都依赖 补充2 先做**。没有字段有效性判定,补充4 的红/橙颜色没有数据来源,补充5 的”复核有效性”也无的放矢。所以 **补充2 必须排在 4、5 之前**。

补充3(时序)相对独立,可以并行或单独排,但它的第④环(后台主动提醒)和补充4的界面有交集,放在一起做更顺。

-----

## 2. 建议的阶段划分

按依赖关系,我建议组织成三个阶段:

### 阶段一 = W10:字段有效性校验(补充2)

**为什么先做**:它是 4 和 5 的地基。先让机器把”字段填得有效没效”判出来并存好,后面的颜色、复核才有数据。

**核心内容**:

- completeness 抽字段时,增加**有效性判定**,结果存进数据库(字段值 + 有效性标记)
- 有效性规则(规则优先,AI 兜底):
  - 手机号:正则 `1[3-9]\d{9}` → 纯规则
  - 微信号:格式规则 → 纯规则
  - 城市:城市词表 → 纯规则
  - 姓名:规则挡明显无效(纯数字/单字/表情);“像不像真名” → AI
  - 时间:规则解析常见格式 + 判断是否到”日期+小时”;相对时间(这周六)转具体日期、模糊判断 → AI
  - **上车地址:是”点”还是”片”** → 几乎必须 AI(规则做不准)
- **成本控制(关键)**:有效性在**消息分析时算一次、存下来**,报表/界面只读存好的标记,绝不在看报表时实时调 AI。复用 W8 的”规则优先、LLM 兜底、配额受限”机制
- schema 增量:存每个字段的有效性结果(如 contact_valid / pickup_location_valid / time_valid 等,或一个 validity JSON)

**风险**:改 W3 completeness 引擎(C 类)+ schema 增量 + 接 AI 有效性。中等改动,要重跑 W3/W7/W9 验收。

### 阶段二 = W11:诊断分类+颜色 + 快速复核(补充4 + 补充5)

**为什么合并**:4 和 5 是同一个界面工作流的两面(颜色标问题 + 点开看记录复核),数据都来自 W10 的有效性结果,一起做界面最连贯。

**核心内容(补充4)**:

- 诊断标签体系:每条会话产出一组带颜色的诊断标签
  - 咨询:灰(无有效信息)/ 橙(价格优惠等咨询)/ 单独标投诉
  - 留资:绿(有效)/ 橙(疑似无效)/ 红(无效)
  - 预约:绿(完整有效)/ 红(缺联系方式、多字段缺失)/ 橙(地址不准、时间不准、姓名存疑)
- 一条会话可有多个标签;列表主色取最严重(红>橙>绿>灰)
- 诊断标签基于 W10 存的有效性结果生成,不重新算

**核心内容(补充5)**:

- 列表里就地弹出(drawer/弹窗)聊天记录,不跳转,人工快速复核
- 加分项:字段抽取值与原文位置关联高亮(机器从哪句抽出的地址)

**风险**:主要是后台前端 + 诊断标签生成逻辑。相对安全(读 W10 的数据做展示)。

### 阶段三 = W12:准实时时序(补充3)

**为什么单独 + 可灵活排**:时序优化相对独立,不依赖 2/4/5 的数据。但它的”后台主动提醒”(第④环)和 W11 的界面相关,所以排在 W11 后,提醒可以直接用 W11 的诊断颜色(如”高意向红色线索”提醒)。

**核心内容(四个环节的时序)**:

- ① 采集节流:MutationObserver 触发后节流 ~10 秒采集(等 DOM 渲染完整)。前提:页面保持前台(写进用户手册)
- ② 上报触发:EventQueue 攒满 N 条 或 距上次 ~15 秒,先到先发(短间隔批量,非单条即发)
- ③ 分析时序:规则毫秒级;要 LLM 的 1-10 秒。风险是 LLM 调用积压拖慢队列——评估是否给”高意向消息”分析优先级
- ④ **后台主动提醒(关键缺口,现在完全没有)**:后台轮询(~30 秒)查新的高意向线索,声音/红点提醒。否则客服不刷新就看不到新线索,前三段再快也白搭
- 目标:总延迟正常 30-45 秒、最坏 ~1 分钟,满足”留资后 1-5 分钟内联系”且有余量

**风险**:改采集节流(动 W4/W5 采集)+ 后台轮询(新功能)。④ 是达成 SLA 的必要补齐。

## 3. 执行顺序与理由(已定)

```
W10 字段有效性(补充2)   ← 先做,是地基
  ↓
W11 诊断颜色+快速复核(补充4+5)  ← 依赖 W10 的有效性数据
  ↓
W12 准实时时序(补充3)   ← 相对独立,但④提醒复用 W11 的诊断颜色
```

**为什么时序(补充3)排最后而不是最前**:虽然”准实时”听起来最急,但它的价值依赖前面——如果诊断不准(没做 W10)、人工看不懂哪条要紧(没做 W11),那”很快地推送一堆没法判断的线索”反而是干扰。先让线索”准”且”可读”,再让它”快”,顺序更合理。此顺序已定,W12 整体(含后台提醒)排在 W11 之后。

## 5. 一个跨阶段的成本提醒

W10 引入”分析时调 AI 判字段有效性”,会增加 LLM 调用量(地址/时间/姓名的有效性判断)。因为 LLM 费用租户付,要守住:

- 规则能判的不调 AI(手机号正则、城市词表)
- 只对”规则判不准”的字段调 AI(地址成点与否、模糊时间)
- 有效性结果存库,报表/界面只读不重算
- 配额耗尽时,有效性判定降级为”仅规则”(规则能判的照判,AI 那部分标记为”未校验”而非报错)

这和 W8 的省钱原则一脉相承。W10 设计时会把这些写死。
