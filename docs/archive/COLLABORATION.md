# Chatsift 协作协议

> 本协议约定三方(用户 / Claude / 执行端)的协作方式。三方指:
> 
> - **用户**(产品负责人,非技术背景,做决策和真实环境验收)
> - **Claude**(方案设计,产出 design + task 文档,review 验收报告)
> - **执行端**(cc / codex 等 AI 编码工具,落地实现代码)
> 
> 三方是独立系统,Claude 与执行端之间无直接通道,所有传递经用户中转。本协议的目标是让中转成本最低、方案对齐最稳、变更最可追溯。

-----

## 第一层:协作机制 — 建议三分类

执行端在落地时常会发现设计端没考虑到的依赖或更优实现。这种反馈有价值(如 W4 发现 self-check 的 sendlock 依赖 sendReply),应鼓励,但要按影响范围分级处理,避免方案漂移。

### A 类 — 实现细节的保守调整(执行端可自主,事后告知)

**定义**:只改”怎么实现”,不改设计意图、不改验收标准、不跨周次、不动已验收代码。

**处理**:执行端直接做,在验收报告里用一句话说明”在 X 点做了调整,原因 Y”。不必停下等批准。

**示例**:新增 event-queue.js 而非改 queue-manager.js;用 djb2 还是 FNV 做 hash;变量命名、文件拆分方式。

### B 类 — 触及设计意图或验收标准(必须停,过用户和 Claude)

**定义**:改变技术路线、风险模型、数据契约、验收口径,或对设计的核心假设提出异议。

**处理**:执行端**停止该项实现**,把问题写成反馈文档(见第二层),经用户转给 Claude,三方确认后再继续。

**示例**:“不该用合成 ID,该上网络拦截”;“intent 优先级顺序应该改”;“events 接口的去重键设计有问题”。

### C 类 — 跨周次或动已验收代码(必须停,且慎重)

**定义**:触碰已经验收通过的代码(W1-W3 的服务端、已验收的引擎逻辑),或把当前周的改动扩散到其他周次的范围。

**处理**:**默认不动**。已验收代码非必要不改。确有必要,执行端停下,明确说明”为什么必须动已验收的 X”,经用户和 Claude 确认风险后才动,且改完要重跑被影响部分的验收。

**示例**:“顺手优化了 W3 的工单去重”;“改 W4 时把 W2 的 analyzer 也重构了”。

### 一句话判据

执行端拿不准是 A 还是 B 时,问自己:**这个改动会不会让验收标准或设计意图变化?** 会 → B 类停下;不会 → A 类自主做。拿不准 B 还是 C,看**有没有碰已验收代码**,碰了就是 C。

## 第二层:产出物文档化 — 一切进 git 仓库

三方之间不靠口头/截图传递,靠 git 仓库里的文档作为”共享白板”。所有产出物都落盘 + 进 git。

### 目录约定

```
chatsift/docs/
├── COLLABORATION.md          ← 本协议(根文档)
├── prd/                      ← Claude 产出:PRD
│   └── PRD_v1.0.0.md
├── architecture/             ← Claude 产出:design + task 文档
│   ├── W1_tasks.md / W2_design.md / ...
│   └── v1-api-spec.md
└── reports/                  ← 执行端产出:反馈 + 验收报告
    ├── W1_acceptance.md
    ├── W4_feedback.md        ← 执行端的 B/C 类反馈
    └── ...
```

### 三方的落盘责任

|方     |产出物                           |落盘位置                          |
|------|------------------------------|------------------------------|
|Claude|design 文档、task 清单、PRD、API spec|docs/architecture/ 或 docs/prd/|
|执行端   |验收报告、B/C 类问题反馈、偏离记录           |docs/reports/                 |
|用户    |决策结论(可选,重要决策建议记一句)            |由 Claude 或执行端代记入相关文档          |

### 传递方式

- **Claude → 执行端**:Claude 把文档内容给用户,用户让执行端写入 docs/ 对应路径(执行端有文件系统权限,直接落盘)。
- **执行端 → Claude**:执行端把反馈/验收报告写成 docs/reports/ 下的 .md 文件,**用户把该文件上传给 Claude**(优先传文件,不传截图——文件信息密度和准确度高于截图 OCR)。
- **约定**:Claude 更新文档后,只告知”改了哪个文件的哪几节”,用户让执行端**重读该文件**或**看 git diff**,不必每次重述全文。

## 第三层:变更可追溯 — 版本号 + 变更日志

每份 design / task / spec 文档,开头必须带版本号和变更日志。这样任何人(包括三个月后的自己)打开文档,一眼知道它经历过什么。

### 文档头部模板(以后每份文档开头都用这个)

```markdown
---
文档: <文档名,如 W5 任务清单>
版本: v1.1.0
周次: W5
状态: Draft | Active | Done
---

## 变更日志

| 版本 | 日期 | 变更摘要 | 触发来源 |
|---|---|---|---|
| v1.1.0 | 2026-05-30 | Task3 改为保留发送方法;Task5 改用独立 event-queue | 执行端 B 类反馈 |
| v1.0.0 | 2026-05-29 | 初版 | Claude 设计 |

---

<正文从这里开始>
```

### 版本号规则(语义化简化版)

- **大改(x.0.0)**:设计意图或技术路线变化(如 W4 从网络拦截改为合成 ID)。
- **中改(1.x.0)**:某个 Task 的实现方案调整(如本次采纳执行端两点反馈)。
- **小改(1.0.x)**:错别字、补充说明、格式,不影响实现。

### 变更日志的”触发来源”列

记清楚这次变更是谁触发的:Claude 设计 / 执行端 A(B/C)类反馈 / 用户决策。这样能看出文档是怎么演进的,也能复盘哪类反馈最有价值。

## 协议执行检查点

每周开始(Claude 发 task 文档时)和每周结束(执行端发验收报告时),对照本协议自检:

**Claude 发文档时**:

- [ ] 文档开头有版本号 + 变更日志表
- [ ] 改动过的,在变更日志记了这次变更 + 触发来源
- [ ] 告知用户”改了哪几节”,不让执行端盲目重读全文

**执行端发报告时**:

- [ ] 验收报告落盘到 docs/reports/
- [ ] A 类调整在报告里一句话说明
- [ ] B/C 类问题已停下,单独成文等确认(没有自作主张往下做)
- [ ] 附 git log –oneline 确认 commit 无漏无混

**用户**:

- [ ] 优先传文件给 Claude,不传截图
- [ ] B/C 类反馈,做决策后让 Claude 更新文档
