# W13 设计说明:消息聚合展示

> **周次**:W13
> **范围**:把分散在会话列表/详情/诊断/字段/工单里的信息,聚合成一个**纯只读**的多栏视图,让客服在一个页面里高效浏览一个客户的全貌。
> **关联**:W6 会话/消息、W7 lead、W10 字段有效性、W11 诊断颜色+MessageDrawer、W12.6 精确时间
> **本周不做**:任何发送/回复功能(见红线)、新的分析逻辑(W13 只聚合展示已有数据)
> **命名**:特意叫"消息聚合**展示**",不叫"工作台"——用命名守住"只读、无操作入口"的边界。

---

## 0. W13 要解决什么

到 W12 为止,关于"一个客户"的信息散落在多个地方:
- 会话列表:看到客户昵称、意图、阶段、完整度、诊断主色
- 会话详情:看消息流
- 字段诊断:看 6 字段哪些有效
- 线索中心:看 lead 等级、评分
- 工单中心:看这个客户有没有工单

客服要了解"这个客户是谁、想干嘛、信息全不全、该不该马上跟",得在几个页面之间跳。**W13 把这些聚合到一个视图里**:左边选客户,中间看完整对话,右边一眼看到字段诊断 + lead + 工单。一个屏幕看全一个客户。

这是产品从"功能分散"到"信息聚合"的一跃,让"准实时催单"真正高效——客服收到提醒,点进来,一个页面就能判断和准备(判断完去抖音原生页面回复)。

---

## 1. 最高约束:纯只读,无任何发送入口 ⚠️

**这条优先于一切,写在最前面。**

- W13 是**展示**视图,不是操作台。**没有输入框、没有发送按钮、没有回复区、没有任何会向抖音发消息的入口。**
- 中间栏是消息流,**只读展示**历史对话(inbound/outbound 都只读显示),不能在这里打字回复。
- 客服看完 W13、做完判断后,回复动作在**抖音原生页面**做,chatsift 不介入。
- 这是 chatsift 的产品红线(永不发送/Observe First,见 HANDOVER §1)。W13 因为长得像"四栏工作台"(竞品草图 IMG_4811 那种),最容易让人想加发送框——**坚决不加**。命名叫"展示"就是为了时刻提醒这条线。
- 实现层面:W13 不引入任何调用发送的代码,不依赖任何 adapter 的发送方法(那些 W5 已删)。

---

## 2. 布局:三栏(不是四栏)

竞品草图是四栏(客服账号 / 会话列表 / 消息窗口 / 用户信息)。chatsift 的 W13 简化为**三栏**——因为"客服账号"那一栏对只读分析没必要(我们不按客服账号操作),合并掉。

```
┌──────────────┬───────────────────────┬──────────────────┐
│ 左:会话列表   │  中:消息流(只读)       │ 右:客户全貌       │
│              │                       │                  │
│ - 客户昵称    │  - 按时间正序的对话     │ - 字段诊断(6字段) │
│ - 诊断主色点  │  - inbound/outbound区分 │   每字段值+颜色+理由│
│ - 意图/阶段   │  - W12.6 精确时间       │ - lead 等级/评分   │
│ - 完整度      │  - 默认滚到最新         │ - 意图/阶段/完整度 │
│ - 筛选/搜索   │  - 无输入框!           │ - 关联工单(只读)  │
│              │                       │ - 诊断标签组       │
│ (点客户→中右刷新)                      │                  │
└──────────────┴───────────────────────┴──────────────────┘
```

### 2.1 左栏:会话列表(复用现有)
- 基本就是现在会话中心列表的精简版:客户昵称 + 诊断主色 + 意图 + 阶段 + 完整度
- 保留 W11 的诊断颜色筛选、W12.6 的页面/昵称/消息搜索
- 点某个客户 → 中栏和右栏刷新成该客户的内容
- 高亮当前选中的客户

### 2.2 中栏:消息流(只读)
- 复用 W6 消息流 + W11 MessageDrawer 的展示逻辑(但这里是常驻栏,不是抽屉)
- inbound(客户)/outbound(客服)左右区分
- 时间用 W12.6 的精确时间(invisible 标签那套)
- 打开默认滚到最新消息(W12.6 已做的逻辑)
- **顶部不要、底部更不要任何输入框/发送按钮**
- 加分项:把右栏字段诊断里"机器抽取的字段值"在消息流里高亮对应原文(如地址从哪句抽的),点字段→消息流定位高亮。这是 W11 提过的加分项,W13 可顺势做,不强求

### 2.3 右栏:客户全貌(聚合)
把关于这个客户的分析结果聚合展示:
- **字段诊断区**:6 个租车字段(姓名/城市/时间/联系方式/上车位置/车型),每个显示 值 + 有效性颜色 tag + 理由(来自 W10 field_validity)
- **诊断标签组**:W11 的诊断标签(红/橙/绿/灰)
- **lead 信息**:等级(high/medium/low)、评分、阶段
- **意图 / 完整度**
- **关联工单**:这个客户产生的工单(只读列表,点开看工单详情,不在这里改工单状态——改状态去工单中心)

## 3. 数据从哪来(复用,不新增分析)

W13 **不产生任何新分析**,纯粹聚合展示已有数据。数据源:

| 栏 | 数据 | 来源接口 |
|---|---|---|
| 左:列表 | 会话+诊断主色 | GET /conversations(W11 已带 diagnosis) |
| 中:消息流 | 消息+精确时间 | GET /conversations/:id/messages(W12.6,latest=1) |
| 右:字段诊断 | field_validity+诊断标签 | GET /conversations/:id(W11 已带 diagnosis.tags) |
| 右:lead | 等级/评分/阶段 | GET /leads(按会话/客户关联) |
| 右:工单 | 关联工单 | GET /workorders(按会话/客户筛) |

可能需要一个**聚合接口**(可选):GET /conversations/:id/aggregate,一次返回这个客户的会话+消息+诊断+lead+工单,省得前端发好几个请求。是否做这个聚合接口由实现侧权衡——数据量小就前端并发几个现有接口,频繁就做个聚合接口。

## 4. 这是新页面,还是改造现有会话中心?

两个选择:
- **A:新增独立页面**(如 /aggregate 或 /workspace-view),菜单加一项"消息聚合"。会话中心保持原样。
- **B:把现有会话中心详情改造成三栏**。

**建议 A(新增独立页面)**。理由:会话中心现在的列表+详情模式有它的用途(批量浏览、筛选、导出视角),不必推翻;聚合视图是另一种"聚焦单客户"的浏览方式,作为新页面并存,让客服按需切换。改造现有页面风险大、也丢了原有用法。

菜单命名:"消息聚合"或"会话聚合"(不要叫"工作台")。

## 5. 验证(W13 结束应看到)

```
1. 新页面三栏布局:左列表、中消息流、右客户全貌
2. 点左栏某客户 → 中栏显示该客户完整对话(精确时间、默认看最新)、右栏显示其字段诊断/lead/工单
3. 右栏字段诊断:6字段值+颜色+理由,和 W10/W11 一致
4. 诊断标签、lead 等级、关联工单都正确聚合显示
5. 全程只读:整个页面找不到任何输入框/发送按钮/回复入口(红线验证)
6. 筛选/搜索:左栏保留 W11 诊断色筛选 + W12.6 搜索
7. (加分)点右栏字段 → 中栏消息流高亮对应原文
8. 不影响现有:会话中心/工单/线索各页照常,W13 是新增不是改造
```

## 6. 风险与注意

第一,**红线第一**:无任何发送入口。这是 W13 最容易出问题的地方,实现和验收都要专门检查"整个页面没有输入框/发送按钮"。

第二,**纯展示不新增分析**:W13 只聚合已有数据(W10字段/W11诊断/W7lead/W6消息),不调 AI、不加分析逻辑、不写业务表。和 W11 一样是"读数据做展示",风险低。

第三,**新页面并存,不改造旧页**:会话中心等保持原样,W13 是新增视图。

第四,**复用而非重写**:中栏消息流复用 W6/W11/W12.6 的成果,右栏诊断复用 W10/W11,左栏复用会话列表。W13 主要是"组装"已有组件成三栏,不重造轮子。

第五,**性能留意**:如果做聚合接口,注意别触发 W11/SPEC_GAP 提到的 diagnosis_color 全表内存过滤那类隐患;单客户聚合数据量小,问题不大。

第六,**沿用 Element Plus 风格**,三栏用现有布局组件,诊断颜色用标准 danger/warning/success/info。

第七,**依赖 W12.6 收口**:中栏的精确时间依赖 W12.6 真实验证通过。W13 实现前确认 W12.6 已收口(时间准确率达标),否则聚合视图里的对话时间还是乱的。
