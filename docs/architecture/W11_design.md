# W11 设计说明:诊断分类+颜色 + 快速复核

> **周次**:W11(后续路线图阶段二)
> **范围**:把 W10 的有效性数据翻译成带颜色的诊断标签;人工就地快速复核聊天记录
> **关联**:W10 field_validity、W6 会话详情、W9 后台、后续路线图
> **本周不做**:准实时/后台提醒(W12)、改分析逻辑(W11 只读 W10 数据做展示)
> **核心**:W11 几乎不碰后端分析逻辑,主要是”翻译 + 展示”——后端拼诊断标签(读 W10 数据)+ 前端颜色和复核界面

-----

## 0. W11 要解决什么

W10 让机器判出了每个字段有效没效(field_validity),但那是给机器看的 JSON。W11 把它翻译成**人能一眼看懂的颜色标签**,让客服快速分流”哪条线索有硬伤、哪条要赶紧跟”,并能点开聊天记录验证机器判断对不对。

这是”机器初筛 + 人工终判”工作流的界面落地。

-----

## 1. 诊断标签:算出来,不存表

诊断标签**在接口返回时实时拼**,数据来源是 W10 已存的 field_validity + intent + lead。不新建表存标签。

理由:W10 的有效性逻辑若调整,标签自动跟着变,不会数据不一致。标签是 field_validity 的”视图”,不是独立数据。

### 1.1 颜色语义(四色)

```
红 danger   硬伤,线索不可用/要优先处理(缺有效联系方式、投诉)
橙 warning  存疑,需人工核对(地址不准、时间不准、姓名存疑、疑似无效)
绿 success  有效/正常
灰 info     无实质信息(纯寒暄)
```

### 1.2 诊断标签生成规则(三环)

按会话所处环节(咨询/留资/预约)+ field_validity 生成一组标签:

**咨询环节**(还没留资):

- 无有效信息(纯寒暄,无字段) → 灰
- 咨询类(价格/优惠/车型等,intent=price_inquiry/simple_inquiry 但有实质内容) → 橙
- 投诉(intent=complaint) → 红(投诉要优先处理,单独标红)

**留资环节**(contact 字段有值):

- contact valid → 绿”联系方式有效”
- contact unknown → 橙”联系方式待核对”
- contact invalid → 红”联系方式无效”

**预约环节**(意图是预约/已抽预约字段):

- 6 字段全 valid → 绿”预约信息完整”
- contact invalid/缺失 → 红”缺有效联系方式”
- pickup_location invalid → 橙”上车位置不准确”
- time invalid → 橙”时间不准确”
- name invalid → 橙”姓名存疑”
- city invalid → 橙”城市不准确”
- car_type invalid → 橙”车型不明确”
- 任意字段 unknown → 橙”<字段>待核对”

### 1.3 一条会话多个标签 + 主色

一条会话可能同时有多个标签(如”联系方式有效”绿 + “上车位置不准确”橙)。

**列表里的”主色”取最严重的**:有红显红 > 有橙显橙 > 全绿显绿 > 灰。这样列表扫一眼就能看到哪些线索有硬伤(红)、哪些要核对(橙)、哪些 OK(绿)。

详情页展示全部标签(每个字段的诊断 + 理由,理由来自 W10 存的 reason)。

## 2. 后端:诊断标签拼装

在 conversations/leads 列表和详情接口里,增加 diagnosis 字段(实时拼,不存表)。

```
buildDiagnosis(conversation):  // 读 field_validity + intent + lead
  tags = []
  // 按 1.2 规则生成标签
  for 每个相关字段/环节:
    tags.push({ label:'联系方式无效', color:'danger', field:'contact',
                reason: field_validity.contact.reason })  // reason 来自 W10
  mainColor = 取 tags 里最严重的颜色(danger>warning>success>info)
  return { tags, mainColor }
```

挂在:

- GET /api/v1/conversations(列表):每条带 diagnosis.mainColor(列表显示主色)+ 简要标签
- GET /api/v1/conversations/:id(详情):完整 diagnosis.tags(每字段诊断 + 理由)
- GET /api/v1/leads(列表/详情):同样带 diagnosis

这些是读已存数据实时拼,不调 AI、不写表、不碰分析流水线。

## 3. 前端:列表颜色 + 诊断标签

### 3.1 会话列表 / 线索列表

- 加一列”诊断”或用整行/客户名的颜色点表示主色(mainColor)
- 主色红:行首一个红点/红色标记,一眼看出有硬伤
- 鼠标悬停或展开显示该会话的标签组
- 支持按诊断颜色筛选(只看红色硬伤线索 / 只看橙色待核对)——这对客服分流很有用

### 3.2 会话详情 / 线索详情

- 在客户档案区,把每个字段的诊断标签显示出来:
  - 字段值 + 有效性颜色 tag + 理由(如”上车位置:浦东新区 [橙]仅区级,缺具体点”)
- 让客服一眼看出”这条预约哪个字段有问题、为什么”

-----

## 4. 快速复核:就地弹出聊天记录(补充5)

### 4.1 核心:不跳转,就地看

客服在列表复核时,不用跳转到详情页再返回。在列表里:

- 点诊断标签 或 一个”看记录”按钮 → **就地弹出 drawer(抽屉)或 dialog** 显示该会话的聊天记录
- 看完关掉,接着看下一条。复核效率高

聊天记录复用 W6 会话详情页的消息流组件(inbound/outbound 区分),放进 drawer 即可。

### 4.2 加分项:字段值与原文关联高亮

drawer 里显示聊天记录时,把”机器抽取的字段值”和”原文对应位置”关联:

- 如机器从”我在普陀区镇坪路666号”抽出了 pickup_location,就在那条消息里高亮这段
- 让客服一眼看出机器判断的依据,快速确认机器对不对

这是加分项,不强求。优先做”就地弹出聊天记录”这个核心。

## 6. 风险与注意

第一,**W11 不碰分析逻辑**。诊断标签是读 W10 的 field_validity 实时拼的视图,不调 AI、不写表、不改 completeness/lead 引擎。这是 W11 风险低的原因,也要守住——别为了诊断去改分析。

第二,**诊断标签算出来不存表**:保证和 W10 有效性数据一致。

第三,**主色规则统一**:红>橙>绿>灰,列表和详情用同一套,抽公共函数。

第四,**理由来自 W10**:诊断标签的 reason 直接用 W10 存的 field_validity.reason,不重新生成。

第五,**快速复核优先做”就地弹出”**,高亮关联是加分项,时间紧可后置。

第六,**沿用 W6/W7 Element Plus 风格**,诊断颜色用 Element Plus 的 danger/warning/success/info 标准色,和现有 tag 一致。
