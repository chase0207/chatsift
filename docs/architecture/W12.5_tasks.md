## 2. 修正一:锁定 intent 取数口径 = 最近20条 inbound,排除 outbound

### 背景

- W6.5 当时把 **completeness** 取数从”最近5条”改成”全量”,但**没有改 intent**——intent 一直是最近5条。codex 这次把 intent 改成20条,方向对(解决意图被寒暄挤出窗口)。
- 但有两个要锁定的点:

### 要确认/修正的

1. **取数范围 = 最近20条**(codex 已改 INTENT_CONTEXT_SIZE=20,保留)。intent 用20条而非全量,因为意图会漂移(客户可能从问价转预约),看近期比看全部历史更准。
1. **必须只取 inbound(客户发的),排除 outbound(客服发的)**。确认 codex 改的20条取数 SQL 有没有 `direction='inbound'` 过滤:
- 有 → 确认即可
- 没有 → **必须补上**。否则客服的促销话术(如”报名优惠”“200元京东卡”)会被算进意图判断,把会话**反向误判成 price_inquiry**(客服越推销越容易误判),这是错的

```bash
# 查 intent 取数的 SQL
grep -n "direction\|inbound\|INTENT_CONTEXT_SIZE\|LIMIT" server/src/v1/analyzer.js
```

确认 intent 取数 = `WHERE direction='inbound' ... ORDER BY occurred_at DESC LIMIT 20`。

### 口径写死 + 注释

在 analyzer.js 注释标明:意图判断 = 最近20条 inbound(客户消息),排除 outbound;completeness = 全量 inbound(W6.5)。两者上下文范围不同是有意的(意图看近期防漂移,完整度看全量防字段丢失)。

## 3. 修正二:结构化预约识别要让位投诉优先级

### 问题

codex 把 classifyStructuredAppointment 放在**所有判断之前**(DB intent_rules 和 LLM 都在它后面),一旦命中3个预约字段就直接返回 appointment。这**绕过了 W2 的意图优先级体系**(投诉10 > 问价20 > 预约30,投诉最优先)。

冲突场景:一条消息既含投诉又含预约字段(如”我要投诉!另外我电话138…明天用车轿车”),codex 逻辑会判 appointment,但**按 W2 投诉应优先**(投诉是更需优先处理的负面信号)。

### 修正

在 classifyStructuredAppointment 之前,先做投诉判断。即顺序改为:

```
classify(tenantId, messages):
  text = inbound消息拼接
  1. 先查投诉(complaint 关键词命中)→ 命中直接返回 complaint(最高优先)
  2. 再 classifyStructuredAppointment → 命中返回 appointment
  3. 再 DB intent_rules(按 W2 优先级:问价 > 预约 > 咨询)
  4. 最后 LLM fallback
```

或更稳妥:让 classifyStructuredAppointment 内部先排除投诉(若文本命中投诉关键词,不走结构化预约直判)。

确认:含投诉的消息,即使带预约字段,也判 complaint。

## 5. 补做:插件启动自动刷新抖音页面(用户问题1)

### 背景

用户验收时数据没上报,原因是忘了刷新抖音页面(插件加载后,已打开的旧页面没注入采集脚本)。

### 需求

插件启动/启用时,**自动刷新当前识别到的抖音页面**(matchPage 命中的标签页),省掉用户手动刷新。

### 实现注意

- 只刷新**识别为抖音目标页**的标签(matchPage 命中的),不要刷新用户所有标签(会很烦)
- 用 chrome.tabs API 找到匹配的标签,chrome.tabs.reload
- 刷新时机:插件 enable / 启动采集时
- 避免循环刷新:刷新后不要因为某种监听又触发刷新。加个标记或只在”启动那一次”刷新
- 这是插件侧改动,确认不影响采集逻辑本身
