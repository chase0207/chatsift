## Task 3 — ④后台提醒前端(核心)

admin 全局(如 MainLayout)加轮询提醒:

- 每 ~30 秒调 GET /api/v1/leads/recent?since=<上次轮询时间>
- 有新线索 → 顶部/角落红点 + 数字(N 条新线索待跟进)
- 可选:新高意向来时提示音(`new Audio(...)`,音量适中)
- 点红点 → 跳线索中心,筛出这些新线索
- since 用上次轮询时间戳,只拿增量,不重复提醒
- 处理过的(status=following)不再提醒

提醒只针对值得跟的(完整预约/高意向/投诉),普通咨询不提醒,避免淹没。

## Task 4 — ① 采集节流(碰 W4 采集,C类,小心)

在 W4 的采集触发处(MutationObserver 回调)加节流:

- MutationObserver 触发后,节流 ~10 秒再执行采集(debounce/throttle)
- 节流期内多次触发只采一次
- **只加节流包装,不改现有采集逻辑**(不动 conversation_id 生成、字段抽取等)

改完做 node –check,真实页面验证不漏采、不重复采、会话仍正确合并(W6.5 的合并别被破坏)。

## Task 7 — 验收

### 7.1 后台提醒(核心,Chase 配合)

```
1. 后台挂着不动(停在某页面)
2. 用 events/batch 造一条完整预约消息(6字段全有效)
3. 计时:~30秒内后台出现红点提醒(N条新线索)
4. 点红点 → 跳线索中心,筛出这条新线索
5. 处理它(改 following)→ 不再重复提醒
6. 造一条普通咨询 → 不提醒(只提醒值得跟的)
```

### 7.2 端到端 SLA 计时(W12 成败标准)

```
制造一条真实预约消息(抖音页面 或 events/batch),
记录:消息产生时间 → 后台提醒出现时间
期望:总耗时 1 分钟左右(远在 5 分钟 SLA 内)
```

### 7.3 时序各段

```
- 采集节流:连续DOM变化,采集~10秒一次(不是每次触发)
- 上报:查上报日志,间隔~15秒或攒满N条
- 轮询:~30秒一次
```

### 7.4 回归(关键:别破坏采集)

```
- 重跑 W4/W5/W6.5:采集准确(不漏不重)、会话仍正确合并(chase不被拆)
- 重跑 W3/W7/W8/W9/W10/W11 核心:分析、诊断未受影响
```

## 重要提示

- **④后台提醒是命门**:前三段再快,客服不刷新看不到也白搭。时间紧时①②③可保守,④必须做
- **轮询不用SSE**:30秒轮询对1-5分钟SLA足够,SSE过度设计,本周不做
- **采集节流碰W4代码(C类)**:只加节流包装,不动采集逻辑;重跑W4/W5/W6.5确认不漏不重、会话仍合并
- **③先评估再改**:LLM调用量被省钱约束压低,可能不积压。真积压才加优先级,不预先重构队列
- **提醒不打扰**:只提醒完整预约/高意向/投诉,普通咨询不提醒,否则被淹没
- **前提页面前台**:准实时依赖抖音页面保持前台打开,写进用户手册(非代码能解决)
- **端到端计时是成败标准**:不只验单段,要计时”消息产生→提醒出现”全程
- **不要改chat_rpa**(只读参考)
