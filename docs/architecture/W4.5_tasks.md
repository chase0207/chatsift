# W4.5:修复 /api/platforms 500

> **背景**:W4 验收时发现服务端 `/api/platforms` 返回 500,当时执行端在插件 background 里加了抖音平台定义兜底,让验收得以继续。但服务端这个 500 是真实缺陷,只是被插件兜底盖住了。W6 做后台时后台也会调这个接口,500 会再暴露。趁现在修掉。
> 
> **风险等级**:C 类(动已验收的 W1 服务端代码)。必须谨慎:先诊断真实病因,再小步修,修完重跑 W1 相关验收确认没碰坏别的。
> 
> **重要**:本任务分两阶段。**阶段一只诊断不修**,把病因回报给 Claude;Claude 确认病因后给阶段二的修复方案。不要在没确认病因前就动手改。

## 阶段二:修复(病因已确认 — 方向 A 迁移遗漏)

> **病因**(阶段一已确认):platformController.js 调用 `normalizePlatformKey` + `extractDetectHosts`,但 chatsift 的 utils/platforms.js 只迁了 `normalizePlatformKey`,漏了 `extractDetectHosts` 和 `getPlatformAliases`。
> 
> **修复决策**:整文件补齐(三个函数全迁),但补之前必须先排查 normalizePlatformKey 的行为变更影响(见 Fix Task 1)。

### Fix Task 1 — 先排查 normalizePlatformKey 的调用方(关键,先做这步)

chatsift 当前的 normalizePlatformKey 和 chat_rpa 的**行为不同**:

- chatsift 当前版:`return String(platform||'').trim().toLowerCase()` —— 原样返回小写
- chat_rpa 版:`return PLATFORM_ALIAS_MAP[value] || value` —— 会把 douyin_dm/life_douyin 等别名归一成 douyin

如果整文件覆盖,normalizePlatformKey 行为会变。必须先查清楚 chatsift 里还有谁依赖它的当前行为:

```bash
cd ~/vscode/chatsift
grep -rn "normalizePlatformKey" server/src/
```

把结果回报。对每个调用点判断:它期望的是”原样小写”还是”别名归一”?

- 如果调用点只有 platformController.js 自己(且它本来就是 chat_rpa 迁过来的,期望别名归一行为)→ 安全,可以整文件覆盖
- 如果有 W1/W2/W3 的已验收代码调用了它、且依赖”原样小写”行为 → **停下回报**,不能直接覆盖,要改用更保守的方案(见下方”保守备选”)

### Fix Task 2 — 整文件补齐 utils/platforms.js

确认 Fix Task 1 安全后,用 chat_rpa 的完整版覆盖 chatsift 的 utils/platforms.js:

```bash
# 整文件迁移(chat_rpa 只读,复制其内容到 chatsift)
cp ~/vscode/chat_rpa/server/src/utils/platforms.js server/src/utils/platforms.js
node --check server/src/utils/platforms.js
```

覆盖后该文件导出三个函数:normalizePlatformKey(含别名映射)、getPlatformAliases、extractDetectHosts。

**保守备选**(仅当 Fix Task 1 发现行为冲突时用):不覆盖,只在现有 platforms.js 追加 extractDetectHosts 和 getPlatformAliases 两个函数,normalizePlatformKey 保持 chatsift 当前实现不动。这样 500 能修,且不改变已被依赖的 normalizePlatformKey 行为。

### Fix Task 5 — 处置插件侧兜底

服务端修好后,W4 时加的”插件 background 抖音平台兜底”如何处理:

**保留**。理由:它现在是一层降级保险(服务端万一再挂,插件仍能用兜底的平台定义工作),无害。但要在代码注释里标明”这是 W4.5 前的服务端 500 兜底,服务端已修复,此为降级保险”,避免以后有人误以为平台定义只能从这里来。不要撤掉,撤掉等于减少一层容错。
