# W6.5:修复会话未合并

> **现象**:会话列表里,同一个客户(chase)在抖音同一平台、同一 private-message 页面,出现了**三条独立会话**(98 条 / 18 条 / 16 条消息)。按产品设计,同一客户在同一平台的对话应合并为**一条**会话,消息累加。
> 
> **根因推断**:会话去重靠 conversations 表的唯一键 `(tenant_id, platform, platform_conversation_id)`。三条没合并,说明同一个 chase 会话的 `platform_conversation_id` 每次采集都不一样 —— 即**插件侧 conversation_id 生成不稳定**。抖音来客会话项 DOM 大概率没有稳定会话 ID(class 是随机串,和 message 一样),adapter 可能用了不稳定的东西当 conversation_id。
> 
> **重要澄清**:W6 的页面没有 bug,它只是如实显示了 W4 采集时就已拆开的数据。要修的是**采集侧的 conversation_id 生成**,不是 W6 页面。修好采集后,页面自然显示为合并。
> 
> **风险**:C 类(动 W4 已验收的采集 adapter)。**本任务是阶段一:只诊断不改**。查清 conversation_id 真实生成逻辑后回报,Claude 给阶段二修复方案。

## 阶段二:修复(已据诊断确认,三处修复)

> **诊断结论**:根因是 legacy-collector 的 `_buildSessionInfo()` 用”昵称+头像URL+URL参数”hash 成 conversationId,头像 URL 波动导致同一 chase 被拆成 3 条。
> 
> **三处修复(已定)**:
> 
> 1. conversation_id 改用 `platform + platform_page + nickname` 稳定组合(去掉头像)
> 1. 清空测试数据,用修好的采集重采
> 1. completeness 改成”按会话累计字段(只增不减)”,不再只看最新 5 条被覆盖
> 
> **不改**:intent “报名优惠” 优先级冲突 —— 记为观察项,本周不动(见末尾)。
> 
> **风险**:修复 1 动 W4 采集(C类),修复 3 动 W3 completeness 核心逻辑(C类)。改完必须重跑 W3/W4 验收。

### Fix Task 1 — 改 conversation_id 生成(去掉头像)

改 `plugin/runtime/legacy-collector.js` 的 `_buildSessionInfo()`:

```js
function _buildSessionInfo(adapter) {
  var nickname = _readNickname(adapter)
  var pageKey = adapter && adapter.pageKey ? adapter.pageKey : 'douyin'
  // 只用 platform + page + nickname 做稳定 seed,不再用 avatar / URL 参数
  var seed = [pageKey, nickname].join('|')
  return {
    conversationId: 'douyin_' + pageKey.replace(/[^a-z0-9]+/ig, '_') + '_' + Dom.simpleHash(seed),
    nickname: nickname,
    pageKey: pageKey,
  }
}
```

关键改动:

- seed 去掉 `avatar`、`_param('conGroupId')`、`_param('lifeAccountId')`、`_param('accountId')`,只留 `pageKey + nickname`
- 同一个客户(同昵称)在同一页面,无论采集几次,seed 都一样 → conversationId 稳定 → 服务端按唯一键合并

注意:

- `_readNickname` 本身要稳定。如果昵称偶尔读到 ‘unknown’(选择器没命中),也会导致拆分。确认 _readNickname 在真实页面能稳定读到 chase,读不到时不要用 ‘unknown’ 兜底入库(那会把所有读取失败的会话合并成一条 unknown)。如果读到 unknown,这次采集应跳过,不上报
- 三个 adapter 的 toConversationEvent 里的 fallback(`'douyin-private-' + hash(nickname||location.href)`)也要同步:fallback 不要用 location.href(它带 query 会变),改成只用 nickname

### Fix Task 3 — completeness 改为按会话累计字段(改 W3 核心逻辑)

这是本次最重要、风险最高的改动。当前 analyzer 每次只取最新 5 条 inbound,导致早期的关键信息(电话/地址)被后续寒暄挤出窗口、completeness 被覆盖回 0。

改法:**字段累计,只增不减**。某字段一旦在会话历史里被抽到,就持久化,后续分析不会因为没提到而清空。

具体实现(两个选择,选 A):

**选择 A(推荐):completeness 抽取范围从”最新5条”改为”全部 inbound 历史”。**

改 `server/src/v1/analyzer.js` 取上下文的 SQL,completeness 分析时不再 LIMIT 5,而是取该会话**全部 inbound 消息**:

```js
// 原:ORDER BY occurred_at DESC LIMIT 5
// 改:completeness 用全量 inbound(intent 仍可只用最新5条)
WHERE tenant_id = ? AND conversation_id = ? AND direction = 'inbound' AND content_text IS NOT NULL
ORDER BY occurred_at ASC
// 不 LIMIT,或 LIMIT 一个大值(如 500)防极端
```

这样字段抽取看的是整段对话,早期给的电话/地址不会丢。实现简单,且天然”累计”(全量里有就抽得到)。

注意:intent 分类可以仍用最新 5 条(意图看近期更合理),completeness 用全量。两者上下文范围可以不同。

**选择 B(更省但复杂):字段持久化到 conversation。** 每次抽到的字段存进 conversations 表新增的 JSON 字段,新分析只做”补充”不做”覆盖”。这个要加表字段、改写入逻辑,比 A 复杂。**本周用 A,B 留作未来优化。**

改完验证那条预约信息:chase 重采后,含”刘思奇/电话13913972023/普陀区/轿车”的会话,completeness 应该不再是 0(若意图判为 appointment 应约 60,若 price_inquiry 应约 50)。
