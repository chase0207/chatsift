# PRD-A 增补：自动巡检器（AutoScanner）

> 增补文档，对《PRD-A 消息抓取引擎》的补充，不替换原文
> 模块定位：PRD-A 新增子模块，员工离岗时段自动点开红点会话并滚动采集，不参与回复
> 前置阅读：PRD-A 主体（§3 组件、§4 回复下发、SessionSnapshot 结构）
> 版本：v1.0 / 2026-05

---

## 1. 背景与目标

### 1.1 背景

PRD-A 的现有采集逻辑只能抓取「当前打开的对话窗口」中可见的消息。员工白天上班时，会手动点开红点会话查看回复，采集自然发生；员工下班离岗后，抖音自带的「平台 AI 客服」会自动回复客户，但 chatsift 插件无法自动点开未读会话，导致离岗时段的对话内容无法被 chatsift 采集。

### 1.2 目标

在员工离岗时段，由插件自动完成"点开红点会话 → 滚动加载 → 等待采集完成 → 切下一个"的动作，让 PRD-A 现有的采集逻辑能覆盖到无人值守时段的对话。

### 1.3 边界（重要）

**本模块只采集，不回复。**

- 不入 SessionQueue。
- 不调用模块 B。
- 不发送任何回复。
- 离岗时段的回复完全交给抖音平台自带的 AI 客服。

本模块本质是一个「自动制造点开和滚动动作」的巡检器，让现有采集链路能在无人值守时段继续工作。

## 2. 与现有模块的关系

```
现有 SessionDetector（实时监听）  ←─ 员工在岗时段
         ↓
   员工自己点开会话 → 现有采集逻辑 → SessionSnapshot

新增 AutoScanner（巡检模式）       ←─ 员工离岗时段
         ↓
   自动点开红点 → 滚动 → 等采集 → 下一个
         ↓
   不入 SessionQueue，仅写 SessionSnapshot.scan_status
```

两条采集路径**共用 SessionSnapshot**，互不冲突。AutoScanner 不会触发回复流程。

### 2.1 与"红点 ≠ 新消息"原则的关系

PRD-A 主体强调「红点不可靠，新消息由 DiffEngine 判定」。本模块不与该原则冲突：

- 红点：用作**"需要点开采集的候选信号"**
- 新消息：仍由 DiffEngine 判定（PRD-A §3.5），不变

也就是说：**红点 = 巡检候选**，**新消息 = Diff 判定**。AutoScanner 只负责把红点会话的内容拉到视野内，是否产生 Diff、是否触发其他动作，由现有逻辑决定。

## 3. 激活机制（三层开关）

采用「总开关 + 定时开关 + 条件激活」组合策略。

### 3.1 三层开关结构

```
总开关（手动主控，默认关闭）
   ↓ 开启后才生效
定时开关（设定工作时段，例如 09:00-18:00）
   ↓ 非工作时段 OR 条件激活满足
条件激活（最后人工操作 N 分钟无动作，N 默认 15 分钟）
   ↓
AutoScanner 进入巡检模式
```

### 3.2 三层开关的作用

| 开关 | 作用 |
|---|---|
| 总开关 | 员工的最终控制权（临时加班、调试时可一键关闭） |
| 定时开关 | 下班自然激活，白天不打扰 |
| 条件激活 | 处理两个边缘情况：① 员工早退 / 午休离开；② 防止员工在场时插件抢操作 |

### 3.3 配置项

| 配置 | 默认值 | 说明 |
|---|---|---|
| 总开关 | OFF | 主开关 |
| 工作时段 | 09:00 - 18:00 | 此时段内不激活（除非"无操作 N 分钟"触发）|
| 无操作阈值 N | 15 分钟 | 检测到该时长无人工操作即激活 |
| 凌晨兜底时间 | 02:00 | 见 §6 |

所有配置项支持插件设置页面修改。

### 3.4 人工操作互锁（关键）

AutoScanner 运行中如果检测到**人工操作**（鼠标移动、点击、键盘输入），**立即暂停巡检**，等再次满足激活条件后恢复。

**理由**：员工坐回来看到鼠标自动移动会受到惊吓，且会与员工操作冲突。

**暂停规则**：

- 检测到人工操作 → 立即停止当前动作（点开/滚动/等待）。
- 当前会话标记 `scan_status = partial`，纳入下一轮巡检或凌晨兜底。
- 重新进入"无操作 N 分钟"倒计时。

### 3.5 激活/退出状态机

```
disabled（总开关关）
   ↓ 总开关 ON
idle（待机）
   ↓ 进入工作时段
working_hours（工作时段，不激活）
   ↓ 离开工作时段 OR 无操作 N 分钟
scanning（巡检中）
   ├─ 检测到人工操作 → idle / working_hours
   └─ 红点全部扫完 → standby（空闲守候，等新红点）
```

## 4. 巡检流程

### 4.1 单轮巡检完整流程

```
[1] 激活条件满足，进入 scanning 状态
    ↓
[2] 扫描会话列表，收集所有带红点的会话节点
    ↓
[3] 按"从下到上"顺序排序（最旧的先扫，见 §4.2）
    ↓
[4] 取队首会话，点开它
    ↓
[5] 滚动消息区到底部（不点"加载更多"按钮，到底即停）
    ↓
[6] 等待"消息加载完成"信号（见 §4.3）
    ↓
[7] 信号触发后再等 3-5s 缓冲，让 PRD-A 现有采集逻辑抓取
    ↓
[8] 校验采集是否成功（见 §4.4）
    ├─ 成功    → SessionSnapshot.scan_status = scanned
    ├─ 部分成功 → scan_status = partial（待重扫）
    └─ 超时    → scan_status = failed（待重扫）
    ↓
[9] 切到下一个红点会话，回到 [4]
    ↓
[10] 队列处理完 → 进入 standby（空闲守候）
     新红点出现时由 SessionDetector 触发新一轮巡检
```

### 4.2 红点处理顺序：从下到上（最旧先扫）

抖音平台对长时间未响应的会话可能有**自动关闭机制**——若先扫最新的会话，最旧的红点可能在排队等待时被平台自动关闭，错失采集。

**规则**：按会话在列表中的位置，从下到上依次处理（最旧的优先）。

> 注：此顺序与 PRD-A §3.6 SessionQueue 的"时间轮转"调度不同——SessionQueue 是为回复设计的（防队尾饿死），本模块是采集，规避超时关闭是首要目标。

### 4.3 消息加载完成信号（A+B 组合）

| 信号 | 机制 | 优先级 |
|---|---|---|
| **A. DOM 稳定检测**（主） | 监听消息区 DOM 变化，连续 1.5 秒无新增节点即视为加载完成 | 通用、兜底 |
| **B. 平台特定信号**（辅） | 检测"加载更多"文案出现、"没有更多消息"标识、loading spinner 消失 | 加速判定 |

**判定逻辑**：A 与 B 任一触发即视为完成。B 命中可立即结束等待，无需熬完 A 的 1.5s。B 的具体选择器纳入 PlatformAdapter 配置（DouyinAdapter 需补充）。

**超时**：信号未触发的兜底——单会话等待超过 30 秒强制退出，标记 `scan_status = failed`，跳到下一个，进入凌晨兜底重扫。

### 4.4 采集成功校验

校验依据：对比本次采集前后的 SessionSnapshot。

| 判定 | 条件 |
|---|---|
| `scanned`（成功） | 本次采集到的最新消息时间 ≥ 会话列表显示的末条消息时间 |
| `partial`（部分） | 采集到部分新消息，但仍有更新的消息未抓到（DOM 显示有但未入库） |
| `failed`（失败） | 完全未采集到新消息，或加载信号超时 |

`partial` 与 `failed` 都纳入下一轮/凌晨兜底重扫。

## 5. SessionSnapshot 字段扩展

复用 PRD-A §3.4 的 SessionSnapshot，新增 3 个字段：

```
SessionSnapshot {
  // ===== 原有字段（PRD-A §3.4）=====
  session_id
  last_message_text
  last_timestamp
  unread_count
  processed
  status
  snapshot_at

  // ===== 新增字段（本模块）=====
  last_scanned_at       // 上次成功采集的时间
  last_scanned_msg_id   // 上次采集到的最后一条消息 ID
  scan_status           // never | scanned | partial | failed
}
```

**字段语义**：

- `last_scanned_at`：上次 AutoScanner 成功采集（或人工触发后采集）的时间戳。
- `last_scanned_msg_id`：上次采集到的最末条消息 ID，用于增量判断与重扫校验。
- `scan_status`：本次采集状态，凌晨兜底回扫据此筛选。

存储位置不变，仍走 `chrome.storage.local`（持久化，防掉线丢失）。

## 6. 凌晨兜底回扫

### 6.1 触发

每日 **02:00**（可配置）启动一次兜底回扫。

### 6.2 回扫对象

从 SessionSnapshot 筛选符合任一条件的会话：

- `scan_status = partial`
- `scan_status = failed`
- `last_scanned_at` 距今超过 24 小时（防止某些会话长期遗漏）

### 6.3 回扫动作

复用 §4 的单轮巡检流程，对筛出的会话依次"点开 + 滚动 + 等待 + 校验"，更新 SessionSnapshot。

### 6.4 与三层开关的关系

凌晨 02:00 一般落在「定时开关」的非工作时段内，自然激活。若总开关被关闭，则跳过该日凌晨回扫并记录日志。

### 6.5 限流

凌晨回扫如果待扫会话过多（如 > 50 个），分批处理：单批 ≤ 20 个，批间休息 5 分钟，避免高频操作触发平台风控。

## 7. 异常处理

| 异常 | 处理 |
|---|---|
| 点开会话失败 | 重试 1 次；仍失败 → `scan_status = failed`，跳下一个 |
| 滚动卡住 / 无响应 | 30 秒超时退出 → `failed` |
| 消息加载信号未触发 | 30 秒超时 → `failed` |
| 检测到人工操作 | 立即停止 → 当前会话 `partial`，AutoScanner 退出 scanning |
| 检测到掉线（LoginMonitor 触发）| 立即停止巡检，与 PRD-A §3.8 流程一致 |
| 单轮巡检中红点会话数异常多（> 100）| 告警 + 限流分批 |

**告警通道**：扩展桌面通知 + 本地日志（与 PRD-A §5 一致，任何环节不静默失败）。

---

## 8. 风控相关

AutoScanner 是本期对平台操作频率影响最大的模块（密集点开多个会话），需特别注意：

- 单次巡检内，点开会话之间随机延迟 3-8 秒。
- 滚动动作模拟真人——分多次小幅滚动，非瞬间滑到底。
- 单账号每分钟操作上限继续遵守 PRD-A §4 的 ≤15 次。
- 凌晨回扫的分批限流（§6.5）。
