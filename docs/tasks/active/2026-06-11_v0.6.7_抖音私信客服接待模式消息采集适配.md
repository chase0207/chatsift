## 2. 技术方案

### 2.1 当前代码路径

当前 `plugin/adapters/douyin/private-message.adapter.js` 的 `getMessages()` 有两条路径:

1. life 私信页主路径:
   ```js
   Dom.queryAll('div[class*="my-4"]')
   ```
   命中后走 `_scanLifeMessages()`,并从 `px-3/py-2` 等节点提取文本。

2. 老版气泡兜底:
   ```js
   incomingBubble / selfBubble
   ```
   当前覆盖 `chatd-bubble-*`、`bubble other/self`、`msg-item left/right`。

场景③的 `csUI-*` DOM 不属于以上两类,所以会扫描成功但消息数为 0。

### 2.2 三场景关键 DOM 对比

| 关键 DOM 点 | 当前代码 | ① 官号-客服模式 | ② 官号-私信模式 | ③ 客服-接待模式 | 结论 |
|---|---|---|---|---|---|
| 顶部模式 | 不依赖模式文案 | `客服模式` | `私信模式` | `当前咨询 / 历史咨询` | 不作为采集判断主依据 |
| 会话列表 | `[class*="conversationItem-"]` | 有 | 有 | 有 | 三者会话列表均可识别 |
| 当前会话 | `[class*="conversationActiveItem"]` | 有 | 有 | 有 | 三者当前会话均可识别 |
| 会话昵称 | `[class*="conversationName"]` | 有 | 有 | 有 | 三者昵称均可识别 |
| 未读标识 | `byted-badge-sup-show` / `newConv` | 有 | 有 | 有 | 三者红点识别材料已补齐 |
| 消息主容器 | `div[class*="my-4"]` | 有 | 有 | 新补充样本有 | ①②③新样本均命中 |
| 文本节点 | `px-3 + py-2` | 有 | 有 | 新补充样本有 | ③新样本不支持“只因 csUI 导致 messages:0”的单因解释 |
| csUI 消息节点 | 当前未覆盖 | 无 | 无 | 早期样本疑似有;新补充样本未见真实 DOM class | 需 CC4 先复核,不得直接按 csUI 写死 |
| csUI 方向 | 当前未覆盖入口 | 无 | 无 | 新补充文件中仅人工说明文字出现 | 不足以作为代码依据 |
| csUI 文本 | 当前未覆盖 | 无 | 无 | 新补充文件未见真实 `csUI-Text` | 不足以作为代码依据 |
| csUI 时间段 | 当前未覆盖 | 无 | 无 | 新补充文件未见真实 `csUI-MsgTimeGap`;实际时间条为 `px-4 text-xs text-center text-gray-2 my-4` | 不足以作为代码依据 |

### 2.3 实现策略

采用「平台-页面-场景」的轻量路由,但本任务不抽通用框架,只在 `douyin/private-message` adapter 内落地。

由于 2026-06-12 新证据推翻了“客服接待模式一定是 csUI DOM”的前提,实现顺序改为:

1. 先补诊断日志和场景识别,明确当前命中的 `scene` / `scanner` / `message_dom_count` / `reason`。
2. 若真实 DOM 为 `my-4`,优先修 `life/my-4` 在该场景下的漏扫或 `position re-align` 跳过问题。
3. 只有当真机再次确认真实 DOM 存在 `csUI-MessageItem` / `csUI-Text` 时,才新增 `csUI` scanner。
4. 未确认前,禁止直接把 `agent_reception_mode` 固定路由到 `csUI`。

```text
platform = douyin
page = private-message
scene = official_customer_mode / official_private_mode / agent_reception_mode / unknown
scanner = scene 对应的消息扫描器
```

原则:
- 场景识别优先看结构特征,不依赖顶部文案。
- ①② 已稳定的 `my-4` 路径不重构、不改输出契约。
- ③ `agent_reception_mode` 先识别真实消息 DOM,再选择 `life/my-4` 或 `csUI`。
- `unknown` 场景进入兜底:先 `my-4`,结果为空再 `csUI`,最后旧 bubble。

建议函数边界:

```text
_detectMessageScene()
_scanLifeMessages(items, collectAt)       // 现有路径
_scanCsuiMessages(items, collectAt)       // 新增路径
_scanLegacyBubbleMessages(collectAt)      // 现有兜底,如当前没有独立函数可不强拆
```

场景路由:

```text
official_customer_mode / official_private_mode -> my-4 / life scanner
agent_reception_mode                          -> detected dom_family -> life/my-4 或 csUI scanner
unknown                                       -> fallback chain
```

如真机确认存在真实 `csUI` DOM,再新增 `csUI` 消息扫描函数:
   ```text
   _scanCsuiMessages(items, collectAt)
   ```

`csUI` 消息节点:
   ```text
   div[class*="csUI-MessageItem"]
   ```

方向判定:
   ```text
   csUI-NormalMessage_right → outbound
   csUI-NormalMessage_left  → inbound
   ```

文本提取优先级:
   ```text
   .csUI-Text
   .csUI-TextLink_text
   .csUI-LeadsCard_card_title
   .csUI-LeadsCard_card_points_point
   .csUI-LeadsCard_card_btn
   ```
   原则:先保证可读文本入库;卡片结构化不在本任务范围内。

时间段识别:
   ```text
   .csUI-MsgTimeGap
   ```
   扫描 DOM 时维护最近一个时间分隔,作为后续消息的 `segment_at`。

逐条时间处理(W17 红线):
- `csUI` scanner 必须为每条消息产出 `time_meta` 或 `timestamp`,不能只产出 `segment_at`。
- 能读到逐条精确时间时,按 `_resolveOccurredAt()` 现有逻辑解析并写入 `time_meta`。
- 读不到逐条精确时间时,必须对齐 life scanner 的继承策略:继承上一条消息时间 `+1s`;会话开头无上一条时,才使用最近的 `csUI-MsgTimeGap` / 时间分隔锚点 `+1s`。
- 禁止让 inbound 消息退回 `_normalizeOccurredAt(undefined)` 或采集当刻,不得用采集当刻冒充消息时间。
- 若 `csUI` DOM 无法提供可用时间锚点且无法继承,触发 Stop Gate,停下回报,不要硬采。

raw_payload 标记:
   - `selector: 'csui-message-item'`
   - `time_source: 'csui-divider'` 或 fallback
   - `segment_at`
   - `time_estimated`

v0.6.7 最终实现目标:

```text
douyin/private-message/agent_reception_mode/life-my4 -> 复用现有 life scanner
douyin/private-message/agent_reception_mode/csUI     -> 新增 csUI scanner
douyin/laike-message/reception                       -> 不在本任务改,暂定 v0.6.8
```

### 2.4 后续架构约束

后续扩展更多平台时,应先提炼统一的「平台-页面-场景」前置模型,再实现页面采集逻辑:

```text
PlatformAdapter
  -> PageAdapter
    -> SceneDetector
      -> ScannerStrategy
```

建议统一字段:

| 字段 | 示例 | 用途 |
|---|---|---|
| `platform` | `douyin` | 平台隔离 |
| `page` | `private-message` | 页面隔离 |
| `scene` | `agent_reception_mode` | DOM 结构差异路由 |
| `scanner` | `csui` / `life` | 消息扫描策略 |
| `confidence` | `high` / `medium` / `fallback` | 诊断日志与回退判断 |

本次 v0.6.7 只做抖音私信内的轻量实现,但命名、日志和函数边界要对齐该模型,避免后续扩平台时继续把 DOM 差异写成散落 fallback。

### 2.5 不变量

- 不改变 `legacy-collector` 的 position 分配与 `message_id` 合成。
- 不改变 server 去重键。
- 不触碰采集权闸门。
- 不新增发送/输入/点击逻辑。

### 5.1 开工前证据核对(诊断先行 —— scene / dom_family / scanner / message_dom_count / reason)

对用户提供的样本逐份核对(grep 结构标记 + console 实证):

| `官号-私信模式_location+dom.txt` | official_private | **life-my4** | life | my-4=20 / 文本节点 12 | 当前可采,无问题 |
