## 5. 技术方案(CC4,plan-only)

> 阶段:仅技术方案,不写业务代码。以下含一个**对 PM 原始建议的修正**(§5.4):单纯 `max+1` 续编会把可见历史重复入库,必须配 **re-align**。

### 5.0 现状与根因(代码核对)
| 本地态 | 现 storage key | namespace 现状 | 问题 |
|---|---|---|---|
| `seen`(已采 message_id 集) | `chatsift_event_seen_ids`(`event-collector.js`) | **全局,零 namespace** | 跨会话/租户/环境全部串用 → 切租户重采同会话历史被 skip |
| `PositionTracker`(`{nextPos, seq}`) | `w17_pos_{conversationId}`(`position-tracker.js` STORAGE_PREFIX) | 仅 conversationId(含 account_biz_id,**不含 tenant/env**) | ① 同抖音账号被两个 chatsift 租户采 → 同 key 串号;② test/prod 串号;③ 冷启动 `seq` 空 → 从 `pos:0` 重编 → 撞库历史 position → 新消息 `duplicated` 吞 |
| `queue`(待传事件) | `chatsift_event_queue`(`event-queue.js`) | 全局 | 切 env/账号后旧事件会被发到新环境/新租户 |
- message_id = `syn_hash(conversationId|position)`(`dom-utils.js synthMessageId` position 路径);position 由 `legacy-collector.js:124-130` `PositionTracker.assign` 赋值并重写 message_id。server 去重键 = `(tenant_id, platform_message_id)`(`eventsController.js`)。
- 根因共性:**客户端持久采集态命名空间只到浏览器 profile**,不含 env/tenant。详见复盘报告 §5/§5A/§5B。

### 5.1 namespace 设计(持久采集态)
- **颗粒度**:`env` + `tenant_id` + `account_biz_id`(+ `conversation_id` 给 position)。
- **持久态不含 `tab_id`**(tab 级是运行实例态,属 `collect_instances` 心跳,本任务不动);env/tenant/account 唯一确定一份持久采集态。
- **seen key**:`chatsift_seen_{envHash}_{tenant}_{accountBizId}`(每"环境+租户+客服账号"一个 Set)。
- **PositionTracker key**:`w17pos_{envHash}_{tenant}_{conversationId}`(conversationId 已含 account_biz_id;再叠 env+tenant 防跨租户/跨环境串)。
- 缺失兜底(fail-closed,**宁可不串、可重号**):`tenant` 缺 → `t0`;`accountBizId` 缺 → `aNA`;`envHash` 缺 → `e0`。不同上下文绝不复用同一 key。

### 5.2 环境隔离:用 normalized serverUrl 的 hash(不靠显示文案)
- `envHash = Dom.simpleHash(normalize(cfg.serverUrl))`;`normalize` = 去尾斜杠 + 小写。**只读持久化的 `cfg.serverUrl`,不读内存 AUTO_ENV/badge 文案**(后者正是 v0.6.4 修过的"会误回 prod"的不可靠态)。
- 用 hash 而非原串:避免 key 含 `://`、`.`、过长;长度可控、稳定。

### 5.3 tenant_id / account_biz_id / conversation_id 获取
- **tenant_id**:`userInfo.tenant_id`(chrome.storage;`authController` 登录响应 `data.userInfo.tenant_id` 已返回、background.js 已存)。旧 token 无 userInfo → 调 `/api/auth/verify`(已存在,返回 userInfo)补;再失败 → `t0` 兜底。**internal 用户 tenant_id=NULL → `t0`**(平台方一般不采集,可接受)。
- **account_biz_id**:URL `accountId`(`adapter._readAccountBizId`)/ `sessionInfo.accountBizId`。
- **conversation_id**:adapter 合成 `douyin-private-{accountBizId}-{hash(accountBizId|nickname)}`(已含 account_biz_id),沿用不改。

### 5.4 ★冷启动续编:server 只读接口 + re-align(**修正 PM 的 max+1 方案**)
- **问题**:若冷启动只取 `MAX(position)` 并把当前可见消息从 `max+1` 重编 → 可见的"历史消息"拿到全新 position → message_id 变 → server 视为新消息 **重复入库**(违反 W17"有几条存几条/幂等",触 §3 stop gate)。**故必须 re-align**:让 PositionTracker 把可见 DOM 历史**对齐回它们已入库的旧 position**,只有真·新消息才续编 `max+1`。
- **新接口(只读)**:`GET /api/v1/conversations/position-state`
  - 参数:`platform`、`platform_page`、`conversation_id`(= 客户端 conversationId = `platform_conversation_id`)、`limit`(默认 ~30,覆盖一个 DOM 窗口)。
  - 鉴权:复用 `auth` + `perm('conversation:list')`;tenant 由 JWT(`scope()` 同口径),**只能查本租户**。
  - 逻辑:按 `(tenant_id, platform, platform_page, platform_conversation_id)` 找 conversation;返回 `{ found, max_position, recent: [{ direction, content_text, position }] }`(按 position 倒序取最近 limit 条)。**纯 SELECT,不建账号/不写库/不改 lifecycle**(同 W20.1 只读口径)。
  - route 落点:`server/src/routes/v1/conversations.js`(已有 `conversation:list`)。
- **客户端冷启动**(`PositionTracker.assign` 内,当 `seq` 为空时):
  1. 调接口拿 `{max_position, recent}`;
  2. 用 `recent` 逐条算 `keyOf(direction, content_text)` 重建 `seq = [{k, p}]`、`nextPos = max_position + 1`;
  3. 走原 `findOffset` 锚点窗口对齐当前 DOM → **命中的历史复用旧 position(幂等)、prepend 的更早消息/底部新消息按 `nextPos` 续编**;
  4. 之后逻辑与现状一致。
- **退化/失败**:接口 `found=false`(新会话)→ 空 `seq` 从 0(空库不撞,安全);网络失败 → **本轮跳过该会话采集 + 记 degrade 日志**(不冒险从 0 撞号),下轮重试。退化策略列为 review 决策点。

### 5.5 queue/batch 是否隔离 — 结论
- **结论:queue 不做持久 namespace 隔离,但必须在"上下文切换"时 flush。**
- **证据/理由**:`event-uploader.tick()` 上传时实时读 `cfg.serverUrl`+token;queue 里的事件不带目标环境/租户。一旦 env/账号切换,残留 queue 会被发往**新环境/新租户**(错配、可能误入库到错租户)。queue 是**短时上传缓冲**(上传即清),无需长期分租户保留。
- **方案**:在 `cycleEnv`(切环境)、`login`(切账号/重登)、`logout`、`START_PLATFORM`(切目标账号)时 **flush `chatsift_event_queue` + 重置 seen 句柄到新 namespace**(seen 不清库,只切到新 key)。次选(更重、不推荐):queue 也加 namespace 前缀。
- 注:queue flush 是丢弃**未上传**的缓冲,不丢已入库数据;丢弃的会在下次扫描重新采到(经 re-align 不重复)。

### 5.6 旧 key 兼容/迁移
- 旧 key:`chatsift_event_seen_ids`、`w17_pos_{conversationId}`、`chatsift_event_queue`。
- **策略:不迁移、一次性弃用**。理由:旧 key 本身就是"跨上下文污染源",迁移=把污染带进新命名空间。v0.6.5 新逻辑**只读写新 key**,不再读旧 key:
  - 旧 seen 弃用 → 最多让历史多几次 `duplicated` 上传(server 幂等,无害,0 重复入库)。
  - 旧 position 弃用 → 触发 §5.4 冷启动 re-align(已设计为幂等)。
  - 旧 queue 弃用 → 残留旧事件丢弃(下次重采)。
- 旧 key 的物理清理**可选、非必须**(不作为正式修复手段——§3 stop gate"禁止清 storage 作为修复");如做,仅一次性删旧 key,不删新 key。

### 5.7 对 W17 / W20 / W21 的影响(均不触 stop gate)
- **W17**:**不改** message_id 合成规则、不改 server 去重键、不改 messages schema。position 语义不变;re-align 保证"有几条存几条 + 重复连发各自 position 不同 + 跨采集幂等"。✓
- **W20**:采集权闸门/collect-permission 不动;新接口只读、tenant-scoped、不碰 SA/lifecycle。v0.6.4 `forgetSeen` 在 namespaced seen 上继续生效(改的是 key,不是逻辑)。✓
- **W21**:`collectNow` 仍走 `legacy collectMessageSession → PositionTracker.assign`(namespaced 后)→ position 规则一致;自动切换开关/人工互锁不受影响。✓
