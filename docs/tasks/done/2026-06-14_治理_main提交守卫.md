## 1. PM 指令

### 用大白话讲:这个守卫是干嘛的,和前两个有什么不一样

A1、A2 是"体检"——只看、只报告,从不阻止你做任何事。

**A3 不一样:它会真的拦住提交。** 规则是"业务代码(server / admin / plugin 里的东西)不能直接提交到 main,必须先走分支、过审查再合并"。这个守卫就是来执行这条规则的门卫:谁想把业务代码直接塞进 main,它当场把这次提交挡下,并提示"请走分支"。

放行的:文档、治理脚本、配置这类改动——它们本来就允许在 main 上动,门卫不拦。

### 为什么这张单的重心是"先验证,后生效"

一个会拦提交的门卫,最怕两件事:**该拦的没拦**(形同虚设),和**不该拦的也拦了**(误伤,正常工作被卡死)。所以本任务**先让它"只报警不真拦",在测试分支上验证它拦得准、放得对,你亲眼确认后,才切成"真拦"并正式挂上去。** 安装很容易,验证才是关键。

### 这个守卫只在你本机生效,会不会很危险

不会。它是 git 的 pre-commit 钩子,只在**提交那一刻**本地检查一下,**只读、不改任何代码**,不通过就拒绝这次提交、让你换条路(走分支)。而且本任务要求留一个**应急放行开关**:万一哪天它误伤、又急着提交,你或 cc 能一句话临时绕过,绝不会把你卡死。

### 目标

新增一个 pre-commit 守卫:阻止 server/admin/plugin 业务代码直接提交到 main;放行文档/治理改动;先 dry-run 验证、确认后再启用;带应急放行。

### 范围(只做这些)

写守卫脚本 + 验证 + 挂上 pre-commit + 写一行说明。**不碰任何业务代码,不改其他规则正文。**

### 文件边界

- **允许改 / 新增**:
  - 新增 `scripts/guard-main-commit.sh`(守卫逻辑,只读判断)
  - 新增或改 `.husky/pre-commit` 或 `.git/hooks/pre-commit`(把守卫挂上;用仓库现有 hook 方案,不引入新依赖)
  - 在 `docs/ops/server-access.md` 或 `release.md` 加**一行**说明守卫规则 + 应急放行怎么用
- **禁止改**:server/admin/plugin 任何业务代码、任何规则正文、任何已验收的脚本逻辑。

### 上位规则

- 本任务单不覆盖 `AGENTS.md`、`PROJECT_STATUS.md`、`docs/ops/prod-safety.md`。如有冲突,停下回报。

## 2. 执行步骤

1. **写守卫逻辑 `scripts/guard-main-commit.sh`(只读判断,不改文件):**
   - 仅当**当前分支是 main** 时才检查;在其他分支上一律放行(分支本来就是用来写业务代码的)。
   - 取本次提交涉及的文件清单,若其中**有任何文件落在 `server/`、`admin/`、`plugin/` 路径下**,判为"业务代码直接进 main"→ 拦截,打印清晰提示:`拦截:业务代码不能直接提交到 main,请在 feature/hotfix 分支上提交后再合并。涉及文件:<列出>`。
   - 否则(纯文档/治理/脚本/配置)→ 放行。
   - **应急放行**:当环境变量 `ALLOW_MAIN_BIZ=1` 时,跳过拦截但打印一行醒目提示 `⚠ 已用 ALLOW_MAIN_BIZ 临时放行业务代码进 main`。供极端情况临时绕过。

2. **先 dry-run(只报警不真拦),在测试分支验证——本步是重点:**
   - 先让守卫处于"报告模式"(打印会不会拦,但 `exit 0` 不真的阻止),或用一个 `--dry-run` 参数手动跑。
   - 切到一个测试分支(如 `test/guard-check`),手动构造两种情况各跑一次:
     - **该拦的**:模拟一笔含 `server/` 文件的提交在 main 上 → 守卫应判"拦"。
     - **该放的**:模拟一笔只含 `docs/` 文件的提交在 main 上 → 守卫应判"放"。
   - 把两次判断输出贴回 §5,确认"拦得对、放得对"。

3. **Chase 亲眼确认**(见 §4 给 Chase 的亲眼版),确认无误后再继续。

4. **切真拦 + 挂 pre-commit:**
   - 把守卫接进 pre-commit:提交时自动运行 `scripts/guard-main-commit.sh`,拦截时 `exit 1` 阻止提交。
   - 确保它和 A1/A2 的检查不冲突(pre-commit 里可先跑守卫,再跑 check-governance 体检;体检 WARN 不阻断提交,守卫拦截才阻断——两者职责分开,别混)。

5. **回归自测(证明真拦也对):**
   - 在 main 上真试一笔含 `server/` 改动的提交 → 应被**真的拒绝**。
   - 同样改动放到 feature 分支提交 → 应**通过**。
   - 在 main 上提交一笔纯 docs 改动 → 应**通过**。
   - 用 `ALLOW_MAIN_BIZ=1` 提交一笔 main 上的 server 改动 → 应**放行并打印警告**。
   - 四种输出贴回 §5。(测试用的改动验证完即清理,不留垃圾。)

6. **用法说明**:在 server-access.md 或 release.md 加一行:守卫规则是什么、`ALLOW_MAIN_BIZ=1` 怎么用于应急。

7. **收尾**:`git status` 干净;守卫与 hook 作为**单独 chore commit**。回写 §5、§6,Status 改为 `ready_for_review`,Next Owner = Review(codex)。**注意:挂上 pre-commit 后,本任务自己的这个 commit 是纯脚本/hook/docs,应能正常通过守卫(不含 server/admin/plugin)。**

## 3. Stop Gates(遇到以下情况停下回报)

- dry-run 验证发现**误伤**(正常文档/治理提交被拦)或**漏拦**(业务代码没被拦)——停下报,先修准再继续,**绝不带病挂上 pre-commit**。
- 需要引入**任何新依赖**,或仓库没有现成 hook 方案需要新建一套机制——停下报。
- 守卫与 A1/A2 的 pre-commit 执行互相干扰——停下报。
- 动到 server/admin/plugin 业务代码、规则正文、或已验收脚本。
- 工作区不干净且有无关改动 / merge conflict。
