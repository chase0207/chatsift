## 1. PM 指令

### 用大白话讲

CHANGELOG 里有条教训被记了两遍:"并行发版需明确分支冻结/合入顺序"(W22 并线触发了 v0.6.1→v0.6.3 版本顺延)。记两遍 = 它一直靠人记得、没机制兜底。这张单把它**变成发版前一个必走的声明动作**,并尽量配一道提醒。

**关键边界:只针对"偶尔多分支并进同一次发版"那种情况。** 你们日常基本单线发版——**单线发版完全不变、不增加任何负担**。版本号时机也不动(仍是合并/发版那刻定)。

### 高风险提醒:不碰真实发版脚本

发版是高风险区。本单**只改发版规则文档 release.md + 可能加一道只读提醒**,**绝不修改 `release.sh` / `release-prod.sh` / `check-env-isolation.sh` 的行为**。

### 文件边界

- **允许改**:`docs/ops/release.md`;(仅当并线信号可靠可判时)新增一道只读检查(并入 check-governance 或独立只读脚本);(仅当需要)在发版记录文档加"并线声明栏"的**模板说明**。
- **禁止改**:`release.sh` / `release-prod.sh` / `check-env-isolation.sh` 的逻辑、业务代码、`W23` PRD、`project-workflow.md`、其他规则正文、以及发版记录的**历史条目**(只动模板/新增,不改既往记录)。

### 上位规则

- 不覆盖 AGENTS / PROJECT_STATUS / prod-safety。冲突即停。

## 2. 执行步骤

1. **先核实两件事(不假设,核实后再设计):**
   - a. **发版记录实际写在哪**——PROJECT_STATUS 的发版记录表?还是 CHANGELOG?并线声明就写进那个现有位置,不另起新文档。
   - b. **能否可靠地只读判出"这次是多分支并入"**(例如 release 提交的 merge 来源、或本版 CHANGELOG 条目跨多个 feature 来源)。
     - 判得准 → 可加一道轻提醒(见步骤 4)。
     - **判不准 → 不要硬造不可靠的自动判断**,退化为"发版前人工确认一项"即可(并在未决项说明)。这是 Stop Gate:宁可人工一句,不上会误报/漏报的自动判断。

2. **在 `release.md` 加规则小节「并线发版声明」(仅多分支并入时适用):**
   - 并线发版前**必须先声明并写入发版记录**:本次包含哪几条分支、按什么合入顺序、最终版本号、谁确认。声明完再合并/打 tag。
   - **明确写出:单线发版无需此步**(免得读者误以为每次发版都要走)。
   - 并线未声明而导致版本顺延 / abort = 发版中止 → **触发复盘**(指向 `task-doc-workflow.md` §6.5.1,即 C1 的复盘强制触发)。

3. **在 `release.md` §3 发版前 checklist 加一项:**
   - `[ ] (仅并线发版)已写并线声明:分支清单 + 合入顺序 + 最终版本号`。

4. **(仅当步骤 1b 判得准)加一道只读轻提醒:**
   - 发版相关提交检测到"并线信号"但发版记录里没有并线声明 → 打印提醒。
   - **优先并入 `check-governance`**(作为提醒,不阻断)或做成独立只读脚本;**不改任何发版脚本**。
   - 判不准就跳过本步,记入 §6 未决项,保留步骤 3 的人工 checklist 项兜底。

5. **收尾:** 改了 release.md → 文档头版本 +1 + changelog 加行;跑 `bash scripts/check-governance.sh` 期望 `WARN 0`;单独 commit;Status → `ready_for_review`。
