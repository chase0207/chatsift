## 1. PM 指令

### 用大白话讲:这个脚本是干嘛的

你们现在用"一个任务一个文档"管事(任务单放在 `docs/tasks/active/`,做完移到 `docs/tasks/done/`)。规则要求每张任务单必须填齐一些关键栏目(比如"谁负责""改动等级""谁审批"),做完才能移走。

**问题是:这些要求现在全靠人记得检查。** 漏填一栏、做完忘了移走、状态和记录对不上——没人会立刻发现。

这个脚本就是替你做这件检查的"机器人":它**只看、不改**,扫一遍所有任务单,把"哪张缺了栏目""哪张做完了还赖在 active 里""哪张状态和内容对不上"全列出来。以后每次提交自动跑,你就不用再一张张人工盯了。

它**不碰任何代码逻辑、不改任何文件**,只是读任务单 + 打印一份体检报告。风险极低。

### 目标

新增一个只读检查脚本,自动核对 `docs/tasks/` 下任务单是否合规;并把它和 A1 的检查并到一个统一入口,为后续"一道门管全部检查"打底。

### 范围(只做这些)

写一个检查任务单的脚本 + 一个把它和 A1 串起来的总入口脚本 + 自测。**不改任何任务单内容,不碰业务代码,不接 pre-commit(那是后面 D 阶段的事)。**

### 文件边界

- **允许改 / 新增**:
  - 新增 `scripts/check-tasks.sh`(或 `.js`,用仓库现有运行时,不引入新依赖)
  - 新增 `scripts/check-governance.sh`(总入口:依次调用 A1 的 `check-doc-freshness` 和本脚本,合并打印)
  - 在 `docs/ops/server-access.md` 或 `release.md` 加**一行**说明这两个脚本怎么跑
- **禁止改**:任何 `docs/tasks/` 下的真实任务单内容、任何业务代码(server/admin/plugin)、任何规则正文。

### 上位规则

- 本任务单不覆盖 `AGENTS.md`、`PROJECT_STATUS.md`、`docs/ops/prod-safety.md`。如有冲突,停下回报。

## 2. 执行步骤

1. **确认要检查哪些栏目(以规则文档为准,不要自己另定一套)。**
   要求的栏目以 [`docs/ops/task-doc-workflow.md` §6.6](../ops/task-doc-workflow.md) 为唯一依据。
   （当前 §6.6 规定 active 任务单必须有:`Status`、`Role`、`Next Owner`、`Problem Layer`、`Change Class`、`Approver`、`Commit Policy`。脚本应以 §6.6 实际内容为准——若日后 §6.6 改了,脚本逻辑也应据之调整,不在本脚本里另立一份字段清单当真源。）

2. **写检查脚本 `scripts/check-tasks.sh`,只读,做以下三类检查,每条打印 `[PASS]` 或 `[WARN] 文件 + 问题`:**
   - **检查 A(字段齐全)**:遍历 `docs/tasks/active/*.md`,逐张确认上面那组必填栏目都存在且非空。缺哪栏 → `WARN` 列出文件 + 缺的栏目。
   - **检查 B(状态与记录匹配)**:
     - 标了 `Status: ready_for_review` 的,必须能在文中找到 `commit`、检查命令、检查结果——缺 → `WARN`。
     - 标了 `Status: blocked` 的,必须写了阻塞原因、触发的 Stop Gate、需要谁拍板——缺 → `WARN`。
   - **检查 C(归档纪律)**:任何 `Status: done` 的任务单都不应还留在 `docs/tasks/active/`(应已移入 `done/`)→ 若留在 active 则 `WARN`。
   - **输出**:逐条结果 + 末尾汇总 `PASS x / WARN y`。脚本**只读,绝不改任何任务单**。
   - **不要做的检查**:文档头版本 == changelog 顶行这条**归 A1 管**,本脚本不要重复做(避免两个脚本查同一件事,那本身就是新的重复)。

3. **写总入口 `scripts/check-governance.sh`:**
   - 依次调用「A1 的 `scripts/check-doc-freshness`」+「本任务的 `scripts/check-tasks`」,把两份报告合并打印,末尾给总的 `PASS / WARN` 数。
   - **兼容写法**:若 `check-doc-freshness` 尚不存在(A1 还没合并),则跳过它、只跑 `check-tasks`,并打印一行提示"A1 检查未就位"。这样本任务不被 A1 卡住。
   - 以后所有治理检查都往这个总入口里加,保证"只有一道门",脚本本身不散落。

4. **自测(证明机器人真的会抓,这步是重点):**
   - 先跑 `bash scripts/check-governance.sh`,当前应**全 PASS**(现有任务单本就合规)。把输出贴回 §5。
   - 在 `docs/tasks/active/` 临时新建一张**测试用**任务单 `__test_broken.md`,故意**漏填一个必填栏目**(如不写 `Approver`)。再跑,确认脚本 `WARN` 抓到它。
   - **删掉**这张 `__test_broken.md`,再跑,确认恢复全 PASS。
   - 三次输出都贴回 §5。(测试任务单用完即删,不留在仓库。)

5. **用法说明**:在 `docs/ops/server-access.md` 或 `release.md` 加一行,写明 `bash scripts/check-governance.sh` 怎么用、查什么。

6. **收尾**:`git status` 干净;脚本作为**单独 chore commit**(例:`chore: 新增任务单一致性检查 + 治理检查总入口`)。回写 §5、§6,Status 改为 `ready_for_review`,Next Owner = Review(codex)。

## 3. Stop Gates(遇到以下情况停下回报)

- 检查逻辑需要**修改任何真实任务单**才能通过——本脚本只读,绝不改任务单;真有任务单不合规,只报告、不代填。
- 脚本实现需要**引入任何新依赖**。
- 想顺手把脚本**接进 pre-commit / CI**——本任务不做,留给 D 阶段。
- 想顺手做"文档头版本一致"检查——那归 A1,本任务不做。
- 动到 `docs/tasks/` 真实任务单、业务代码或任何规则正文。
- 工作区不干净且有无关改动 / merge conflict。
